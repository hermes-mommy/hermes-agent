## 1. Root Cause Analysis

### 1.1 Failure Sequence

| Attempt | Migration File | Failure Point | Error | DB State After |
|---------|---------------|---------------|-------|----------------|
| 1st | Original autogenerated (without schema creation) | First `CREATE TABLE` referencing `agents` schema | `schema "agents" does not exist` | Baseline (clean rollback) |
| 2nd | Patched via `patch-migration.py` (schemas added) | `add_compression_policy('surveillance.events', INTERVAL '7 days', if_not_exists => TRUE)` | `columnstore not enabled on hypertable "events"` | Baseline (confirmed) |

### 1.2 Direct Cause

The `patch-migration.py` script added these operations for `surveillance.events` in wrong order:

```python
# From patch-migration.py — lines 66-68
op.execute("SELECT create_hypertable('surveillance.events', ...)")       # ✅ Creates hypertable
op.execute("SELECT add_compression_policy('surveillance.events', ...)")  # ❌ Fails — compression NOT enabled
op.execute("SELECT add_retention_policy('surveillance.events', ...)")    # Would have worked (retention doesn't need compression)
```

**Missing**: `ALTER TABLE surveillance.events SET (timescaledb.compress, ...)` between `create_hypertable` and `add_compression_policy`.

TimescaleDB requires **explicit columnstore enablement** via `ALTER TABLE ... SET (timescaledb.compress, ...)` before any `add_compression_policy()` call. Without it, the policy has no columnstore engine to operate on.

### 1.3 Why memory.episodes Didn't Fail (But Was Wrong Too)

The `patch-migration.py` for `memory.episodes`:
```python
op.execute("SELECT create_hypertable('memory.episodes', ...)")
op.execute("ALTER TABLE memory.episodes SET (timescaledb.compress, ...)")  # ✅ Has this
op.execute("SELECT add_compression_policy('memory.episodes', ...)")        # ✅ Would work
```

The episodes block had the correct order, but the **events block did not** — it was simply missing the ALTER TABLE step.

### 1.4 Current Local Migration State (e401bb5fd274)

The local copy `tmp/migration.py` shows signs of manual repair AFTER the failures:

| Table | Inline After CREATE TABLE | Manual Patch Section (line 1053+) | Issues |
|-------|--------------------------|-----------------------------------|--------|
| `memory.episodes` | `create_hypertable('memory.episodes', 'started_at', INTERVAL '7d')` | `create_hypertable('memory.episodes', 'started_at', INTERVAL '7d')` — **DUPLICATE** | Redundant call (harmless with `if_not_exists`, but sloppy) |
| `surveillance.events` | `create_hypertable(... INTERVAL '1 day')` + `add_retention_policy('180 days')` + **comment: "# Compression policy deferred"** | `create_hypertable(... INTERVAL '7 days')` — **DIFFERENT chunk interval than inline!** | Two hypertable calls with conflicting chunk intervals |
| `audit.audit_trail` | `create_hypertable(... INTERVAL '1 month')` + `add_retention_policy('1 year')` | `create_hypertable(... INTERVAL '1 month')` — **DUPLICATE** | Harmless duplicate |
| `financial.transactions` | `create_hypertable(... INTERVAL '1 month')` + `add_retention_policy('7 years')` | `create_hypertable(... INTERVAL '1 month')` — **DUPLICATE** | Harmless duplicate |

**Key observation**: The local `e401bb5fd274` already has compression **deferred** for both `memory.episodes` and `surveillance.events`. This is the correct fix. The only remaining issue is the duplicate/scattered hypertable calls.

## 3. Recovery Options

### OPTION A (RECOMMENDED): Defer Compression — Minimal Patch to e401bb5fd274

**Effort**: Quick (<1h)  
**Risk**: Very Low  
**What**: Use the local `e401bb5fd274` migration as-is for core tables + retention policies, but clean up the clustered manual patch section and defer ALL compression policies.

**Required changes to `e401bb5fd274`**:

1. **Remove duplicate hypertable calls from manual patch section** (lines 1053-1058). Delete the 4 `create_hypertable` calls since they're already done inline after each table definition.

2. **Consolidate into the manual patch section** only: HNSW indexes + B-tree indexes for FK lookups (lines 1059-1063). These are the only operations that can't be autogenerated.

3. **Verify no `add_compression_policy` exists anywhere** in the migration. Compression is fully deferred.

4. **Remove the duplicate `create_hypertable('surveillance.events', ... INTERVAL '7 days')`** at line 1058 (already in manual patch section), AND decide which chunk interval is correct for events — the inline says 1 day, the manual patch says 7 days. Keep **1 day** (higher-volume surveillance data benefits from smaller chunks).

**Why this is safe**:
- 47 tables created as standard PostgreSQL tables
- 4 hypertables created (no compression, no columnstore)
- 3 retention policies added (retention works without compression)
- Compression deferred to follow-up migration
- HNSW indexes on vector columns created
- B-tree indexes on FK lookup columns created
- Downgrade cleanly drops tables (hypertables are dropped as normal tables)

**Follow-up**: P3-004 (or P3-002b) — focused migration that adds:

## 7. Edge Cases

- **Duplicate hypertable call with different chunk intervals**: If line 1058's `create_hypertable('surveillance.events', ... INTERVAL '7 days')` runs AFTER line 973's `create_hypertable(... INTERVAL '1 day')`, TimescaleDB with `if_not_exists => TRUE` will silently skip. The chunk interval from the FIRST call (1 day) will be used. Remove line 1058 to avoid confusion.
- **TimescaleDB 2.x vs 3.x `create_hypertable` behavior**: Both versions accept `if_not_exists` and will not error on existing hypertables with matching parameters. Different chunk intervals are ignored on re-run.
- **`compression_policy` with `if_not_exists => TRUE`**: Even with `if_not_exists`, TimescaleDB 2.x still validates that the hypertable has columnstore enabled. It does NOT skip silently — it errors. This is the root cause of the failure.
