 2. ROTATION PROCEDURE
===============================================================================

  2.1  SOPS re-encryption
       a) Generate new secret value for the target credential.
       b) Update the value in the plaintext source file.
       c) Run: sops --encrypt --in-place <source-file>
       d) Confirm the encrypted file is valid: sops --decrypt <source-file>
          produces the expected plaintext.
       e) Commit the re-encrypted SOPS file to the repository.

  2.2  Deployment
       a) Push the commit containing the new encrypted secrets.
       b) Pull on the target VPS: git pull origin <branch>.
       c) Decrypt the file to the runtime path:
          sops --decrypt <source-file> > <runtime-path>
       d) Set restrictive permissions: chmod 600 <runtime-path>.

  2.3  Service reload
       a) For each service that reads the rotated secret, reload:
          systemctl daemon-reload          (if unit file changed)
          systemctl restart <service>      (e.g. hermes-gateway, guinevere-mcp)
       b) For Discord bot token: restart the Discord bot service.
       c) For Redis AUTH: update requirepass in redis.conf, then:
          redis-cli CONFIG SET requirepass '<new-password>'
          redis-cli CONFIG REWRITE
       d) For PostgreSQL: ALTER USER <user> PASSWORD '<new-password>';
          then update the connection string in the consuming service.

  2.4  Verification
       a) Confirm the service pod/process is running:
          systemctl status <service>
       b) Confirm the service can authenticate:
          - Discord bot: bot presence visible in Discord channel.
          - Redis: redis-cli PING returns PONG after AUTH.
          - PostgreSQL: pg_isready or SELECT 1 via the app user.
          - 9Router API: invoke a test endpoint and confirm 200 OK.
          - SOPS age key: sops --decrypt <any-encrypted-file> succeeds.
       c) Check service logs for auth errors:
          journalctl -u <service> --since "5 minutes ago" | grep -i "auth\|error\|fail"

  2.5  Audit log update
       a) Record the rotation in the security audit log:
          Date, secret rotated, operator, verification result.
       b) Update the Next Scheduled column in this schedule file.
       c) If rotation failed or was blocked, add an entry to the
          Blocker Register (docs/20-security/hermes-phase-7-blocker-register.md).

 3. KNOWN BLOCKER — Restic/Offsite Backup Credential Restoration
===============================================================================

  DR research (phase 7) found that SOPS-encrypted restic credentials are
  missing from secrets/backup/. The restic restore command cannot proceed
  without these files.

  Impact:  Restoration of offsite backups is blocked.
  Blocker: B10 (SOPS credentials missing) and B11 (backup sentinel missing)
           in docs/20-security/hermes-phase-7-blocker-register.md.
  Action:  Credentials must be regenerated or restored from a secure offline
           source before the next rotation window. File issue under Phase 7c.

  Once credentials are available, the rotation cadence for restic credentials
  should be 90 days, following the same SOPS re-encryption procedure above.

 4. NOTES
===============================================================================

  - This file is a schedule and procedure reference only. It does not
    constitute proof that any rotation has been performed.
  - Actual rotation must be recorded in the security audit log with date,
    operator, and verification outcome.
  - SOPS-encrypted secrets are stored in the repository. Access to the age
    private key is required for decryption.
  - All cadences start from the first scheduled rotation. The Next Scheduled
    column is updated after each completed rotation.
  - Emergency rotation (on suspected compromise) follows the same procedure
    immediately, regardless of the cadence window.
