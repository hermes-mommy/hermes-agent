### Step P13-010: Session Recovery

**Type:** Application
**Status:** Not Started
**Risk:** High
**Git Commit:** `feat(P13): pending`

**Goal:** Implement the manual X session recovery flow that responds to an expired P13 X session by moving all pending and processing posts to `held/`, sending a Discord alert in `#guinevere-alerts`, blocking any automated login retry, and enabling `/x-resume` to move held items back to `pending/` after Faiz re-exports and SOPS re-encrypts fresh cookies.
**Dependencies:** P13-005 Queue Polling Loop, P13-008 Cookie Injector, P13-009 Session Health Check, P13-022 Status Commands.
**Cost Impact:** $0/month direct; uses existing S3 prefix state machine and Discord bot.
**ADR References:** ADR-016 (SOPS + age secrets management), P13 requirements sections 2.2, 5.2, 5.3, 7.1, and 8.1.
**Acceptance Criteria:** AC-POSTING-005 (expiry moves queue to held and notifies), AC-POSTING-007 (`/x-resume` command functional), AC-POSTING-004 (session expired is manual recovery).
**Estimated Time:** 4 hours

#### Context

X authentication is sensitive and must remain manual. When P13-009 classifies the X session as expired, Guinevere must stop posting safely, preserve queued work, alert Faiz, and wait for manual re-authentication. The correct recovery path is: Faiz exports fresh cookies from the laptop browser, those cookies are SOPS re-encrypted, the VPS picks up the updated encrypted secret, P13-008 reinjects the cookies into the dedicated Obscura 9223 context, and `/x-resume` returns held queue items to `pending/`.

This step must not implement automated login, password submission, MFA automation, or repeated login retries. The queue state transition is protective: all `pending/` and `processing/` posts move to `held/` so the system cannot keep attempting posts with a bad session. The Discord alert must be clear, actionable, and posted to `#guinevere-alerts` with the exact message core: `X session expired — manual re-auth required`.

After Faiz completes manual re-auth (export → SOPS re-encrypt → VPS pickup → P13-008 injection), the `/x-resume` command is the recovery trigger. It must verify that the freshly injected session is valid (potentially by running a lightweight health check against the Obscura context) before moving held items. If the session is still expired despite new cookies, the held items must remain in `held/` and Faiz should be alerted again. This prevents a premature resume that would immediately re-trigger session expiry.

#### Troubleshooting
- **Issue:** Some `processing/` items are older than the 30-minute processing timeout.
  - **Solution:** Session recovery wins over processing timeout; move them to `held/` and document the transition.
- **Issue:** Discord alert sends repeatedly every heartbeat.
  - **Solution:** Add an idempotent session-expired state or alert cooldown keyed by active expired-session incident.
- **Issue:** `/x-resume` runs before fresh cookies are injected.
  - **Solution:** Require a fresh successful P13-009 health check or explicit re-auth marker before moving held items back to `pending/`.
- **Issue:** A sidecar is missing during held transition.
  - **Solution:** Move the image to `held/`, log the missing sidecar as a recoverable metadata issue, and preserve the object for manual review.
- **Issue:** Multiple concurrent expiry detections before the recovery flow completes.
  - **Solution:** Use a session-expired incident lock (in-memory or Redis) to prevent duplicate held transitions and redundant Discord alerts.

#### Notes
- Session recovery is manual by design because automated login to X is too risky.
- This step must coordinate with P13-009 but must not weaken the health check.
- Keep alerts actionable and minimal; do not include cookie values, auth tokens, filenames with sensitive personal context, or decrypted secret paths.
- Use Gemini Flash default and Gemini Pro fallback only in caption/moderation steps; recovery should not require LLM calls.
- The session-expired incident state should publish to the `p13_session_expired` gauge metric for Grafana monitoring (wired in P13-026).
- Do not add cookie validation logic to the recovery flow itself; P13-009 remains the sole health check gate.
- Use `post-launch` for future multi-account or richer recovery enhancements.
