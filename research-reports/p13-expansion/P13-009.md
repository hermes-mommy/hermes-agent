### Step P13-009: Session Health Check

**Type:** Application
**Status:** Not Started
**Risk:** High
**Git Commit:** `feat(P13): pending`

**Goal:** Implement the mandatory pre-post X session health check that navigates the dedicated Obscura CDP browser to `https://x.com/home`, waits for a complete DOM load, verifies the page is not an X login flow, and returns either healthy/proceed or expired/recovery-required before every post attempt.
**Dependencies:** P13-003 Obscura 9223, P13-008 Cookie Injector, P13-005 Queue Polling Loop, P13-010 Session Recovery.
**Cost Impact:** $0/month direct; uses existing dedicated Obscura 9223 runtime and existing logging/Discord infrastructure.
**ADR References:** ADR-016 (SOPS + age secrets pattern), existing browser automation ADRs for Obscura/CDP isolation, P13 requirements section 5.3.
**Acceptance Criteria:** AC-POSTING-005 (health check before each post, expiry moves queue to held and notifies), AC-POSTING-010 (dry-run includes session check).
**Estimated Time:** 3 hours

#### Context

P13 posts to X through a dedicated Obscura browser context on port 9223. That context is initialized from SOPS-encrypted cookies and persisted through a dedicated storage directory, but X sessions can expire or rotate without warning. This step creates the defensive pre-post gate: every post attempt must verify the account is still logged in before any caption, media upload, compose navigation, or post action proceeds.

The health check is intentionally simple and deterministic. Navigate to `https://x.com/home` via CDP, wait until `document.readyState === 'complete'`, reject known login URLs, and reject login-page DOM text such as `Sign in to X`. If the session is healthy, the posting pipeline may continue. If expired, this step must hand off to P13-010 Session Recovery and must not attempt to log in automatically.

The gate runs as part of the heartbeat cycle managed by the queue polling loop: before the queue moves an item from `pending/` to `processing/` for the compose/post phase, the session health check is invoked. If healthy, the queue proceeds normally. If expired, the queue engine should not advance any items into processing until P13-010 recovery completes and `/x-resume` is called. This design prevents partial post attempts on a stale session and keeps the queue state consistent.

#### Troubleshooting
- **Issue:** `document.readyState` never reaches `complete`.
  - **Solution:** Use a bounded timeout and classify the check as unhealthy/recovery-required only if the page is stuck in a login or unusable state; otherwise record a transient browser error for the retry engine.
- **Issue:** X redirects through an intermediate auth flow URL.
  - **Solution:** Treat any `/login` or `/i/flow/login` URL as expired and hand off to P13-010.
- **Issue:** The DOM text check matches unrelated text.
  - **Solution:** Prefer exact visible login prompt checks and combine DOM text with URL checks; document any selector-specific refinement in evidence.
- **Issue:** CDP page object is unavailable.
  - **Solution:** Fail closed for the current post attempt and route through the error classifier; do not skip the pre-post gate.
- **Issue:** Cloudflare challenge or bot detection page appears after navigation.
  - **Solution:** Treat any unexpected CAPTCHA or challenge page as an unhealthy session; route to P13-010 recovery so Faiz can intervene manually.

#### Notes
- This step is a safety gate, not a recovery implementation. Queue movement to `held/` and Discord alerting belong to P13-010.
- The check must run before every post, including immediate posts and dry-run simulations.
- Do not add auto-login, password filling, MFA automation, or credential prompts.
- Keep X session state isolated to Obscura port 9223 and the dedicated X storage directory.
- Use Gemini Flash default and Gemini Pro fallback only in later caption/moderation steps; this session check should not call an LLM.
