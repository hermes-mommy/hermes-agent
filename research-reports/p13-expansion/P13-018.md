#### 1. Context

The retry engine is the recovery layer for transient P13 failures. It classifies errors into `network`, `rate_limit`, `dom_change`, `media_upload`, `llm_error`, `session_expired`, `corrupt`, and `content_blocked`, then applies the correct action for each class.

The standard retry policy is three attempts with delays of 30 seconds, 2 minutes, and 5 minutes. The policy is not universal: rate limits return the object to pending for the next day, DOM changes pause the queue and notify, media upload failures retry media upload only, LLM errors use a generic caption fallback, session expiry moves to held, corrupt files fail immediately, and content blocks fail immediately with moderation reason.

Retry count must be tracked in S3 object metadata so crash/restart does not reset attempts.

#### 4. Implementation Requirements

- Define a typed error classification model for all eight error classes.
- Map low-level exceptions and validation failures into domain classifications at pipeline boundaries.
- Apply retry delays exactly: first retry after 30 seconds, second after 2 minutes, third after 5 minutes.
- After the third failed retry, move object to `/failed/` with the final error reason.
- Network errors retry the full post attempt while preserving existing generated caption where available.
- Rate-limit errors do not retry the same day; move back to `/pending/` with next-day scheduling metadata if the system supports it.
- DOM change errors do not retry; notify Discord and pause the queue for investigation.
- Media upload failures retry only the upload portion and reuse caption, alt text, and moderation result.
- LLM errors do not retry LLM generation after primary and fallback model fail; use generic caption fallback.
- Session expired errors move to `/held/` and request manual re-auth.
- Corrupt files move to `/failed/` with reason `corrupt_file`.
- Content-blocked items move to `/failed/` with reason `content_blocked` and moderation detail.
- Track `retry_count` in S3 object metadata and preserve existing metadata fields.
- Emit metrics with `reason` labels for failure classes.
- Every exception handler must log classification, object key, retry count, and next action.

#### 8. Troubleshooting

- **Issue:** retry count resets after restart.
  - **Solution:** Read retry_count from S3 metadata at object acquisition time and update it through a single metadata writer.
- **Issue:** media upload retry regenerates caption.
  - **Solution:** Store generated caption in the in-memory post plan and sidecar cache before upload attempts.
- **Issue:** rate-limit handling posts later the same day.
  - **Solution:** Persist next eligible timestamp and enforce it before queue selection.
- **Issue:** DOM selector failure loops.
  - **Solution:** Classify selector failures as `dom_change` and pause immediately.

#### 9. Notes

- Retry logic must be deterministic and auditable.
- A retry should never create duplicate X posts.
- Backoff timing should be testable without waiting real wall-clock time by injecting a clock or scheduler abstraction.
- Retry metadata is operational state, not a substitute for PostgreSQL per-post logs.
- Keep this compatible with post-launch alerting and operations.
