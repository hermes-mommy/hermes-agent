### Step P13-020: Processing Timeout Handler

**Type:** Application
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P13): pending`

**Goal:** Implement a timeout sweeper that reclaims S3 objects stuck in `/processing/` for more than 30 minutes by moving them back to `/pending/` and logging the timeout event.
**Dependencies:** P13-001 S3 Queue Setup, P13-005 Queue Polling Loop, P13-018 Retry Engine, P13-026 Grafana Dashboard.
**Cost Impact:** Minimal S3 list/copy/delete requests; no new infrastructure.
**ADR References:** P13 requirements sections 2.2 and 7.4, ADR-015 for credential handling.
**Acceptance Criteria:** AC-POSTING-001, AC-POSTING-004, AC-POSTING-008.
**Estimated Time:** 2.5 hours.

#### 1. Context

Objects move from `/pending/` to `/processing/` when the poster starts work. If the VPS crashes, the process is killed, or a restart interrupts the pipeline, an object can remain stuck in `/processing/` forever. The processing timeout handler prevents queue starvation.

The timeout threshold is 30 minutes after the object enters `/processing/`. The handler must use the S3 object `LastModified` timestamp for timeout calculation and move timed-out objects back to `/pending/`. It must log the object key and stuck duration.

#### 4. Implementation Requirements

- Add a processing timeout sweeper that scans `guinevere-assets/x-poster/processing/`.
- Use S3 `LastModified` as the source of truth for object age.
- Treat objects older than 30 minutes as timed out.
- Move timed-out image objects back to the matching `/pending/` key.
- Move or preserve matching sidecar JSON consistently with the image object.
- Preserve metadata, including retry count and original upload identifiers.
- Log timeout event with object key, duration, original processing key, reclaimed pending key, and timestamp.
- Increment a timeout metric for monitoring.
- Ensure the sweeper is idempotent if run multiple times.
- Ensure an object currently being processed by an active worker is not reclaimed before 30 minutes.
- Run sweeper on startup before normal queue acquisition.
- Run sweeper periodically during the heartbeat loop.
- Do not mark timeout as content failure.
- Do not send noisy Discord alerts for every timeout unless requirements later wire alerting; structured logs and metrics are required.

#### 8. Troubleshooting

- **Issue:** sidecar remains in processing while image returns to pending.
  - **Solution:** Treat image and sidecar as a pair and move both through the same state transition helper.
- **Issue:** LastModified changes during copy and causes confusing duration.
  - **Solution:** Log the source object's LastModified before copy and include reclaimed timestamp separately.
- **Issue:** duplicate pending keys appear.
  - **Solution:** Use deterministic key mapping and check destination before copy.
- **Issue:** active worker loses ownership after long media upload.
  - **Solution:** Keep live processing under 30 minutes or add explicit heartbeat metadata in a later refinement.

#### 9. Notes

- This handler is crash recovery, not failure classification.
- Reclaimed objects may be retried by normal queue logic.
- Do not increment consecutive failure circuit breaker count for timeout reclaim alone.
- The handler should be safe for launch and post-launch operations.
- Use UTC timestamps internally and display WIB only in human-facing reports.
