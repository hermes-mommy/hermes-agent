**Goal:** Implement two Faiz-only Discord commands — `/x-retry-failed` and `/x-retry <filename>` — that move failed posts back to the pending queue for automatic reprocessing, resetting retry metadata in the process.
**Dependencies:** P13-001 S3 Queue Setup, P13-005 Queue Polling Loop, P13-006 Sidecar Parser, P13-018 Retry Engine, P13-022 Status Commands, existing Discord infrastructure.

**Estimated Time:** 2 hours.

#### 1. Context

Posts in `/failed/` may have failed for transient reasons — network errors, content moderation false positives, or cancelled-by-operator that Faiz later decides to post. `/x-retry-failed` iterates all objects under `guinevere-assets/x-poster/failed/` and moves them to `/pending/`. `/x-retry <filename>` does the same for a single specified file.

Both commands reset the `retry_count` metadata in the sidecar or S3 metadata to zero so the retry engine treats the post as a fresh attempt. This prevents the post from immediately exhausting its retry budget.

The retry engine's standard retry policy (30s/2m/5m, up to 3 attempts) applies after the file enters `/pending/`. Files moved by retry commands are not immediately posted — they enter the queue and wait for the next heartbeat cycle like any other pending file. This preserves FIFO ordering.

#### 4. Implementation Requirements

- Register `/x-retry-failed` as a Faiz-only slash command with no additional options.
- Register `/x-retry <filename>` as a Faiz-only slash command with one required option: `filename` (string, basename without prefix).
- `/x-retry-failed` lists all objects under `guinevere-assets/x-poster/failed/` and groups them by basename (image + sidecar pairs).
- For each failed pair, copy the image and sidecar to `guinevere-assets/x-poster/pending/` with the same basename.
- After copy, delete the source objects from `/failed/`.
- Reset `retry_count` to zero in the sidecar JSON before writing to pending.
- If the sidecar has no `retry_count` field, add it with value 0.
- Preserve all other sidecar fields — do not mutate `caption`, `custom_alt`, `tags`, `schedule`, or other metadata.
- `/x-retry <filename>` performs the same operation for a single matching basename in failed/.
- Report count of successfully retried files in the command response.
- `/x-retry-failed` response: "Retried N files (M succeeded, F failed) from failed/ to pending/."
- `/x-retry` response: "Retried <filename> to pending/." or "File <filename> not found in failed/."
- Handle edge case: failed/ is empty → "No failed files to retry."
- Handle edge case: filename exists in failed/ but is malformed → skip with warning.
- Handle edge case: destination filename already exists in pending/ → append timestamp suffix to avoid collision.
- Handle edge case: sidecar is missing for an image in failed/ → create a minimal sidecar with caption=null and retry_count=0.
- Handle edge case: `/x-retry` with non-existent filename → "File not found in failed/."
- Log retry command execution with command name, file count, success count, failure count, and timestamp.
- Do not retry files with reason `"content_blocked"` unless explicitly overridden — return warning: "Content-blocked files require manual review. Use /x-retry-reason overridden for this case." (Post-launch refinement.)

#### 8. Troubleshooting

- **Issue:** retry moves files but retry_count is not persisted.
  - **Solution:** Sidecar must be re-read, modified, and re-uploaded after the copy; verify the write-to-pending step includes the updated sidecar, not the original.
- **Issue:** image moved but sidecar remains in failed/ (orphan).
  - **Solution:** Always process image+sidecar as a pair; if sidecar write fails, abort the image move and log.
- **Issue:** file retried but immediately fails again with same error.
  - **Solution:** The error was likely not transient; suggest Faiz investigate before retrying further. Circuit breaker may also be preventing processing.
- **Issue:** failed/ contains files from old P13 versions with different sidecar schema.
  - **Solution:** Validate sidecar against current schema before move; log schema version mismatch and skip if incompatible.
- **Issue:** retry floods pending queue with many files.
  - **Solution:** `/x-retry-failed` logs the count and warns if more than 10 files are being retried at once.

#### 9. Notes

- Retry commands are for operator recovery — they bypass automatic retry limits intentionally.
- Content-blocked files should not be retried without manual review of the moderation reason.
- Resetting retry_count prevents the retry engine from exhausting the budget immediately.
- The commands do not trigger immediate posting; files enter the FIFO queue like any other pending item.
- Keep suitable for post-launch operations — Faiz may use these after investigating a failure.
- Idempotent: retrying the same file twice will fail the second time (file already moved or already in pending).
