### Step P13-021: Post Notification

**Type:** Application
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P13): pending`

**Goal:** Implement Discord and Gotify notification flows for P13 post success, failure, content-blocked events, and critical fallback delivery.
**Dependencies:** P13-011 Caption Generator, P13-012 Content Moderation, P13-016 Post Action, P13-018 Retry Engine, P13-019 Circuit Breaker, existing P2 Gotify infrastructure.
**Cost Impact:** $0/month; uses existing Discord and Gotify integrations.
**ADR References:** P13 requirements sections 8.1, 8.3, and 10.3; PersonaSafetyPolicy for consent-aware messaging.
**Acceptance Criteria:** AC-POSTING-004, AC-POSTING-006, AC-POSTING-008.
**Estimated Time:** 3 hours.

#### 1. Context

P13 must report outcomes clearly to Faiz. Successful posts go to `#guinevere-status` with a caption preview, hashtags, image count, latency, and link to the posted tweet. Failures go to `#guinevere-status` with error reason, filename, retry count, and next retry time. Content-blocked events go to `#guinevere-alerts` with filename and moderation reason.

Critical events must fall back to Gotify using existing P2 infrastructure. Critical events include content blocked, session expired, circuit breaker opened, and any notification delivery failure that would hide an important operational state.

#### 4. Implementation Requirements

- Implement a success notification embed for `#guinevere-status`.
- Success embed includes caption preview limited to first 100 characters.
- Success embed includes hashtags, image count, latency, posted timestamp, and tweet link.
- Implement a failure notification embed for `#guinevere-status`.
- Failure embed includes error reason, filename, retry count, and next retry time when applicable.
- Implement a content-blocked notification embed for `#guinevere-alerts`.
- Content-blocked embed includes filename and moderation reason.
- Use Gotify fallback for critical events and critical Discord delivery failures.
- Reuse existing P2 Gotify configuration; do not introduce duplicate credentials.
- Keep Discord embed text concise and operator-readable.
- Avoid raw secrets, raw cookies, full S3 credentials, or sensitive personal data in notifications.
- Include correlation identifiers such as object key basename or post attempt ID.
- Record notification delivery result in logs.
- Support testable payload builders separate from network senders.

#### 8. Troubleshooting

- **Issue:** tweet URL is missing after success.
  - **Solution:** Include post identifier from success verification; if unavailable, link to profile and mark URL unresolved in logs.
- **Issue:** Discord embed exceeds limits.
  - **Solution:** Enforce caption preview and field length limits in the payload builder.
- **Issue:** Gotify fallback sends duplicate critical alerts.
  - **Solution:** Deduplicate by event type and correlation identifier inside the cooldown window.
- **Issue:** moderation reason includes sensitive text.
  - **Solution:** Send category and concise reason, not raw unsafe content.

#### 9. Notes

- Notification payload builders should be pure functions for stable tests.
- Discord channel names are human requirements; implementation should use configured channel IDs.
- Gotify is fallback for critical events, not a replacement for normal Discord status updates.
- Keep messages suitable for launch and post-launch operations.
- Failure notifications should help Faiz decide whether to wait, retry, or investigate.

#### 10. Acceptance Mapping

- AC-POSTING-004: failure notifications expose retry and next action.
- AC-POSTING-006: content-blocked notifications report moderation result.

- Boundary proof: no secret leakage, no unsafe content echoing, and no silent notification failure.
