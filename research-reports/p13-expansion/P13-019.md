### Step P13-019: Circuit Breaker

**Type:** Application
**Status:** Not Started
**Risk:** High
**Git Commit:** `feat(P13): pending`

**Goal:** Implement a PostgreSQL-backed circuit breaker for X Auto Poster that pauses queue processing after five consecutive failures, alerts Discord with cooldown, and recovers through `/x-resume`.
**Dependencies:** P13-005 Queue Polling Loop, P13-018 Retry Engine, P13-021 Post Notification, P13-022 Status Commands.
**Cost Impact:** $0/month; uses existing PostgreSQL and Discord infrastructure.
**ADR References:** ADR-023-style persistent operational tracking pattern where applicable, ADR-015 for secret safety, P13 requirements section 7.3.
**Acceptance Criteria:** AC-POSTING-004, AC-POSTING-007, AC-POSTING-008.
**Estimated Time:** 3.5 hours.

#### 1. Context

The circuit breaker prevents repeated automated posting attempts when the system is clearly unhealthy. It opens after five consecutive posting failures of any error type. Once open, the queue is auto-paused and no new posts are attempted until Faiz manually resumes via `/x-resume`.

The circuit state must live in PostgreSQL using `circuit_state` values `closed`, `open`, and `half-open`. Alert spam must be controlled with a 30-minute cooldown between consecutive failure alerts. The breaker should integrate with status commands and metrics so Faiz can see why posting is paused.

#### 4. Implementation Requirements

- Add PostgreSQL persistence for circuit breaker state if not already present.
- Store state as one of `closed`, `open`, or `half-open`.
- Track consecutive failure count, last failure timestamp, last alert timestamp, last error class, and pause reason.
- Increment consecutive failure count after a final failed post outcome, not after every retry attempt.
- Reset consecutive failure count after a successful post.
- Open the circuit when consecutive failures reach five.
- Auto-pause queue processing immediately when circuit is open.
- Send a Discord alert to `#guinevere-alerts` when the circuit opens.
- Enforce 30-minute cooldown for repeated failure alerts.
- Wire `/x-resume` to close or half-open the circuit after Faiz approval.
- On resume, allow one guarded attempt in `half-open` if that state is implemented.
- If the guarded attempt succeeds, close the circuit and reset consecutive failures.
- If the guarded attempt fails, return to open and alert only if cooldown allows.
- Expose circuit state in `/x-status` output.
- Emit metrics for circuit state and consecutive failure count.

#### 8. Troubleshooting

- **Issue:** circuit opens during retry attempts before final failure.
  - **Solution:** Increment breaker only when retry engine emits a final outcome event.
- **Issue:** alerts spam every loop tick.
  - **Solution:** Read and update `last_alert_at` inside the same persisted state transaction.
- **Issue:** process restart clears pause state.
  - **Solution:** Load circuit state from PostgreSQL before polling S3.
- **Issue:** `/x-resume` bypasses investigation context.
  - **Solution:** Include last error class and failure count in the command response.

#### 9. Notes

- Circuit breaker protects Faiz from invisible repeated automation failures.
- The breaker should treat any final failure class as eligible for the consecutive failure count.
- Do not count dry-run failures toward the live posting circuit.
- Keep operational state small and explicit.
- This is a post-launch reliability control as well as launch readiness protection.
