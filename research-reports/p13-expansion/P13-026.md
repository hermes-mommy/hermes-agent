**Type:** Infrastructure / Monitoring
**Status:** Not Started
**Risk:** Medium

**Goal:** Register eight Prometheus metrics for the X Auto Poster pipeline, build a dedicated Grafana dashboard panel section, and implement per-post PostgreSQL logging with 90-day retention.
**Dependencies:** P13-001 S3 Queue Setup, P13-005 Queue Polling Loop, P13-011 Caption Generator, P13-012 Content Moderation, P13-016 Post Action, P13-018 Retry Engine, P13-019 Circuit Breaker, P8 Observability infrastructure (Prometheus, Grafana, PostgreSQL).

#### 1. Context

The X Auto Poster requires full observability so Faiz can monitor pipeline health at a glance. Eight Prometheus metrics cover total attempts, successes, failures by reason, queue depth per state, session health, heartbeat lag, caption generation count, and content blocks. A Grafana dashboard panel groups these into a single operational view.

Beyond metrics, per-post logging in PostgreSQL provides an auditable trail of every post attempt with latency, status, error reason, and session age. This supports the daily summary (P13-027), retrospective analysis, and post-launch troubleshooting.

Log retention is 90 days — consistent with P7 surveillance data policy. After 90 days, logs are archived or deleted. The retention policy must be enforced by the logging layer, not manually.

#### 4. Implementation Requirements

**Prometheus Metrics:**

- Register `p13_posts_total` as a Counter — incremented on every post attempt start.
- Register `p13_posts_success` as a Counter — incremented on confirmed success.
- Register `p13_posts_failed_total` as a Counter with `reason` label — incremented per failure with reason string.
- Register `p13_queue_depth` as a Gauge with `state` label — set to current count per queue state (pending, processing, posted_today, failed_today, held).
- Register `p13_session_expired` as a Gauge — set to 1 if session is expired, 0 if healthy.
- Register `p13_heartbeat_lag_seconds` as a Histogram — records seconds since last successful post. Buckets: [60, 300, 600, 1800, 3600, 7200, 14400, 28800, 43200, 86400].
- Register `p13_caption_generated_total` as a Counter — incremented on each LLM caption generation.
- Register `p13_content_blocked_total` as a Counter — incremented when moderation blocks a post.
- Prefix all metric names consistently with `p13_`.
- Use the existing project Prometheus registry; do not create a separate HTTP server.

**Grafana Dashboard:**

- Add a "P13 X Auto Poster" panel section to the existing Grafana dashboard (or create a dedicated P13 dashboard if the existing one does not support sections).
- Include a queue depth time series (p13_queue_depth by state, stacked).
- Include a post success/fail rate panel (p13_posts_success vs p13_posts_failed_total, rate over 24h).
- Include a session status panel (p13_session_expired state — color-coded green/red).
- Include a heartbeat lag panel (p13_heartbeat_lag_seconds — current value and histograms).
- Include a caption generation panel (p13_caption_generated_total rate and p13_content_blocked_total rate).
- Set dashboard refresh to 30 seconds for operational use.
- Add panel descriptions for each metric so operators new to P13 can interpret the data.

**Per-Post PostgreSQL Logging:**

- Create a `p13_post_log` table with columns:
  - `id` (UUID, primary key)
  - `timestamp` (TIMESTAMPTZ, not null)
  - `image_key` (TEXT, not null — S3 object key)
  - `caption_length` (INTEGER, nullable)
  - `post_status` (TEXT, not null — success/failed/blocked)
  - `latency_ms` (INTEGER, nullable — total ms from processing start to outcome)
  - `session_age_hours` (REAL, nullable)
  - `error_reason` (TEXT, nullable)
  - `retry_count` (INTEGER, default 0)
- Create index on `timestamp` for time-range queries.
- Create index on `post_status` for status-based aggregation.
- Write a log row at the end of every post attempt (success, failed, or blocked).
- Use the existing PostgreSQL connection pool (P3 episode storage).
- Implement a periodic cleanup job that deletes rows older than 90 days.
- Run cleanup as a scheduled task once per day (aligned with P13-027 daily summary scheduling).
- Log cleanup metrics: `p13_log_cleanup_deleted_total` Counter with count of deleted rows.
- Handle edge case: logging insert failure does not crash the post pipeline.
- Handle edge case: cleanup job overlaps with new writes — use DELETE with timestamp filter and READ COMMITTED isolation.

#### 8. Troubleshooting

- **Issue:** p13_queue_depth gauge is slow because S3 list calls are expensive.
  - **Solution:** Cache queue depth counts for 30 seconds; the gauge does not need real-time accuracy.
- **Issue:** p13_session_expired gauge never resets to 0 after recovery.
  - **Solution:** Wire the session recovery flow (P13-010) to explicitly set the gauge to 0 on successful re-auth.
- **Issue:** p13_post_log insert blocks the post pipeline.
  - **Solution:** Use async insert or fire-and-forget with a write-ahead queue; never block post outcome on log write.
- **Issue:** Grafana panel shows no data because metric name prefix differs.
  - **Solution:** Standardize on `p13_` prefix across all metrics; verify naming in the provisioning file.
- **Issue:** log cleanup deletes too many rows in one transaction.
  - **Solution:** Batch deletions in chunks of 1000 rows with short sleeps between batches.
- **Issue:** histogram bucket range does not capture heartbeat lag spikes.
  - **Solution:** Review the max bucket (86400s = 24h) — add a larger bucket if gaps beyond 24h occur.

#### 9. Notes

- Metrics cover the full pipeline: attempts → outcomes → failure classification → system health.
- The log table is append-only for post attempts; do not UPDATE existing rows.
- Retention policy aligns with P7 (90 days). Do not change retention without updating P7 policy documents.
- Grafana dashboard panels should be usable from mobile view for post-launch operations.
- Metric naming uses `p13_` prefix for consistent discovery in Prometheus queries.
- Do not expose S3 credentials or raw cookie data through metrics labels.
- All timestamps in logs should be UTC; WIB conversion is done in display layers (daily summary, Grafana).
