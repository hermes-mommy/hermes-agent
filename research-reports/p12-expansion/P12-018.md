### Step P12-018: Real-Time Email Notifications

**Goal:** Push Discord notifications for important and classified emails using rich embeds with action buttons (Draft Reply, Mark Read, Ignore) and rate limiting.
**Dependencies:** P12-010 (Email Classification Engine — provides classification verdict and importance score for each incoming email)
**ADR References:** ADR-022 (Communication Channel Strategy — Discord as notification surface for email events)
**Estimated Time:** 3.5 hours

#### Context

Real-time email notifications bridge the gap between Gmail's inbox and Faiz's primary communication surface (Discord). When a new email arrives and passes through the classification engine (P12-010), the `EmailNotifier` evaluates whether the email warrants an immediate Discord notification. The trigger conditions are: importance score ≥ 5 (per §3.2 of requirements), OR classification is `CLIENT_WORK`, `FINANCIAL`, or `BILLING_INVOICE`. Emails that do not meet either condition are stored in the conversation log and memory but do not generate a Discord notification — they appear in the morning briefing (P12-019) instead.

The notification is posted as a rich Discord embed to the dedicated private email channel (created by P12-016 guild setup extension). The embed includes sender address, subject line, classification badge, importance score, label list, thread depth, and a sanitized body preview (first 300 characters after the full content sanitization pipeline). Three action buttons use Discord's Button component API: "Draft Reply" triggers P12-015 draft generation, "Mark Read" calls Gmail API to mark the email as read, and "Ignore" dismisses the notification without further action.

Rate limiting prevents notification spam during high-volume email periods (e.g., conference announcements, Black Friday promotions that slip through classification). The limiter uses a sliding window: maximum 10 notifications per hour. Emails that exceed the rate limit are queued and included in the next available notification window or the morning briefing. The rate limit is configurable via environment variable `EMAIL_NOTIFICATION_RATE_LIMIT`.

The notification flow is asynchronous: the classification engine (P12-010) publishes a `email_classified` event to an internal event bus, and the `EmailNotifier` subscribes to this event. This decoupling ensures that notification failures (Discord API down, rate limit exceeded) do not block the email processing pipeline. Failed notifications are logged and included in the morning briefing.

All notifications go to the same private email channel used for draft approval (P12-016). This keeps all email-related Discord interactions in one place. The channel is private — only Faiz and the Guinevere bot role can view it.

Content sanitization is mandatory: the body preview in the notification embed has already passed through the full pipeline (HTML normalize → hidden CSS strip → injection scan → secret scan → PII scan) per §3.3 of requirements. No raw email content is displayed in Discord. If a secret or PII is detected, the body preview shows "[Content redacted — see Gmail directly]" and a separate Discord alert is posted to Faiz.

Quiet hours are configurable but default to disabled (no quiet hours). Faiz decides when to enable them via a Discord command or environment variable. When active, notifications during quiet hours are queued and delivered when quiet hours end.

#### Troubleshooting

- **Issue:** Discord Button interaction times out after 3 minutes (Discord default)
  - **Solution:** Set a custom timeout on the `discord.ui.View` that holds the buttons: `View(timeout=86400)` for 24 hours. When the view times out, the buttons become disabled and the embed footer updates to "⏰ Actions expired". Alternatively, use `View(timeout=None)` for persistent buttons, but handle stale email state (email may have been deleted from Gmail).

- **Issue:** Rate limiter allows more than 10 notifications in an hour
  - **Solution:** The sliding window implementation must use minute-granularity buckets (60 buckets per hour). Verify the Redis key format: `email_notify:rate:{YYYY-MM-DD-HH:MM}` with TTL 3600s. The check sums all non-expired buckets. Race conditions between concurrent notifications are handled via Redis `INCR` (atomic).

- **Issue:** "Draft Reply" button click does not trigger draft generation
  - **Solution:** The button callback must import and call `DraftGenerator.generate_draft()` from P12-015. Verify the import path and that the generator is initialized with valid Gmail service and LLM client. Add structured logging: `logger.info("Draft Reply button clicked", email_id=email_id, thread_id=thread_id)`.

- **Issue:** Body preview shows raw HTML tags or broken formatting
  - **Solution:** The body preview must be extracted from the already-sanitized content (post-pipeline output from P12-010). Do not use the raw email body. Use the `sanitized_body` field from the `EmailClassifiedEvent` payload. Truncate to 300 characters at a word boundary.

- **Issue:** Notifications stop appearing after Discord bot restart
  - **Solution:** The event bus subscription must be re-established on bot startup. Verify that `EmailNotifier` is instantiated and subscribed in the bot's `on_ready()` handler or startup sequence. Add a startup log: `logger.info("EmailNotifier subscribed to email_classified events")`.

#### Notes

- **Button vs Reaction:** Notifications use Discord Button components (interactive buttons below the embed), not reactions. This is different from draft approval (P12-016) which uses reactions. The distinction is intentional: notifications offer multiple distinct actions (Draft Reply, Mark Read, Ignore) that are clearer as labeled buttons than emoji reactions.
- **No Auto-Draft:** The "Draft Reply" button does not auto-generate a draft. It triggers the P12-015 draft generation flow which produces a draft and posts it as a new approval embed (P12-016). Faiz still needs to approve the draft before sending.
- **Notification Priority:** `CLIENT_WORK` and `FINANCIAL` emails are considered high-priority notifications. If rate limiting is active, these classifications are prioritized over `IMPORTANT` emails in the queue. Priority order: `CLIENT_WORK` > `FINANCIAL` > `BILLING_INVOICE` > `IMPORTANT` > others.
- **Mark Read Side Effect:** Clicking "Mark Read" updates Gmail but does NOT update the conversation log `delivery_status`. The conversation log `delivery_status` field is for sent emails (P12-017), not for read status. Read status is tracked via the `metadata_` JSON field: `"read": true, "read_at": "2026-06-03T08:15:00+07:00"`.
- **Quiet Hours Default:** Quiet hours are disabled by default (no quiet window). Faiz can enable them via environment variable `EMAIL_QUIET_HOURS=22:00-07:00` (WIB timezone). When the Guinevere service starts, it parses this variable and schedules a delivery task for the quiet window end time.
- **Cross-Reference P12-019:** Emails that are rate-limited or arrive during quiet hours are included in the morning briefing (P12-019). The morning briefing queries the conversation log for all emails in the time range, regardless of whether a notification was sent.
