### Step P12-010: Importance Scorer

**Type:** AI / Scoring Engine
**Status:** Not Started
**Risk:** Low-Medium
**Git Commit:** `feat(P12-010): pending`

**Goal:** Implement composite importance scoring with 8 weighted signals and threshold-based notification trigger (score ≥ 5 = notify Faiz immediately), using fixed weights for MVP with post-launch tunability via Discord.
**Dependencies:** P12-009 (Email Classifier provides category input for scoring)
**Cost Impact:** $0/month (all signals computed locally; no external API calls)

**Estimated Time:** 4 hours

#### Context

After classification (P12-009), every email receives an importance score that determines whether Faiz is notified immediately, included in the morning briefing, or silently archived. Faiz chose composite scoring with all 8 signals evaluated — not just the first match. This ensures a nuanced score that captures multiple importance dimensions.

The threshold is score ≥ 5 = notify Faiz immediately via Discord embed. This threshold was refined from an earlier "2+ signals" decision to a weighted sum approach that provides more granularity. A CLIENT_WORK email (+3 from classification) from a whitelisted sender (+2) scores exactly 5 and triggers notification. A NEWSLETTER with no other signals scores 0 and goes to the daily digest.

All 8 signal weights are fixed for MVP to keep the system predictable. Post-MVP, Faiz can tune weights via Discord commands (e.g., `!email-weight whitelist 3` to change whitelist weight from 2 to 3). Weight configuration is stored in Redis for runtime adjustment without code changes.

The scoring engine integrates with the classifier output: `CLIENT_WORK`, `FINANCIAL`, and `BILLING_INVOICE` classifications automatically add +3 to the score (equivalent to the Gmail Important label signal). This means classified-high-priority emails always score ≥ 3, needing only 2 more points from other signals to trigger notification.

Signal evaluation is fully composite — all 8 signals are checked independently and their weights summed. No signal is exclusive; multiple signals stack. The maximum theoretical score is 15 (all signals fire), but practical maximum is ~10-12.

The whitelist is Redis-backed for fast lookups and runtime management. Faiz can add/remove senders from the whitelist via Discord commands (`!email-whitelist-add sender@domain.com`).

#### Troubleshooting
- **Issue:** Score always 0 — no signals firing
  - **Solution:** Check that `UnifiedMessage` has the required metadata fields. `_check_important_label()` needs `metadata["labels"]` to contain Gmail label IDs. `_check_whitelisted_sender()` needs the whitelist Redis SET to be populated (use `!email-whitelist-add` command). Add debug logging for each signal evaluator.
- **Issue:** Thread depth always returns 0
  - **Solution:** `_check_thread_depth()` queries `EmailContextManager.get_thread_context()`. If the context manager hasn't stored any messages for the thread yet (first email in a new thread), depth is correctly 0. For subsequent emails, verify the Redis thread cache is populated.
- **Issue:** Financial amount regex misses valid amounts
  - **Solution:** The regex `Rp\s?\d{1,3}(?:[.,]\d{3})*(?:[.,]\d{2})?` handles: `Rp 1.500.000`, `Rp1500000`, `Rp 1,500,000.00`. It does NOT handle: `IDR 1500000` (add `IDR` as alternative prefix), `$100` (different currency — not in scope for MVP). Test with the financial extractor test suite.
- **Issue:** Whitelist domain match not working for subdomains
  - **Solution:** `is_whitelisted()` checks `@domain.com` suffix match. For `sub.domain.com`, add both `@domain.com` and `@sub.domain.com` to the whitelist. Alternatively, implement domain hierarchy matching (strip subdomains) if Faiz requests it post-launch.
- **Issue:** Scoring latency exceeds 100ms
  - **Solution:** The `_check_reply_rate()` signal queries PostgreSQL via `EmailContextManager`. If this query is slow, check the `idx_conversations_sender` index exists. Cache reply rates in Redis with a 1-hour TTL to avoid repeated DB queries.
- **Issue:** Discord notification not triggered despite score ≥ 5
  - **Solution:** `should_notify()` checks both score ≥ threshold AND classification category priority. Verify the Discord notification handler reads `ScoringResult.notify` correctly. Check that the Discord bot is connected and the email notification channel exists.

#### Notes
- The 8 signals are deliberately independent and composable. A financial email from a whitelisted sender with urgency keywords scores: financial_amount(3) + whitelisted_sender(2) + urgency_keywords(2) = 7. This composite approach captures importance more accurately than any single signal.
- Thread depth is capped at 3 replies (+3 max) to prevent runaway scores on very long threads. A 20-message thread doesn't score +20.
- The whitelist starts empty and grows as Faiz adds contacts. Seed it with known important senders during initial setup (bank notifications, client contacts, personal contacts).
- Post-MVP weight tuning via Discord is a planned feature. The `ScoringConfig` class already supports runtime weight changes from Redis. The Discord command handler (`!email-weight <signal> <value>`) will be implemented in a separate step.
- Classification category acts as a scoring multiplier in practice: `CLIENT_WORK`/`FINANCIAL`/`BILLING_INVOICE` emails already have high classification priority, and the scoring adds additional signals on top. These categories should almost always score ≥ 5 unless the email is clearly informational.
