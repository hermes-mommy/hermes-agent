**Goal:** Integrate Gmail processing with the cross-channel HARD STOP system, ensuring safe word detection in email content triggers a global halt, and HARD STOP from any channel (Discord, WhatsApp, email) stops all email processing immediately.

#### Context

The HARD STOP protocol is Guinevere's emergency safety mechanism. When triggered, all persona behavior stops, all processing halts, and the system enters a neutral state until Faiz explicitly resumes. P11 (WhatsApp) established the cross-channel HARD STOP pattern using a shared Redis flag (`guinevere:hard_stop`). This step extends that pattern to Gmail integration, making email the third channel in the cross-channel safety net.

Cross-channel HARD STOP operates in two directions:

**Inbound (email triggers HARD STOP):** When an incoming email contains the safe word after content sanitization (P12-007), the system triggers a global HARD STOP. This covers the edge case where someone sends Faiz an email containing the safe word — perhaps Faiz is away from Discord/WhatsApp and uses email as the emergency channel. The safe word detection runs on the email body AFTER sanitization strips HTML, tracking pixels, and known-safe content. False positives are mitigated by requiring an exact match of the full safe word phrase, not partial matches.

**Outbound (HARD STOP stops email):** When HARD STOP is triggered from any channel (Discord `HARD STOP` command, WhatsApp safe word, or email safe word), all email processing stops immediately. This means: sync engine stops polling, Pub/Sub StreamingPull stops acknowledging messages, draft generation cancels, notification delivery halts, and the morning briefing scheduler pauses. The email pipeline does NOT delete data or revoke consent — it simply stops processing until HARD STOP is cleared.

The `HardStopHandler` already exists as a channel-agnostic pure logic module (from P11). It reads and writes the shared Redis flag, manages the HARD STOP state machine, and provides hooks for channel-specific stop/start actions. This step integrates the email pipeline with the existing handler without modifying the handler's core logic.

Resume from HARD STOP is only possible via explicit Discord command by Faiz. No automatic resume, no timeout-based resume. This is a non-negotiable safety requirement per ADR-002.

#### Troubleshooting

- **Issue:** Safe word detected in legitimate email (false positive)
  - **Solution:** The safe word `HARD STOP` is a specific two-word phrase. False positives can occur in emails discussing system administration, emergency procedures, or technical documentation. Mitigation: require the safe word to appear as a standalone phrase (not part of a larger word), case-insensitive match after sanitization. If false positives persist, consider adding a minimum context window (e.g., safe word must appear in the first 500 characters of the body or in the subject line).
- **Issue:** HARD STOP does not stop email processing — sync continues running
  - **Solution:** Verify the `HardStopHandler` callback is registered correctly in `GmailHardStopIntegration.register()`. The sync engine checks `is_hard_stop_active()` at the start of each cycle. If the cycle is long-running (e.g., processing a batch of 50 emails), the check only fires between batches. For immediate stop, the HARD STOP callback must also cancel the current batch task.
- **Issue:** Pub/Sub messages pile up during HARD STOP — queue grows unbounded
  - **Solution:** Messages are NACK'd during HARD STOP, meaning they remain in the subscription queue. Pub/Sub message retention is 7 days (configured in P12-006). If HARD STOP lasts longer than 7 days, messages expire and are lost. For extended HARD STOP periods, switch to polling-only mode (which can be paused without accumulating queue messages).
- **Issue:** Email processing does not resume after HARD STOP cleared
  - **Solution:** The `on_hard_stop_cleared()` callback must re-initialize all stopped components: restart sync engine polling, re-establish Pub/Sub StreamingPull, renew watch if expired, and resume notification delivery. Check that each component's `_resume_email_processing()` call succeeds. If the watch expired during HARD STOP, `WatchManager.renew_watch()` must be called before resuming.
- **Issue:** HARD STOP from email also stops unrelated Guinevere functions
  - **Solution:** HARD STOP is intentionally global per ADR-002. When triggered, ALL persona behavior stops — not just email. This is by design. The `HardStopHandler` manages the global state, and all registered channels respond to it. The email integration only TRIGGERS the global halt; it does not define what stops. The PersonaSafetyPolicy defines the full HARD STOP behavior.
- **Issue:** Safe word check runs before sanitization — HTML entities cause missed detection
  - **Solution:** The safe word check MUST run after P12-007 sanitization. The sanitization pipeline strips HTML tags, decodes entities, removes tracking pixels, and normalizes whitespace. If the safe word appears as `HARD&nbsp;STOP` or `<b>HARD STOP</b>` in the raw email, sanitization converts it to plain `HARD STOP` before the safe word check runs.

#### Notes

- **HardStopHandler Reuse:** The `HardStopHandler` from P11 is channel-agnostic pure logic. It manages the Redis flag, state machine, and callback registry. This step does NOT modify the handler's core logic — it only registers email-specific stop/start callbacks and calls the handler's trigger method when safe word is detected.
- **Shared Redis Flag:** The `guinevere:hard_stop` Redis key is the single source of truth for cross-channel HARD STOP state. All channels (Discord, WhatsApp, email) read and write this same key. The value is a JSON object: `{"active": true, "source": "email", "timestamp": "2026-06-03T12:00:00Z", "triggered_by": "safe_word"}`.
- **Safe Word in Email — Edge Case:** The safe word in email is an emergency fallback for when Faiz cannot access Discord or WhatsApp. It assumes Faiz can send himself an email (or have someone send him one) containing the safe word. The email does not need to come from Faiz's address — any email containing the safe word triggers HARD STOP. This is intentional: in a distress scenario, anyone who knows the safe word can trigger it.
- **NACK vs ACK During HARD STOP:** NACK'd messages remain in the Pub/Sub subscription queue and are redelivered when the consumer reconnects. This is preferable to ACK-and-discard because no emails are lost during the HARD STOP period. The 7-day retention window provides ample buffer for typical HARD STOP durations.
- **No Automatic Resume:** HARD STOP never auto-clears. Even if the safe word was a false positive, Faiz must explicitly clear it via Discord. This prevents the system from resuming unsafe behavior without human verification. The Discord resume command is `!resume` or `HARD STOP off` (from P11).
- **Cross-Reference P12-007:** The Email Content Sanitizer (P12-007) runs before safe word detection. Sanitization quality directly affects false positive/negative rates for safe word detection.
- **Cross-Reference P12-021:** Consent revocation (`!email-consent-revoke`) is NOT the same as HARD STOP. Consent revoke is a graceful, email-specific shutdown. HARD STOP is an emergency, global halt. After HARD STOP clears, email processing resumes if consent is still active.
