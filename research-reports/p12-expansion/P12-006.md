#### Context

P12 requires near-real-time email ingestion. Faiz chose a hybrid architecture: Pub/Sub StreamingPull for urgent notifications combined with 5-minute polling fallback. This decision is critical because Gmail Pub/Sub notifications can be dropped (max 1 event/sec/user rate limit), and the watch expires every 7 days.

The Pub/Sub architecture uses **StreamingPull gRPC**, NOT HTTPS webhooks. This is an outbound connection from the VPS to Google Cloud — no exposed ports, no SSL certificates, no reverse proxy needed. The VPS initiates the gRPC stream and Google pushes messages down it. This eliminates the webhook complexity that would require nginx, Let's Encrypt, and firewall rules.

The sync flow: `users.watch()` registers a Pub/Sub topic for mailbox changes. When a new email arrives, Gmail publishes a notification to the topic. The StreamingPull client receives it, extracts the `historyId`, and calls `history.list(startHistoryId=stored_old_id)` to fetch all changes since the last known state. The counter-intuitive but correct behavior: use the OLD `historyId` as `startHistoryId`, not the new one from the notification.

Watch renewal is integrated into the main service (not a separate systemd timer). A daily `users.watch()` call refreshes the 7-day expiry. The polling fallback activates when no push notification has been received for 120 seconds, ensuring no emails are missed even if Pub/Sub drops events.

GCP project `guinevere-gmail-prod` is already created (P12-001) with billing enabled. The free tier covers single-user usage: 10GB messaging, 10GB storage, 200K publisher operations per month.

#### Troubleshooting
- **Issue:** `PERMISSION_DENIED` when calling `users.watch()` — topic IAM not configured
  - **Solution:** Verify `gmail-api-push@system.gserviceaccount.com` has `roles/pubsub.publisher` on the topic. Re-run the `add-iam-policy-binding` command. Wait 30-60 seconds for IAM propagation.
- **Issue:** StreamingPull connection drops frequently (every few minutes)
  - **Solution:** Check `ack_deadline` (set to 60s). Ensure messages are acknowledged within the deadline. Check network stability on VPS. The auto-reconnect with exponential backoff (1s, 2s, 4s, 8s, max 60s) handles transient drops.
- **Issue:** `history.list()` returns HTTP 404 — history unavailable
  - **Solution:** This happens when the stored `historyId` is too old (>1 week retention). Fall back to full sync via `messages.list()`, store the new `historyId`, and resume incremental sync.
- **Issue:** Watch expires before daily renewal runs
  - **Solution:** Daily renewal is scheduled every 24h but watch expires after 7 days. Add a check on service start: if `watch_expiry` is missing or past, immediately call `start_watch()`. Log a warning if renewal fails and alert via Discord.
- **Issue:** Polling fallback never triggers — emails missed during push silence
  - **Solution:** Verify `last_push_time` is updated correctly on every push receipt. The 120s threshold is configurable. If the VPS clock drifts, use `time.time()` not `datetime.now()` for comparison.
- **Issue:** `grpc` import fails or version conflict
  - **Solution:** Ensure `grpcio>=1.60` and `google-cloud-pubsub>=2.21` are installed. Pin `protobuf>=4.25` to avoid known conflicts. Run `uv pip install --upgrade grpcio google-cloud-pubsub`.

#### Notes
- StreamingPull is the correct choice for single-user VPS. HTTPS push webhooks would require exposing a port, configuring SSL, and managing certificates — unnecessary complexity for one mailbox.
- The `users.watch()` API costs 100 quota units per call. Daily renewal = 100 units/day, well within the 6,000 units/min per-user limit.
- `history.list()` costs only 2 quota units per call — the cheapest Gmail API method. Even with frequent polling, quota consumption is minimal.
- The 1 event/sec/user rate limit means rapid email bursts (e.g., 10 emails in 5 seconds) will produce only ~5 notifications. The polling fallback catches these missed events.
- Pub/Sub message retention is set to 7 days — if the service is down for up to a week, unacknowledged messages are still available when it comes back online.
- The encrypted service account key (`secrets/gmail-pubsub-reader-key.enc.json`) must be deployed to the VPS via SOPS decrypt at service start. Never commit the plaintext key.
