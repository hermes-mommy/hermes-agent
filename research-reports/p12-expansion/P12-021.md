### Step P12-021: !email-consent + !email-reauth Commands

**Type:** Application + Security
**Status:** Not Started
**Risk:** High
**Git Commit:** `feat(P12-021): pending`

**Goal:** Implement three Discord commands for email consent management (`!email-consent-grant`, `!email-consent-revoke`) and OAuth2 re-authentication (`!email-reauth`), enabling Faiz to control email processing lifecycle and recover from token expiry within 2 minutes.
**Dependencies:** P12-002 (OAuth2 Token Management — token refresh and storage infrastructure), P12-006 (Pub/Sub StreamingPull — watch must be cleared on consent revocation)
**Cost Impact:** $0/month (Redis consent flag negligible; OAuth re-auth uses existing token infrastructure)
**ADR References:** ADR-002 (Safe Word / HARD STOP — consent revocation is a softer form of processing halt), PersonaSafetyPolicy §4 (consent-aware processing), SurveillanceDataPolicy (email = surveillance data requiring explicit consent)
**Acceptance Criteria:** AC-EMAIL-009 (re-authentication flow < 2 minutes), AC-EMAIL-003 (consent management — grant/revoke), AC-EMAIL-008 (HARD STOP cross-channel — consent revoke stops processing)
**Estimated Time:** 5 hours

#### Context

Email processing in Guinevere is classified as surveillance under the SurveillanceDataPolicy because it involves reading Faiz's personal communications. This classification mandates explicit opt-in consent before any email data is processed, stored, or analyzed. The consent model is stored in Redis (`guinevere:consent:email`) and must be checked by every email pipeline component before processing begins.

Three commands implement the full consent and authentication lifecycle:

**`!email-consent-grant`** activates email processing. It sets the Redis consent flag to `true`, logs the consent event to the audit trail with timestamp and source, and triggers the email processing pipeline to start (Pub/Sub watch, polling, classification). The confirmation embed shows consent details: what data is collected, retention periods, and how to revoke.

**`!email-consent-revoke`** deactivates email processing immediately. It clears the Redis consent flag, stops the active Pub/Sub watch, halts any in-progress draft generation, and purges the polling scheduler. Existing classified data in the `conversations` table is retained per the data retention policy (not deleted on revoke — deletion requires a separate `!data-purge` command per SurveillanceDataPolicy). The confirmation embed confirms all processing has stopped.

**`!email-reauth`** handles OAuth2 token recovery when the refresh token expires or is revoked by Google. It generates a fresh OAuth2 authorization URL, presents it in a Discord embed with a clickable link, and waits for the callback. Faiz opens the link on his laptop, grants access, and the webhook receives the new token. The token is SOPS-encrypted and stored, and the service resumes automatically. AC-EMAIL-009 mandates this entire flow completes in under 2 minutes.

All three commands are Faiz-only (whitelist check) and every invocation is logged to the audit trail for compliance with the SurveillanceDataPolicy consent logging requirement.

#### Troubleshooting

- **Issue:** `!email-reauth` generates auth URL but callback never arrives
  - **Solution:** Verify the OAuth2 callback URL is registered in the GCP console (P12-002). The callback endpoint must be reachable from the browser. If using a local callback server, ensure it binds to the correct port. Check that the `state` parameter matches between the auth request and callback to prevent CSRF.
- **Issue:** Consent grant succeeds but email processing does not start
  - **Solution:** The `_start_email_pipeline()` method must initialize the Pub/Sub watch (P12-006) and start the sync engine polling (P12-005). Check that `WatchManager.start_watch()` and `SyncEngine.start()` are called. Verify Pub/Sub credentials are available and the watch topic exists.
- **Issue:** Consent revoke does not stop in-progress draft generation
  - **Solution:** Draft generation runs as an async task. The revoke handler must cancel pending draft tasks via `task.cancel()`. Check that the draft generator checks `ConsentChecker.is_consent_active()` before each API call, not just at the start of the batch.
- **Issue:** OAuth token refresh fails during `!email-reauth` — invalid_grant error
  - **Solution:** Google revokes refresh tokens when the user changes their password, revokes access from account settings, or when the token has not been used for 6 months. The re-auth flow generates a completely new authorization code, which replaces the old refresh token. Ensure the old token is deleted before storing the new one.
- **Issue:** Consent checker returns stale data — pipeline continues after revoke
  - **Solution:** The `ConsentChecker` caches consent state for 60 seconds to reduce Redis load. After revoke, the cache must be invalidated immediately. Add a Redis pub/sub notification: on revoke, publish to `guinevere:consent:invalidate` channel, and the `ConsentChecker` subscribes to clear its cache.
- **Issue:** Audit trail write fails silently — consent events not logged
  - **Solution:** Audit trail writes must be synchronous (blocking) within the command handler, not fire-and-forget. If the audit write fails, the command must refuse to proceed and alert Faiz: "⚠️ Cannot log consent event. Audit trail unavailable. Contact system admin."

#### Notes

- **SurveillanceDataPolicy Compliance:** Email is classified as surveillance data because it involves Faiz's personal communications. The SurveillanceDataPolicy requires explicit consent before collection, processing, or storage. The consent commands implement this requirement directly. Consent state is stored in Redis for fast checking, with audit trail as the authoritative log.
- **Consent Revocation vs HARD STOP:** Consent revocation (`!email-consent-revoke`) is a planned, graceful shutdown of email processing. HARD STOP (`guinevere:hard_stop`) is an emergency halt that overrides everything. Both stop email processing, but HARD STOP also stops all other channels and persona behavior. Consent revoke is email-specific; HARD STOP is global.
- **OAuth Testing Mode:** Per Faiz's decision, the OAuth consent screen uses Testing mode (not Published). Testing mode tokens expire every 7 days, requiring periodic re-authentication via `!email-reauth`. This is acceptable for single-user usage and avoids the Google verification process.
- **Re-authentication Timeout:** The 120-second timeout for `!email-reauth` is generous for the expected flow (click link → grant → callback takes ~30 seconds). The timeout prevents the command from hanging indefinitely if Faiz closes the browser or the callback fails.
- **Data Retention on Revoke:** Revoking consent stops processing but does NOT delete existing data. The SurveillanceDataPolicy specifies retention periods (90 days for Confidential, 30 days for Restricted). Deletion requires a separate `!data-purge` command. This is intentional — consent revocation is about stopping collection, not erasing history.
- **Cross-Reference P12-020:** The `!email-digest` command checks consent state before returning results. If consent is revoked, digest returns a "processing paused" message.
- **Cross-Reference P12-022:** HARD STOP from any channel also revokes email processing implicitly, but does not change the consent flag. After HARD STOP is cleared, email processing resumes if consent was still active.
