**Goal:** Implement automated Gmail watch renewal (daily `users.watch()` call) and a 60-second health check loop monitoring OAuth token validity, Gmail API connectivity, Pub/Sub StreamingPull status, Redis/PostgreSQL availability, with auto-refresh and Discord alerts on failure.

**Estimated Time:** 5 hours

#### Context

Gmail integration has several time-sensitive components that require continuous monitoring and proactive maintenance:

**Watch Renewal:** The Gmail `users.watch()` API registers a Pub/Sub notification channel with a 7-day expiry. If the watch expires, no push notifications arrive and the system falls back to polling-only mode (which has higher latency and API quota usage). To prevent expiry, the watch is renewed daily — well within the 7-day window. Faiz decided to integrate watch renewal into the main service (not a separate systemd timer or cron job). The renewal runs as an asyncio task within the main event loop, renewing when the stored expiry timestamp indicates less than 24 hours remaining.

**OAuth Token Health:** OAuth2 tokens have a finite lifetime. Refresh tokens in Testing mode expire every 7 days (Google's Testing mode limitation). The health check monitors token age and triggers auto-refresh when less than 1 hour remains. If auto-refresh fails (e.g., Google revoked the refresh token), a Discord alert prompts Faiz to run `!email-reauth` (P12-021). A Prometheus metric `gmail_oauth_token_age_seconds` alerts when the token exceeds 50 days (approaching the 7-day Testing mode limit is detected separately).

**Service Health Check (60s interval):** A continuous health check loop verifies all components of the email pipeline are operational:
- **OAuth token validity:** Check token expiry timestamp, trigger refresh if < 1h remaining
- **Gmail API connectivity:** Lightweight `users.getProfile()` call (1 quota unit) to verify API access
- **Pub/Sub StreamingPull connection:** Verify the gRPC stream is active and receiving keepalive messages
- **Redis connectivity:** Verify the consent flag (`guinevere:consent:email`) is readable
- **PostgreSQL connectivity:** Verify the `conversations` table is writable (test INSERT/DELETE)

On any component failure, the health check logs the failure, increments a Prometheus counter, and sends a Discord alert if the failure persists for more than 3 consecutive checks (3 minutes). This prevents alert spam from transient network blips.

The health endpoint `/health` provides a machine-readable status for the systemd watchdog and external monitoring tools. It returns JSON with per-component status and an overall `healthy` boolean.

#### Troubleshooting

- **Issue:** Health check consumes too many Gmail API quota units
  - **Solution:** The `users.getProfile()` call costs only 1 quota unit. At 60-second intervals, this is 1,440 calls/day — negligible against the 6,000 units/min per-user limit. If quota is a concern, increase the API connectivity check interval to 300 seconds (5 minutes) while keeping the other checks at 60 seconds.
- **Issue:** `/health` endpoint returns 503 even though service appears operational
  - **Solution:** A single unhealthy component causes the overall status to be `unhealthy`. Check which component is failing: `curl localhost:PORT/health | python -m json.tool`. Common causes: Redis connection pool exhausted (increase pool size), PostgreSQL connection timeout (check `max_connections`), Pub/Sub stream dropped (auto-reconnect should handle this within 60s).
- **Issue:** Watch renewal runs too frequently — multiple renewals per day
  - **Solution:** The renewal service checks `guinevere:gmail:watch_expiry` in Redis. If the expiry timestamp is not being written correctly after renewal, the service thinks the watch is always about to expire. Verify the `WatchManager.renew_watch()` method returns the new expiry timestamp and that it is stored in Redis: `redis-cli GET guinevere:gmail:watch_expiry`.
- **Issue:** OAuth auto-refresh creates a refresh loop — token keeps refreshing
  - **Solution:** Auto-refresh should only trigger when token expiry is < 1 hour. If the token expiry timestamp is not being updated after refresh, the system thinks the token is always about to expire. Verify `OAuthTokenManager.refresh_token()` updates the stored expiry: `redis-cli GET guinevere:gmail:token_expiry`. Also check for clock skew between the VPS and Google's servers.
- **Issue:** Discord alert spam — health check sends too many alerts
  - **Solution:** Alerts fire after 3 consecutive failures (3 minutes) per component. To prevent repeated alerts, implement alert deduplication: only send a new alert if the previous alert for the same component was more than 30 minutes ago. Store last alert timestamp in Redis: `guinevere:gmail:health:last_alert:{component}`.
- **Issue:** Systemd watchdog kills service — WATCHDOG_USEC timeout exceeded
  - **Solution:** The systemd `WatchdogSec` value must be greater than 2x the watchdog notification interval. If notifications are sent every 30s, set `WatchdogSec=90` in the systemd unit file. The `WatchdogNotifier` checks `sd_notify` availability and no-ops gracefully when not running under systemd (development mode).
- **Issue:** Health check blocks the event loop during database connectivity test
  - **Solution:** All health check operations must be async and use timeouts. The PostgreSQL connectivity test uses an async connection from the pool with a 5-second timeout. The test INSERT/DELETE uses a transaction that is rolled back, not committed, to avoid data pollution: `BEGIN; INSERT INTO conversations (...) VALUES (...) RETURNING id; DELETE FROM conversations WHERE id = $1; COMMIT;`.

#### Notes

- **Integrated Architecture:** Per Faiz's decision, watch renewal and health monitoring are integrated into the main service process, not separate systemd timers or sidecar containers. This simplifies deployment (one service unit) and ensures the health monitor has direct access to all pipeline components. The trade-off is that health monitoring stops if the main service crashes — but in that case, systemd restarts the entire service.
- **60-Second Health Interval:** The 60-second interval balances responsiveness with resource usage. Each cycle makes 5 checks: OAuth (Redis read), Gmail API (1 quota unit), Pub/Sub (in-memory check), Redis (1 read), PostgreSQL (1 transaction). Total per-cycle cost: ~1 API quota unit + 2 Redis operations + 1 DB transaction. At 1,440 cycles/day, this is well within all rate limits.
- **Alert Threshold — 3 Consecutive Failures:** Transient failures (network blip, Redis momentary unavailability) are common on VPS infrastructure. Requiring 3 consecutive failures (3 minutes) before alerting prevents noise while still detecting real issues within a reasonable timeframe.
- **Polling Fallback on Watch Failure:** When watch renewal persistently fails (3 retries exhausted), the system degrades gracefully to polling-only mode. Polling has higher latency (5-minute intervals vs real-time push) and higher API usage, but ensures no emails are missed. The Discord alert informs Faiz of the degraded mode.
- **Token Age Metric:** The `gmail_oauth_token_age_seconds` gauge provides early warning for Testing mode token expiry (7 days = 604,800 seconds). The alert threshold of 50 days (4,320,000 seconds) is for Published mode tokens; for Testing mode, a separate alert at 5 days (432,000 seconds) should be configured in Grafana.
- **Cross-Reference P12-006:** The `WatchManager` from P12-006 handles the actual `users.watch()` API call. This step (P12-024) adds the scheduling, retry, and alerting layer on top of it.
- **Cross-Reference P12-002:** The `OAuthTokenManager` from P12-002 handles token refresh. This step (P12-024) adds the proactive refresh trigger (< 1h remaining) and failure alerting.
- **Cross-Reference P12-021:** When OAuth refresh fails and `!email-reauth` is needed, the Discord alert directs Faiz to run the re-authentication command from P12-021.
- **Cross-Reference P12-022:** Health monitoring respects HARD STOP state. When HARD STOP is active, the health check still runs (infrastructure monitoring continues) but suppresses Discord alerts for email-specific components to avoid noise during intentional processing halts.
