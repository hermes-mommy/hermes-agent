#### Context

P12-026 packages the Gmail integration as a production systemd service. Faiz decided on a **separate systemd unit** (`guinevere-gmail.service`) rather than integrating into `guinevere-api.service`. This isolation ensures that Gmail-specific failures (OAuth token expiry, Pub/Sub disconnection, API quota exhaustion, memory spikes from large email processing) do not cascade to Discord, WhatsApp, or other subsystems.

The service runs under `guinevere.slice`, which has an 8G total memory budget. Current slice usage is 6.75G (guinevere-api ~4G, guinevere-whatsapp ~1.5G, PostgreSQL ~768M, Redis ~512M). Adding `MemoryMax=512M` for Gmail brings the total to 7.25G, leaving 750M headroom within the slice. If the Gmail service exceeds 512M, systemd invokes the OOM killer on the Gmail process only — other services are unaffected.

The systemd watchdog (`WatchdogSec=120`) complements the application-level health check. The Gmail service sends `sd_notify("WATCHDOG=1")` every 60 seconds via the `systemd` Python package. If systemd does not receive a watchdog ping within 120 seconds, it considers the service hung and restarts it. This catches deadlocks, infinite loops, and stalled event loops that do not crash the process but render it non-functional.

The operational runbook covers 7 scenarios specific to Gmail operations: service lifecycle (start/stop/restart), OAuth re-authentication via Discord, watch renewal troubleshooting, Pub/Sub connection recovery, quota exceeded handling, memory limit troubleshooting, and service health verification. Each procedure provides exact commands with expected output.

#### Systemd Unit File Example

```ini
# /etc/systemd/system/guinevere-gmail.service
# Guinevere Gmail Integration — separate unit per ADR-014
# Isolation: Gmail failures do not affect API, Discord, WhatsApp, or other subsystems

[Unit]
Description=Guinevere Gmail Integration Service
Documentation=https://github.com/faiz/guinevere
After=guinevere-core.service postgresql.service redis.service
Wants=network-online.target
PartOf=guinevere.slice

[Service]
Type=simple
User=guinevere
Group=guinevere
WorkingDirectory=/opt/guinevere

# Environment: load SOPS-decrypted secrets
EnvironmentFile=/opt/guinevere/.env.gmail
Environment=PYTHONUNBUFFERED=1
Environment=PYTHONDONTWRITEBYTECODE=1

# Entry point: Gmail service module
ExecStart=/opt/guinevere/.venv/bin/python -m src.gmail.main

# Slice integration: 512M budget within 8G guinevere.slice
Slice=guinevere.slice
MemoryMax=512M
MemoryHigh=448M

# Restart policy: restart on failure with 10s delay
Restart=on-failure
RestartSec=10
StartLimitBurst=3
StartLimitIntervalSec=60

# Watchdog: service sends sd_notify every 60s, systemd restarts if no ping in 120s
WatchdogSec=120
NotifyAccess=main

# Logging: stdout/stderr to journald
StandardOutput=journal
StandardError=journal
SyslogIdentifier=guinevere-gmail

# Resource limits
LimitNOFILE=65536
TimeoutStopSec=30

# Hardening (P10-004 pattern)
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
PrivateDevices=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
RestrictSUIDSGID=true
LockPersonality=true
RestrictRealtime=true
RestrictNamespaces=true
SystemCallArchitectures=native

# Read-write paths: Gmail data and credentials
ReadWritePaths=/opt/guinevere/data/gmail /opt/guinevere/logs

[Install]
WantedBy=multi-user.target
```

#### Runbook Content

The runbook file `runbooks/gmail-service.md` must cover these 7 operational procedures:

**Procedure 1: Service Start/Stop/Restart**
```
1. Start:     sudo systemctl start guinevere-gmail
2. Stop:      sudo systemctl stop guinevere-gmail
3. Restart:   sudo systemctl restart guinevere-gmail
4. Status:    sudo systemctl status guinevere-gmail
5. Logs:      sudo journalctl -u guinevere-gmail -f --no-pager
6. Verify:    curl -s http://localhost:9101/metrics | grep gmail_connected
```

**Procedure 2: OAuth Re-Authentication**
```
1. Discord alert fires or !email-status shows token expiring
2. Run re-auth command: !email-reauth (Discord)
3. Discord returns OAuth URL embed
4. Open URL on laptop → Google OAuth consent → grant
5. Token auto-stored and SOPS-encrypted
6. Verify: !email-status shows token age reset
7. Verify: redis-cli -p 6380 --user guinevere_core GET guinevere:gmail:oauth:token_age
```

**Procedure 3: Watch Renewal Troubleshooting**
```
1. Check watch status: !email-status or Prometheus gmail_watch_active
2. If watch_active == 0, check logs: sudo journalctl -u guinevere-gmail -n 30 | grep -i "watch"
3. Common causes:
   a. Pub/Sub topic deleted → recreate: gcloud pubsub topics create guinevere-gmail-notifications
   b. Pub/Sub subscription expired → recreate: gcloud pubsub subscriptions create guinevere-gmail-sub --topic=guinevere-gmail-notifications
   c. Gmail API watch() failed → check OAuth token validity first
4. Force watch renewal: !email-watch-renew (Discord command)
5. Verify: gmail_watch_active returns 1 in Prometheus within 60s
```

**Procedure 4: Pub/Sub Connection Recovery**
```
1. Check StreamingPull status: sudo journalctl -u guinevere-gmail -n 20 | grep -i "stream\|pubsub\|grpc"
2. If StreamingPull disconnected:
   a. Service auto-reconnects with exponential backoff (5s, 10s, 30s, 60s)
   b. Wait 2 minutes for auto-recovery
3. If auto-recovery fails after 4 attempts:
   a. Check GCP service account: gcloud iam service-accounts list | grep guinevere
   b. Check Pub/Sub subscription exists: gcloud pubsub subscriptions list | grep guinevere
   c. Verify network connectivity: curl -v https://pubsub.googleapis.com
4. Manual restart: sudo systemctl restart guinevere-gmail
5. Verify: StreamingPull connected log appears within 30s
```

**Procedure 5: Quota Exceeded Handling**
```
1. Discord alert fires: "Gmail API Quota > 80%"
2. Check current quota: !email-quota or Prometheus gmail_api_quota_usage
3. If quota > 90%:
   a. Temporarily reduce polling frequency: !email-config set poll_interval 600
   b. Disable historical backfill if running: !email-backfill stop
4. If quota exhausted (HTTP 429 errors in logs):
   a. Service auto-throttles with exponential backoff
   b. Wait for quota reset (daily at midnight Pacific)
5. Long-term: request quota increase via GCP Console → APIs → Gmail → Quotas
```

**Procedure 6: Memory Limit Troubleshooting**
```
1. Check if OOM killed: sudo journalctl -u guinevere-gmail -n 10 | grep -i "oom\|memory\|killed"
2. Check memory usage: systemctl show guinevere-gmail -p MemoryCurrent,MemoryMax
3. If OOM killed:
   a. Check for large email processing: sudo journalctl -u guinevere-gmail --since "1 hour ago" | grep -i "large\|size\|attachment"
   b. Check for memory leak: review memory usage trend in Grafana
   c. Temporary fix: increase MemoryMax to 768M in unit file, daemon-reload, restart
   d. Permanent fix: profile memory usage and optimize email processing pipeline
4. If MemoryHigh (448M) throttling causes latency:
   a. Check Gmail processing latency histogram in Grafana
   b. Consider increasing MemoryHigh if sustained high usage is normal
```

**Procedure 7: Service Health Verification**
```
1. Full health check: !email-status (Discord)
2. Systemd status: sudo systemctl status guinevere-gmail
3. Metrics endpoint: curl -s http://localhost:9101/metrics | grep "gmail_"
4. Watchdog ping age: systemctl show guinevere-gmail -p WatchdogUSec,WatchdogTimestamp
5. Slice usage: systemctl show guinevere.slice -p MemoryCurrent,MemoryMax
6. Connection state: redis-cli -p 6380 --user guinevere_core GET guinevere:gmail:connection:state
7. OAuth token age: redis-cli -p 6380 --user guinevere_core GET guinevere:gmail:oauth:token_age
8. All green = service healthy
```

"""Gmail integration service entry point — launched by systemd.

Initializes GmailClient, PubSubListener, EmailPipeline, and runs the event loop.
Sends sd_notify watchdog pings every 60 seconds.
"""
import asyncio
import signal
import sys
from systemd.daemon import notify

logger = structlog.get_logger()

class GmailService:
    def __init__(self) -> None: ...
    async def start(self) -> None: ...
    async def stop(self) -> None: ...
    async def _watchdog_loop(self) -> None:
        """Send WATCHDOG=1 to systemd every 60 seconds."""
        while True:
            await asyncio.sleep(60)
            notify("WATCHDOG=1")
            logger.debug("watchdog_ping_sent")
    async def _graceful_shutdown(self, signal_name: str) -> None: ...

async def main() -> None:
    notify("STATUS=Starting Gmail service...")
    service = GmailService()
    loop = asyncio.get_running_loop()
    for sig in (signal.SIGINT, signal.SIGTERM):
        loop.add_signal_handler(
            sig, lambda s=sig: asyncio.create_task(service._graceful_shutdown(s.name))
        )
    notify("READY=1")
    await service.start()

if __name__ == "__main__":
    asyncio.run(main())
DESIGN

#### Troubleshooting
- **Issue:** `systemctl start guinevere-gmail` fails immediately
  - **Solution:** Check journal: `sudo journalctl -u guinevere-gmail -n 50 --no-pager`. Common causes: (1) missing `.env.gmail` — decrypt from SOPS, (2) Python import error — test imports: `sudo -u guinevere /opt/guinevere/.venv/bin/python -c "from src.gmail.main import GmailService"`, (3) permission denied on data directory — verify ownership: `ls -la /opt/guinevere/data/gmail`.

- **Issue:** Watchdog kills service (status shows "Watchdog timeout")
  - **Solution:** The service is not sending `sd_notify("WATCHDOG=1")` pings. Verify `systemd-python` is installed: `uv pip show systemd-python`. Check if `_watchdog_loop` task is spawned in `GmailService.start()`. If the event loop is blocked (deadlock), the watchdog cannot fire — this is expected behavior. Check logs for what blocked the loop: `sudo journalctl -u guinevere-gmail --since "5 min ago"`.

- **Issue:** Service exceeds MemoryMax (512M) and gets OOM killed
  - **Solution:** Check memory usage pattern: `systemctl show guinevere-gmail -p MemoryCurrent,MemoryPeak`. If peak is just above 512M, increase to 768M temporarily. If memory grows unbounded, profile the email processing pipeline for leaks — common culprit: large email bodies held in memory during classification. Consider streaming processing for emails >100KB.

- **Issue:** `ProtectSystem=strict` causes "Read-only file system" errors
  - **Solution:** Add missing paths to `ReadWritePaths`. The service writes to: `/opt/guinevere/data/gmail` (email cache, sync state), `/opt/guinevere/logs` (log files). If OAuth token storage needs a write path, add it: `ReadWritePaths=/opt/guinevere/data/gmail /opt/guinevere/logs /opt/guinevere/.credentials`.

- **Issue:** Service starts but never connects to Gmail API
  - **Solution:** Verify OAuth credentials in environment: `sudo -u guinevere env | grep GMAIL_` (run from service context). Check if refresh token is valid: `sudo journalctl -u guinevere-gmail -n 20 | grep -i "oauth\|token\|auth"`. If token expired, run `!email-reauth` from Discord. Check network: `curl -v https://gmail.googleapis.com/discovery/v1/apis/gmail/v1/rest`.

- **Issue:** Slice budget exceeded after adding Gmail service
  - **Solution:** Check total slice usage: `systemctl show guinevere.slice -p MemoryCurrent,MemoryMax`. If `MemoryCurrent + 512M > 8G`, reduce other service budgets or increase slice total. Temporary: increase slice to 10G: `sudo systemctl set-property guinevere.slice MemoryMax=10G`.

#### Notes
- **Isolation Contract (ADR-014):** Gmail runs in its own process under `guinevere-gmail.service`. If the Gmail API client throws an unhandled exception or the Pub/Sub StreamingPull enters an unrecoverable state, only the Gmail service crashes. Discord, WhatsApp, memory recall, and all other subsystems continue operating.
- **Watchdog vs Application Health Check:** Two layers: (1) application-level — `GmailService` has internal health monitoring that checks Gmail API connectivity, OAuth token validity, and Pub/Sub stream status, reporting to Prometheus metrics. (2) systemd watchdog — catches process-level hangs where the event loop itself is blocked. The watchdog complements, not replaces, application health checks.
- **Slice Budget Tracking:** After this step, guinevere.slice usage is approximately 7.25G of 8G. Remaining headroom: 750M. Future phases must account for this budget. If a future phase needs more memory, the slice total can be increased with `systemctl set-property`, but Faiz must approve any increase.
- **sd_notify Protocol:** The service uses the `systemd` Python package (specifically `systemd.daemon.notify`) to communicate with systemd. Key notifications: `READY=1` (service started), `WATCHDOG=1` (keepalive ping), `STATUS=...` (human-readable status string), `STOPPING=1` (graceful shutdown initiated). If the `systemd` package is unavailable, watchdog functionality is silently disabled — the service still runs but systemd cannot detect hangs.
- **MemoryHigh vs MemoryMax:** `MemoryHigh=448M` is a soft limit — systemd throttles the service (reduces CPU allocation) when memory exceeds 448M, giving it a chance to reduce usage. `MemoryMax=512M` is a hard limit — exceeding it triggers OOM kill. This two-tier approach prevents sudden OOM kills for transient memory spikes while protecting against genuine memory leaks.
- **Cross-Reference P11-022:** The Gmail service unit follows the same pattern as the WhatsApp service unit (P11-022). Key differences: (1) no QR pairing required (OAuth instead), (2) different entry point module, (3) watchdog enabled (WhatsApp does not use sd_notify), (4) `MemoryDenyWriteExecute` not needed (pure Python, no CGo/FFI).
- **Environment File Security:** The `.env.gmail` file contains OAuth client credentials and refresh token. It must be SOPS-encrypted at rest (ADR-015). Plaintext file permissions: `0600` owned by `guinevere:guinevere`. The refresh token is the most sensitive value — it grants persistent access to Faiz's Gmail account.
- **Runbook Location:** The runbook lives in `runbooks/gmail-service.md` following project convention (see `runbooks/dr/` for disaster recovery runbooks, `runbooks/whatsapp-operations.md` for WhatsApp operations). All runbooks are version-controlled and accessible to agents during incident response.
