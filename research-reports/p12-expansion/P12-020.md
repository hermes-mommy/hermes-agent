### Step P12-020: !email-digest Command

**Type:** Application
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P12-020): pending`

**Goal:** Implement an on-demand Discord command `!email-digest` that generates a configurable email digest from the conversations table, outputting a paginated embed with stats, action-required, FYI, and filtered sections — identical to the morning briefing format.
**Dependencies:** P12-019 (Morning Briefing Scheduler — digest uses same formatting pipeline and classification data), P12-013 (Email Classifier — classification labels available for filtering), P12-008 (Channel Context Manager — conversations table populated)
**Cost Impact:** $0/month (Discord API rate limits only; no additional LLM calls for digest generation — uses pre-classified data)
**ADR References:** ADR-022 (Communication Channel Strategy — Discord as primary interface for email digests)
**Acceptance Criteria:** AC-EMAIL-010 (on-demand digest with configurable time range), AC-EMAIL-005 (email notifications via Discord embeds)
**Estimated Time:** 4 hours

#### Context

Faiz requested an on-demand `!email-digest` command complementing the automated morning briefing from P12-019. While the morning briefing fires at a scheduled time (default 07:00 WIB), the digest command lets Faiz pull a summary at any moment. The default time range is the last 12 hours, configurable via arguments: `!email-digest 24h`, `!email-digest 7d`, `!email-digest today`.

The command reuses the same formatting pipeline established by the morning briefing scheduler. Data is sourced from the `conversations` table (populated by P12-008 Channel Context Manager) joined with classification data from P12-013 Email Classifier. The output format is identical: stats summary, action-required section, FYI section, and filtered/spam section. This ensures Faiz gets a consistent reading experience whether the digest arrives on schedule or on demand.

The command follows the existing Discord bot pattern: 11 wired commands plus 22 stub commands using the `cmd_*.py` file convention in `src/discord/`. Text commands use the `!` prefix (not slash commands) to match the established interaction model. The command is Faiz-only via whitelist check and rate-limited to 5 requests per hour to prevent abuse and unnecessary database load.

Pagination is required because a 7-day digest could easily exceed 20 emails. When the result set exceeds 20 items, the command splits output into multiple Discord embeds, each with a page indicator (e.g., "📧 Email Digest — Page 2/3"). Discord embed limits (6000 characters total, 25 fields per embed) must be respected.

#### Troubleshooting

- **Issue:** `!email-digest` returns no results despite emails existing in the mailbox
  - **Solution:** Verify the `conversations` table has rows with `channel = 'email'` and timestamps within the requested range. Check that P12-008 sync is running and writing to the database. Run `SELECT COUNT(*) FROM conversations WHERE channel = 'email' AND created_at > NOW() - INTERVAL '12 hours'` to verify.
- **Issue:** Pagination produces empty pages or exceeds Discord embed limits
  - **Solution:** Each embed is limited to 6000 characters total and 25 fields. The pagination logic must count character length, not just email count. If a single email description is very long, truncate at 200 characters with "..." suffix. Test with emails containing long subject lines and body previews.
- **Issue:** Rate limiter blocks all requests immediately after deployment
  - **Solution:** The sliding window uses Redis sorted sets with timestamps. If Redis clock and application clock are misaligned, all entries may appear outside the window. Ensure both use UTC. Clear the rate limit key: `redis-cli DEL guinevere:ratelimit:email_digest`.
- **Issue:** Time range parsing fails for `today` or `yesterday`
  - **Solution:** Named ranges depend on timezone. The parser must use WIB (UTC+7) as the reference timezone. Verify `zoneinfo` is available (Python 3.12 standard library). If running on a VPS with UTC system time, explicitly set `ZoneInfo("Asia/Jakarta")` for all calculations.
- **Issue:** `MorningBriefingGenerator.generate_digest()` does not accept time range parameter
  - **Solution:** P12-019 must expose the digest generation with a configurable time range. If the current interface only supports the fixed morning window, refactor to accept `start_time` and `end_time` parameters. The `EmailDigestCommand` should call the same pipeline with custom bounds.
- **Issue:** Command conflicts with existing `!email` or similar prefix
  - **Solution:** The command dispatcher must match the longest prefix first. If `!email` exists, ensure `!email-digest` is checked before `!email` in the dispatch order, or use exact prefix matching with space delimiter: `!email-digest ` (trailing space).

#### Notes

- **Format Consistency:** The digest output MUST match the morning briefing format exactly. Faiz expects the same reading experience whether the digest arrives at 07:00 WIB on schedule or on demand at any time. Reuse `MorningBriefingGenerator` from P12-019 — do not duplicate formatting logic.
- **Rate Limiting Rationale:** 5 requests/hour prevents both accidental spam and unnecessary database load. Each digest query hits the `conversations` table with a time range filter. At 5 queries/hour, the load is negligible. The rate limit uses Redis sorted sets for accurate sliding window semantics.
- **Data Source:** The digest queries the `conversations` table (PostgreSQL), not the Gmail API directly. This means the digest reflects only emails that have already been synced and classified. If sync is delayed, the digest will show stale data. The stats section should include a "Last synced: [timestamp]" indicator.
- **Permission Model:** Same as all other Guinevere Discord commands — Faiz-only via `AUTHORIZED_USER_IDS` whitelist. The command does not expose email content to other Discord users even if they share a server.
- **Cross-Reference P12-019:** The morning briefing scheduler owns the `MorningBriefingGenerator` class. This step consumes it but does not modify it. If the generator needs refactoring to support arbitrary time ranges, that change belongs in P12-019.
- **Cross-Reference P12-021:** The digest is only useful when email consent is active (`guinevere:consent:email = true`). If consent is revoked, the command should return "📧 Email processing is paused. Use !email-consent-grant to resume."
- **Cross-Reference P12-022:** If HARD STOP is active (`guinevere:hard_stop = true`), the digest command must refuse to run and return "⛔ HARD STOP is active. All processing paused."
