### Step P12-028: Agent Loop Trigger Detector

**Type:** Feature
**Status:** Not Started
**Risk:** High
**Git Commit:** `feat(P12): pending`

**Goal:** Implement `LoopTriggerDetector` that identifies client emails with action keywords capable of triggering the P5 agent loop, notifies Faiz via Discord, and awaits reaction-based approval before creating a TaskContract.
**Dependencies:** P12-009 (Email classification engine — provides `CLIENT_WORK` classification), P12-018 (Discord notification bridge — provides embed + reaction handling)
**Cost Impact:** $0/month (uses existing Discord bot + LLM for keyword scoring)
**ADR References:** ADR-022 (Channel integration — Gmail as trigger source), ADR-015 (Agent loop — TaskContract creation and LoopManager integration)
**Acceptance Criteria:** AC-EMAIL-TRIGGER-001 (Client email with action keywords detected and notified to Discord within 10s), AC-EMAIL-TRIGGER-002 (Rate limiting enforced: max 3 loop trigger candidates per hour)
**Estimated Time:** 5 hours

#### Context

P12-028 bridges email intake to the agent loop system. When a client sends an email containing action keywords (e.g., "implement", "build", "deploy", "fix", "deadline"), the `LoopTriggerDetector` identifies this as a potential agent loop candidate and presents it to Faiz for approval via Discord. Faiz's reaction (✅ or ❌) determines whether a full TaskContract is created and the P5 SDLC loop begins.

Faiz decided that **all client emails can trigger** the agent loop, but **every trigger requires explicit Faiz approval** — no automatic loop starts. This is a consent-safety boundary: even if the detector is 100% confident, the loop does not start without Faiz's ✅ reaction. The standard TaskContract (P5 SDLC loop) is used, not a lightweight variant.

The detection logic is keyword-based + sender whitelist. The sender must be in the client whitelist (stored in Redis), the email must be classified as `CLIENT_WORK` by the classification engine (P12-009), and the email body must contain at least one action keyword from the configured keyword list. The keyword list includes both English and Indonesian terms to handle bilingual client communication.

Rate limiting prevents notification fatigue: maximum 3 loop trigger candidates per hour. If the limit is reached, subsequent candidates are logged but not notified until the rate window resets. Faiz can override the rate limit via `!email-trigger-override` Discord command for urgent situations.

```python
    3. Email body contains at least one action keyword

    ]

    RATE_LIMIT_WINDOW = 3600    # seconds
    
    async def check_trigger(self, email: EmailMessage, classification: str) -> TriggerResult | None:
        """Evaluate if email qualifies as a loop trigger candidate."""
        ...
    
    async def _score_confidence(self, email: EmailMessage, matched_keywords: list[str]) -> int:
        """Score trigger confidence 1-10 based on keyword count, urgency signals, thread depth."""
        ...
    
    async def _check_rate_limit(self) -> bool:
        """Return True if under rate limit (max 3 per hour)."""
        ...
    
    async def _notify_faiz(self, email: EmailMessage, result: TriggerResult) -> DiscordMessage:

        ...
```

**Confidence Scoring (1-10):**
- Base: 3 points for any keyword match
- +1 per additional keyword (max +3)
- +2 for date/deadline pattern match
- +1 for urgency keyword ("segera", "ASAP", "urgent")
- +1 for thread depth >2 (ongoing conversation)

Score ≥5 = "high confidence" notification. Score <5 = "low confidence" notification.

```
**Thread:** 3 messages in conversation

React ✅ to create TaskContract | ❌ to ignore
```

On ✅ reaction:
1. Log approval to Redis: `guinevere:gmail:trigger:approved:{email_id}`
2. Forward to `EmailTaskContractBuilder` (P12-029)
3. Send confirmation: "📋 TaskContract created for [Subject] — agent loop starting"

On ❌ reaction:
1. Log rejection to Redis: `guinevere:gmail:trigger:rejected:{email_id}`
2. Send confirmation: "❌ Trigger ignored for [Subject] — continuing normal processing"
3. Email continues through standard pipeline (notify, classify, store)

#### Troubleshooting
- **Issue:** Trigger detector never fires for legitimate client emails
  - **Solution:** Check all 3 conditions: (1) Sender in whitelist: `redis-cli -p 6380 --user guinevere_core SISMEMBER guinevere:gmail:client_whitelist client@company.com` — should return 1. (2) Classification is CLIENT_WORK: check pipeline logs for the email's classification result. (3) Keywords matched: check logs for `_extract_keywords` output. If keywords exist but aren't matched, verify body text is properly decoded from base64 before scanning.

- **Issue:** Rate limit fires too aggressively (blocks valid triggers)
  - **Solution:** Check current rate: `redis-cli -p 6380 --user guinevere_core KEYS "guinevere:gmail:trigger:rate:*"` and `GET` each key. If stuck, delete the rate key: `redis-cli -p 6380 --user guinevere_core DEL guinevere:gmail:trigger:rate:{current_hour}`. Consider increasing `RATE_LIMIT_MAX` to 5 if 3 is too restrictive for Faiz's workflow.

- **Issue:** Discord reaction handler does not process ✅
  - **Solution:** Verify the handler cog is loaded: `grep -rn "EmailTriggerReactionHandler\|add_cog.*trigger" src/discord/`. Check if the reaction event includes the correct message ID: `sudo journalctl -u guinevere-api -n 20 | grep -i "reaction\|trigger"`. Verify the message ID stored in Redis matches the Discord message: `redis-cli -p 6380 --user guinevere_core GET guinevere:gmail:trigger:pending:{email_id}`.

- **Issue:** Non-Faiz user can approve triggers by reacting
  - **Solution:** The `_is_faiz()` method must check `payload.user_id` against `FAIZ_USER_ID` from config. Verify: `grep -n "FAIZ_USER_ID\|is_faiz\|user_id" src/discord/handlers/email_trigger_reaction.py`. The handler must return early (no-op) for any user_id that is not Faiz.

- **Issue:** Confidence scoring is inaccurate (too high or too low)
  - **Solution:** Review the scoring weights in `_score_confidence()`. If scores are consistently too low, reduce `min_confidence_score` in `TriggerConfig`. If too high (false positives), increase keyword specificity — add more context requirements (e.g., keyword must appear in first 200 chars, or must be in sentence with client name).

- **Issue:** Pipeline blocks while waiting for Faiz's reaction
  - **Solution:** The reaction handling must be asynchronous — the pipeline should NOT block waiting for a reaction. After `_notify_faiz()`, the pipeline returns and continues processing other emails. The reaction is handled by the Discord bot's event loop, which calls `_handle_reaction()` when Faiz reacts. Verify the pipeline does not `await` the reaction.

#### Notes
- **Consent Boundary:** This is a consent-critical component. No agent loop starts without Faiz's explicit ✅ reaction. Even if the detector has 10/10 confidence, the loop waits for approval. This is non-negotiable per the consent-safety mandate. The approval is per-email, not batch — each trigger candidate gets its own notification and independent approval.
- **Keyword Localization:** The keyword list includes Indonesian terms because Faiz's clients may communicate in Bahasa Indonesia. Post-MVP, the keyword list should be configurable via Discord command (`!email-trigger-keywords add/remove`) and persisted in Redis for dynamic updates without code changes.
- **Rate Limiting Strategy:** 3 candidates per hour balances notification fatigue against responsiveness. If Faiz receives many client emails in a burst (e.g., Monday morning), only the first 3 trigger notifications. The rest are logged and can be reviewed via `!email-triggers` command. Post-MVP, this could be adjusted to a sliding window or priority-based system.
- **Integration with P12-029:** When Faiz reacts ✅, the handler forwards the email to `EmailTaskContractBuilder` (P12-029), which constructs the full TaskContract with email context and starts the P5 SDLC loop. P12-028 only detects and notifies — it does not build contracts or start loops.
- **Cross-Reference ADR-015:** The TaskContract created by this flow uses the standard P5 SDLC loop (7-phase pipeline). It is NOT a lightweight variant. The TaskContract includes email-specific context (thread history, client dossier, deadline extraction) that enriches the agent loop's starting prompt.
- **Cross-Reference P12-009:** The classification engine must return `CLIENT_WORK` for the trigger to evaluate. If classification is wrong (e.g., classifies a client email as `TRANSACTIONAL`), the trigger never fires. Post-MVP, the trigger could evaluate independently of classification as a secondary check.
- **Security Consideration:** The trigger detector processes email content that has already passed through the sanitization pipeline (P12-011). Injection patterns and secrets have been stripped. The keyword scan operates on sanitized content, not raw email body. This prevents injection payloads from being interpreted as action keywords.
