### Step P12-008: Channel Context Manager

**Type:** Data Layer / State Management
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P12-008): pending`

**Goal:** Implement email conversation thread tracking and channel state management, persisting conversation history to PostgreSQL with thread-aware metadata for draft generation and classification context.
**Dependencies:** P12-007 (GmailAdapter — provides UnifiedMessage with thread_id and metadata)
**Cost Impact:** $0/month (PostgreSQL already running; minimal storage for single-user)
**ADR References:** ADR-022 (channel strategy — 1 conversation = 1 Gmail thread)
**Acceptance Criteria:** AC-EMAIL-002 (emails classified within 5s — context lookup must be <50ms)
**Estimated Time:** 5 hours

#### Context

Guinevere needs to track email conversations as coherent threads, not isolated messages. Faiz decided: 1 conversation = 1 Gmail thread (identified by `thread_id`). This maps naturally to how Gmail groups related emails and provides the context window needed for intelligent draft replies.

The `EmailContextManager` maintains conversation state per thread, storing the last 3 messages per thread for draft generation context. This 3-message window balances context richness against LLM token costs — enough to understand the conversation flow without overwhelming the prompt.

Each email becomes one row in the PostgreSQL `conversations` table. The schema includes channel-specific metadata as a JSON column: subject, cc, labels, thread_id, delivery_status. The `delivery_status` field tracks the email lifecycle: `delivered` → `read` → `replied` or `draft_pending`. This enables the Discord UI to show accurate email state.

The context manager serves three consumers:
1. **Email Classifier (P12-009):** Provides sender history and thread context for classification decisions
2. **Importance Scorer (P12-010):** Provides reply rate per sender and thread depth for scoring signals
3. **Draft Pipeline:** Provides last 3 messages in thread for reply context generation

Thread continuity is maintained via `thread_id` linking. When a new email arrives with an existing `thread_id`, it's appended to the existing conversation. When a new `thread_id` appears, a new conversation row is created. This preserves the natural Gmail conversation grouping while enabling Guinevere to query conversation history efficiently.

class DeliveryStatus(str, Enum):
    DELIVERED = "delivered"      # Email received in inbox
    READ = "read"                # Faiz viewed (via Discord notification)
    REPLIED = "replied"          # Draft approved and sent
    DRAFT_PENDING = "draft_pending"  # Draft created, awaiting approval
    ARCHIVED = "archived"        # No action needed, archived

class DeliveryStatusTracker:
    """Tracks email delivery lifecycle.
    
    State machine: delivered → read → draft_pending → replied
                                         → archived (no reply needed)
    """
    VALID_TRANSITIONS: dict[DeliveryStatus, set[DeliveryStatus]] = {
        DeliveryStatus.DELIVERED: {DeliveryStatus.READ, DeliveryStatus.DRAFT_PENDING, DeliveryStatus.ARCHIVED},

        DeliveryStatus.DRAFT_PENDING: {DeliveryStatus.REPLIED, DeliveryStatus.ARCHIVED},

#### Troubleshooting
- **Issue:** `asyncpg.exceptions.UniqueViolationError` on duplicate message insert
  - **Solution:** The `UNIQUE(channel_type, message_id)` constraint is working correctly. Use `INSERT ... ON CONFLICT DO NOTHING` or check existence before insert. This prevents duplicate processing when Pub/Sub delivers the same notification twice.
- **Issue:** Redis thread cache stale — `get_thread_context()` returns old messages
  - **Solution:** Always invalidate Redis cache on `update_delivery_status()` calls. If cache appears stale, `DEL` the key and fall back to PostgreSQL query. Add a TTL of 1 hour to thread cache keys to prevent permanent staleness.
- **Issue:** GIN index on `metadata_->'thread_id'` not being used by query planner
  - **Solution:** Use the correct JSONB query syntax: `WHERE metadata_ @> '{"thread_id": "abc123"}'::jsonb`. Do not use `metadata_->>'thread_id' = 'abc123'` which won't use the GIN index. Alternatively, create a B-tree expression index on `(metadata_->>'thread_id')`.
- **Issue:** `DeliveryStatusTracker` rejects valid transition
  - **Solution:** Check the `VALID_TRANSITIONS` map. Common mistake: trying to go from `DELIVERED` directly to `REPLIED` without going through `DRAFT_PENDING`. The draft pipeline must set `draft_pending` before `replied`.
- **Issue:** Migration fails because `conversations` table already exists from P11
  - **Solution:** The migration uses `CREATE TABLE IF NOT EXISTS`. If the table exists from P11, the migration only adds Gmail-specific indexes. Review existing schema and adjust column types if needed.

#### Notes
- The `conversations` table may already exist from P11 WhatsApp implementation. This step adds Gmail-specific indexes and validates the schema is compatible. If P11 hasn't been implemented yet, this creates the table from scratch.
- `metadata_` column uses trailing underscore to avoid conflict with Python's `metadata` keyword conventions in some ORMs. The JSONB type allows flexible schema without migrations for each new metadata field.
- The 3-message thread context limit is a deliberate design choice. Gmail threads can be very long (dozens of messages). Loading all messages for draft context would be expensive and waste LLM tokens. 3 messages provide enough context for coherent replies in most cases.
- `content` column stores the LLM-generated summary, NOT the full email body. Full body is stored separately (encrypted) per SurveillanceDataPolicy. The summary is sufficient for conversation context and classification.
