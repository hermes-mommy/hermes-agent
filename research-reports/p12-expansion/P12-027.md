#### Context

P12-027 is the **phase gate test** for the entire Gmail integration. Individual step tests verify each component in isolation. P12-027 verifies that ALL components work together as a coherent system — emails flow from Gmail API through classification, sanitization, notification, draft generation, and approval; security defenses catch injection and secrets; HARD STOP propagates cross-channel; OAuth refresh operates transparently; scheduled and on-demand briefings generate correctly.

The test framework uses `pytest` + `pytest-asyncio` with two modes: (1) **CI mode** — mock Gmail API using `unittest.mock` and synthetic email fixtures, runs in any environment, (2) **Integration mode** — real Gmail API with test emails sent to Faiz's account, runs manually on VPS. The P12 GATE requires integration mode to pass. CI mode provides regression coverage.

Test data consists of synthetic emails covering all 8 categories: `CLIENT_WORK` (project request from known client), `FINANCIAL` (bank transaction notification), `BILLING_INVOICE` (invoice PDF), `IMPORTANT` (Gmail Important label + signals), `NEWSLETTER` (list-unsubscribe header), `PROMOTION` (marketing email), `TRANSACTIONAL` (order confirmation), `SPAM_PHISHING` (suspicious sender + injection payload). Each synthetic email has realistic headers, body content, and metadata.

The 10 test scenarios are ordered by dependency and cover the full user-facing behavior matrix: authentication (scenario 1), core pipeline (scenario 2), financial integration (scenario 3), full draft flow (scenario 4), security (scenarios 5-7), operational resilience (scenario 8), scheduled operations (scenarios 9-10). Each scenario has explicit setup, actions, assertions, expected timing, and cleanup. The test runner reports individual scenario results and an aggregate PASS/FAIL verdict. P12 GATE passes only when ALL 10 scenarios PASS.

#### Troubleshooting
- **Issue:** Scenario 2 fails — no Discord notification after email injection
  - **Solution:** Check email processing pipeline: `sudo journalctl -u guinevere-gmail -n 30 | grep -i "classify\|notify\|pipeline"`. Verify Discord email channel configured: `grep "DISCORD_EMAIL_CHANNEL" /opt/guinevere/.env`. Check if importance score meets threshold (≥5): inspect classification log for the injected email. If score <5, the synthetic email may need more importance signals (add Important label, whitelist sender).

- **Issue:** Scenario 4 fails — draft embed not appearing
  - **Solution:** Verify draft generation is wired: `grep -n "draft\|DraftGenerator" src/gmail/pipeline.py`. Check if the injected email triggers draft generation (needs classification = CLIENT_WORK and action-required detected). Check Gmail API draft creation: `sudo journalctl -u guinevere-gmail -n 20 | grep -i "draft"`. If Gmail API returns error, verify OAuth token has `gmail.modify` scope.

- **Issue:** Scenario 5 fails — injection not detected
  - **Solution:** Verify sanitization pipeline active: `grep -n "injection\|sanitize\|SanitizationPipeline" src/gmail/sanitizer.py`. Check injection regex patterns loaded: `sudo journalctl -u guinevere-gmail -n 10 | grep -i "injection\|pattern"`. The test email body must contain a pattern that matches one of the 50+ injection regexes. Verify the base64-decoded body contains the expected payload.

- **Issue:** Scenario 6 fails — HARD STOP not propagating cross-channel
  - **Solution:** The HARD STOP must be recognized from email channel, not just Discord/WhatsApp. Verify email message router forwards HARD STOP: `grep -n "HARD STOP\|hard_stop\|safe_word" src/gmail/message_router.py`. Check Redis shared flag: `redis-cli -p 6380 --user guinevere_core GET guinevere:safeword:active`. CLEANUP: reset persona after test.

- **Issue:** Scenario 8 fails — OAuth refresh causes processing interruption
  - **Solution:** The token refresh should be transparent. Check if the refresh is blocking the event loop: review `src/gmail/oauth.py` for synchronous HTTP calls during refresh. The refresh must be async (`aiohttp` or `httpx.AsyncClient`). If refresh takes >5s, the email polling may time out — ensure polling uses independent connection from the refresh flow.

- **Issue:** Scenario 9 fails — morning briefing not delivered at 8am WIB
  - **Solution:** Verify scheduler configured for 8am WIB: `grep -n "briefing\|schedule\|8:00\|WIB\|Asia/Jakarta" src/gmail/briefing.py`. Check timezone: server may be UTC, so 8am WIB = 1am UTC. Verify APScheduler or asyncio task is running: `sudo journalctl -u guinevere-gmail -n 20 | grep -i "briefing\|schedule"`. For testing, temporarily set schedule to 2 minutes from now.

- **Issue:** Full test run exceeds 10-minute timeout
  - **Solution:** Scenario 9 (morning briefing) has a 120s wait. Run it separately or adjust schedule for testing. Use `pytest-xdist` for parallel execution of independent scenarios (1-8 can run before 9-10). Increase `--timeout` flag to 900 if needed.
