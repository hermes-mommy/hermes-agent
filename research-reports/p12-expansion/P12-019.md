### Step P12-019: Morning Briefing + On-Demand Digest

**Goal:** Deliver a daily 8:00 AM WIB morning email briefing and an on-demand `!email-digest` Discord command with stats, action items, FYI, and filtered sections.
**Dependencies:** P12-018 (Real-Time Email Notifications — provides `EmailNotifier` infrastructure and email channel; classified emails stored in conversation log)
**ADR References:** ADR-022 (Communication Channel Strategy — Discord as briefing delivery surface)
**Estimated Time:** 3.5 hours

#### Context

The morning briefing is Guinevere's daily summary of email activity, delivered at 8:00 AM WIB (Asia/Jakarta, UTC+7) to the dedicated private email channel. It gives Faiz a quick overview of overnight email activity without requiring him to open Gmail. The briefing aggregates emails from the last 12 hours (covering the period since the previous evening) and organizes them into four sections: stats, action required, FYI, and filtered.

The on-demand `!email-digest` command provides the same format on demand, defaulting to the last 12 hours. Faiz can specify a different time range: `!email-digest 24h` for the last 24 hours, `!email-digest 6h` for the last 6 hours. The command queries the same data source (conversation log) and uses the same embed builder as the morning briefing.

Data source: the `conversations` table with `channel_type='gmail'` and `role='user'` (received emails). The query filters by time range and classification, grouping emails into the four briefing sections. The "Action Required" section includes emails classified as `CLIENT_WORK`, `FINANCIAL`, or `BILLING_INVOICE` that have no corresponding `role='assistant'` entry (i.e., no reply has been sent). The "FYI" section includes `IMPORTANT` and `TRANSACTIONAL` emails. The "Filtered" section counts `NEWSLETTER`, `PROMOTION`, and `SPAM_PHISHING` emails without listing them individually.

Scheduling uses APScheduler with a cron trigger: `CronTrigger(hour=8, minute=0, timezone="Asia/Jakarta")`. The scheduler runs within the `guinevere-gmail.service` systemd unit — no separate timer unit is needed. If the service is down at 8:00 AM, the briefing is delivered on the next service start (APScheduler `misfire_grace_time=3600` allows up to 1 hour of misfire tolerance).

The briefing embed follows the existing frozen dataclass pattern: `MorningBriefingEmbedData` holds all section data, `build_morning_briefing_embed_data()` constructs it from the database query results, and `to_discord_embed()` converts it to a `discord.Embed`. The embed uses Discord's field API to create visual sections with bold headers and bulleted items.

The `!email-digest` command is registered in the Discord bot's command handler, following the same pattern as existing commands (`!status`, `!cost`, `!budget`, etc.). It accepts an optional time range argument parsed with a simple regex: `(\d+)(h|d)` for hours or days. Invalid input returns a help message with usage examples.

Both the morning briefing and the on-demand digest are delivered to the same private email channel used by P12-016 (draft approval) and P12-018 (notifications). This keeps all email-related Discord activity in one channel.

#### Troubleshooting

- **Issue:** Morning briefing not delivered at 8:00 AM WIB
  - **Solution:** Verify APScheduler is running and the job is registered: `scheduler.get_job("morning_briefing")` should return a job object. Check the scheduler's timezone configuration: `CronTrigger(hour=8, minute=0, timezone="Asia/Jakarta")`. Verify system clock is synchronized: `timedatectl status` should show NTP synchronized. Check service logs for scheduler errors: `journalctl -u guinevere-gmail.service --since "today" | grep -i scheduler`.

- **Issue:** `!email-digest` command not recognized by Discord bot
  - **Solution:** Verify the command is registered in the bot's startup sequence. Check that `register_commands(bot)` is called in `src/discord/bot.py` or `startup.py`. Ensure the command name does not conflict with existing commands. Restart the Discord bot after adding the command.

- **Issue:** Briefing embed exceeds Discord's 6000 character limit on high-volume days
  - **Solution:** Implement truncation: limit Action Required to 10 items, FYI to 10 items, with "... and N more" suffix. If total embed still exceeds limit, truncate body previews to 100 characters instead of 200. The Filtered section already shows count only and does not contribute significantly to character count.

- **Issue:** Conversation log query returns no results even though emails were received
  - **Solution:** Verify that P12-010 is inserting emails into the conversation log with `channel_type='gmail'`. Check the time range: the morning briefing queries from `NOW() - INTERVAL '12 hours'` to `NOW()`. If the service was down for more than 12 hours, increase the query range or run `!email-digest 24h` manually.

- **Issue:** APScheduler fires the briefing job multiple times
  - **Solution:** Ensure `replace_existing=True` is set on `add_job()` to prevent duplicate job registration on service restart. Verify the job ID is unique: `id="morning_briefing"`. If using multiple workers, ensure only one instance of the scheduler is running (use Redis lock: `SET briefing:lock 1 EX 300 NX`).

- **Issue:** Timezone mismatch — briefing delivered at wrong time
  - **Solution:** Verify the system timezone is set correctly: `timedatectl` should show `Asia/Jakarta` or `UTC` with correct offset. APScheduler's `CronTrigger` uses the `timezone` parameter to interpret the cron schedule — it does not depend on system timezone. Ensure `timezone="Asia/Jakarta"` is explicitly set, not relying on system default.

#### Notes

- **No Weekly Summary:** Faiz explicitly decided against a weekly email summary. Only daily morning briefing and on-demand digest are implemented. If a weekly summary is desired post-launch, it can be added as an extension using the same `EmailBriefing` class with a `period_hours=168` parameter.
- **Data Source Consistency:** Both the morning briefing and `!email-digest` query the `conversations` table — they do not query Gmail API directly. This ensures consistency with the classification engine's output and avoids redundant API calls. The conversation log is the single source of truth for email activity after classification.
- **Action Required Logic:** An email is "action required" if: (1) classification is `CLIENT_WORK`, `FINANCIAL`, or `BILLING_INVOICE`, AND (2) no `role='assistant'` entry exists in the conversation log for the same `thread_id`. This means emails that already have a sent reply (via P12-017) are not shown in the Action Required section.
- **Embed Field Limits:** Discord allows up to 25 fields per embed. The briefing uses 4 main sections (Stats, Action Required, FYI, Filtered), each as a field. If Action Required or FYI items are listed individually, they should be combined into a single field value with line breaks, not separate fields.
- **APScheduler vs Systemd Timer:** APScheduler is chosen over systemd timer because it runs within the same process as the Gmail service, shares the same database connection pool, and has built-in misfire handling. A systemd timer would require a separate script invocation and connection setup. If APScheduler proves unreliable, a systemd timer with `OnCalendar=*-*-* 08:00:00 Asia/Jakarta` is the fallback.
- **Caching:** The morning briefing query result can be cached in Redis for 1 hour with key `briefing:{date}`. If Faiz runs `!email-digest 12h` at 8:30 AM, the cached morning briefing data can be reused (with a note that it covers a slightly different time window). This reduces database load for repeated queries.
- **Cross-Reference P12-018:** Emails that were not notified in real-time (due to rate limiting or quiet hours) appear in the morning briefing. The briefing does not check whether a notification was sent — it shows all emails in the time range regardless of notification status.
