### Step P12-017: Gmail Draft Sync + Send

**Goal:** Send Faiz-approved Gmail drafts via the Gmail API, update conversation log and Discord embed with sent status, and store the sent message in memory.
**Dependencies:** P12-016 (Discord Draft UX — provides approve reaction trigger and draft_id from Redis state)
**ADR References:** ADR-022 (Communication Channel Strategy — Gmail as email channel, Discord as control surface)
**Estimated Time:** 3 hours

#### Context

When Faiz reacts ✅ on a draft approval embed (P12-016), the `DraftSender` class takes over to execute the actual email send. This step implements the final mile of the draft reply pipeline: fetching the Gmail draft by its draft_id, calling `drafts.send()` to dispatch the email through Gmail's infrastructure, and updating all downstream state (conversation log, Discord embed, memory) to reflect the sent status.

The architecture follows a "save as draft first, send on approval" model. This means the Gmail draft already exists in Faiz's Gmail account (created by P12-015 `DraftGenerator`) and is editable from Gmail web if Faiz wants to make manual edits outside Discord. The `drafts.send()` call converts the draft into a sent message — Gmail handles all SMTP delivery, threading, and recipient delivery. No separate SMTP server or Resend API is needed for draft replies.

Error handling is critical because several failure modes exist between the approve reaction and successful delivery. The draft may have been deleted from Gmail (manually by Faiz or by a filter), the OAuth token may have expired (7-day refresh cycle), or the Gmail API may return a transient error. Each failure mode has a specific recovery path: deleted drafts trigger a Discord alert, expired OAuth triggers the `!email-reauth` flow, and API errors trigger a Discord alert with retry logic.

The conversation log update ensures Guinevere's memory system knows that a reply was sent. The entry uses `role='assistant'` to distinguish it from received emails (`role='user'`), and `delivery_status='sent'` to track delivery state. The memory store call uses `store_episode()` with `source="gmail"` and `role="assistant"` so that future memory recalls can find the sent reply in context.

Metrics track the approval/rejection ratio: `gmail_drafts_approved_total` increments on successful send, `gmail_drafts_rejected_total` increments when Faiz reacts ❌. These metrics feed into Grafana dashboards for operational visibility and help identify patterns in draft quality (high rejection rate may indicate the LLM needs prompt tuning).

The Discord embed is updated in-place after send: the title changes to include "✅ Sent", a timestamp field is added, and the reaction prompt footer is replaced with delivery confirmation. This gives Faiz immediate visual feedback without requiring a new message.

#### Troubleshooting

- **Issue:** `drafts.send()` returns HTTP 400 "Invalid draft" even though draft exists
  - **Solution:** The draft may have malformed headers (missing `To:` or `Subject:`). Verify the draft was created correctly by P12-015. Fetch the draft via `drafts.get()` and inspect the `message.raw` field. Ensure the `To` header is set and the MIME structure is valid.

- **Issue:** Conversation log INSERT fails with unique constraint violation on `content_hash`
  - **Solution:** The draft content may be identical to a previously stored email (e.g., a test email sent to self). Add `ON CONFLICT (content_hash) DO UPDATE SET delivery_status = 'sent', updated_at = NOW()` to the INSERT statement, or generate a unique hash that includes the draft_id.

- **Issue:** Discord embed update fails with "Unknown Message" error
  - **Solution:** The original draft embed message may have been deleted by Faiz or by the timeout cleanup task. Before calling `message.edit()`, fetch the message via `channel.fetch_message(message_id)` and handle `discord.NotFound` gracefully by logging the error and skipping the embed update.

- **Issue:** `store_episode()` fails silently — sent email not found in memory recall
  - **Solution:** Verify the memory store connection is active before calling `store_episode()`. Add structured logging: `logger.info("Storing sent email in memory", draft_id=draft_id, subject=subject)`. Check that the episode_type is `"email"` and source is `"gmail"` for correct recall filtering.

- **Issue:** OAuth token expires mid-send, causing a partially completed flow
  - **Solution:** The send flow should be treated as a transaction: if `drafts.send()` fails due to OAuth expiry, the conversation log and embed should NOT be updated. The error handler triggers `!email-reauth` and the approve reaction can be retried after re-authentication. No draft state is lost because the Gmail draft still exists.

#### Notes

- **Gmail Draft Send Semantics:** When `drafts.send()` is called, Gmail converts the draft into a sent message. The draft_id becomes invalid after send. The response includes the sent `message.id` which should be stored in the conversation log for future thread lookups. The sent message appears in the "Sent" label in Gmail web.
- **Thread Continuity:** Gmail automatically threads the sent reply with the original email based on the `In-Reply-To` and `References` headers (set by P12-015 during draft generation). No manual threading is needed. The `thread_id` from the original email is preserved in the sent message metadata.
- **No SMTP Fallback:** Draft replies always use `drafts.send()` through the Gmail API. There is no fallback to direct SMTP or Resend API for draft replies. Resend API (P12 step for transactional emails) is a separate pipeline for invoices and notifications, not for conversational replies.
- **Idempotency:** The send flow is idempotent via Redis lock: `SET draft:send:{draft_id} 1 EX 60 NX`. If the lock already exists (e.g., Faiz double-reacted ✅), the handler returns early without sending a duplicate email.
- **Metrics Granularity:** The `gmail_drafts_send_errors_total` counter has an `error_type` label with values: `draft_not_found`, `oauth_expired`, `rate_limited`, `server_error`, `unknown`. This allows Grafana dashboards to show error breakdown.
- **Cross-Reference P12-016:** The `handle_approve()` reaction handler in `draft_discord_ux.py` calls `DraftSender.send_approved_draft()`. The UX layer does not contain any send logic — all send operations are in `draft_sender.py`.
- **Cross-Reference P12-003:** The `!email-reauth` command (from P12-003 OAuth flow) is triggered programmatically when OAuth expiry is detected. The `DraftSender` posts a Discord message with the reauth URL embed rather than requiring Faiz to type the command manually.
