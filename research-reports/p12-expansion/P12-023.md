#### Context

All email data in Guinevere is classified as surveillance data under the SurveillanceDataPolicy because it involves reading Faiz's personal communications. The surveillance classification system uses a 5-tier model already established in Guinevere: Public, Internal, Confidential, Restricted, and Critical. Each tier has specific handling requirements, retention periods, and access controls.

The default classification for all email content is **Confidential**. This baseline reflects that personal email is inherently private but does not contain the most sensitive data categories. Auto-escalation rules elevate the classification to **Restricted** when specific content patterns are detected:

- **FINANCIAL or BILLING_INVOICE category** (from P12-013 Email Classifier) → Restricted
- **CLIENT_WORK category** (from P12-013) → Restricted
- **Financial amounts detected** (currency symbols + amounts, e.g., "$5,000", "Rp 50.000.000") → Restricted
- **Client PII detected** (names, addresses, phone numbers associated with client work) → Restricted

The **Critical** tier is reserved for system-level emergencies (HARD STOP events, security breaches) and is never assigned to email content automatically. The **Public** and **Internal** tiers are not applicable to personal email surveillance data.

Classification is applied at three points in the pipeline:
1. **Memory storage**: The `store_episode()` call includes the classification level, affecting retention and recall behavior.
2. **Conversation log metadata**: The `conversations` table row includes a `surveillance_classification` column for filtering and audit.
3. **Notification embeds**: Discord notification embeds show the classification level as a colored indicator (Confidential = blue, Restricted = red).

The SurveillanceDataPolicy mandates that retention periods vary by tier: Confidential data is retained for 90 days, Restricted data for 30 days. The classification system must integrate with the existing data retention scheduler to enforce these periods. All classification decisions are logged to the audit trail for compliance verification.

#### Troubleshooting

- **Issue:** Financial pattern detector produces false positives on normal email (e.g., "$5 coffee" in a newsletter)
  - **Solution:** Add a minimum threshold: financial amounts below $100 (or equivalent) should not trigger escalation. Alternatively, require the financial pattern to appear in conjunction with keywords like "invoice", "payment", "billing", "transfer". The current patterns are intentionally broad; tuning will be needed based on Faiz's actual email content.
- **Issue:** Classification column not found in `conversations` table
  - **Solution:** The migration (`P12_023_add_surveillance_classification.sql`) must be run before the application code references the column. Verify migration ran: `psql -d guinevere -c "\d conversations" | grep surveillance`. If using a migration tool (e.g., Alembic), ensure the migration is registered and applied.
- **Issue:** Client PII detection is too aggressive — flags names in personal emails
  - **Solution:** Client PII detection must be context-aware. A name like "John" in a personal email is not client PII. The detector should require co-occurrence of a name with client-work indicators (company name, project reference, "client", "contractor", "freelance"). The CLIENT_WORK category from P12-013 is the primary signal; PII detection is a secondary escalation for emails not already categorized as client work.
- **Issue:** Retention scheduler does not respect classification-based retention periods
  - **Solution:** The data retention scheduler must query conversations by `surveillance_classification` and `created_at`. Restricted data (30 days) is purged before Confidential data (90 days). Verify the scheduler uses the index `idx_conversations_surveillance_retention` for efficient queries.
- **Issue:** Classification decision audit trail grows unbounded
  - **Solution:** Audit trail entries for classification decisions follow the standard audit retention policy. If no policy exists, implement a 365-day retention for audit entries (configurable). Old audit entries are archived, not deleted, per the SurveillanceDataPolicy.
- **Issue:** `SurveillanceClassification` model does not serialize correctly for audit logging
  - **Solution:** Ensure the model has a `to_dict()` method that returns JSON-serializable data. The audit trail `log_event()` expects a dict payload. Include: `tier`, `base_tier`, `escalation_triggers`, `retention_days`, `email_id`, `timestamp`.

#### Notes

- **5-Tier Model:** Guinevere's classification system has 5 tiers, but only 2 apply to email: Confidential (default) and Restricted (escalated). Public and Internal are not applicable to personal surveillance data. Critical is reserved for system emergencies (HARD STOP, security breach). The `ClassificationTier` enum includes all 5 for completeness but the classifier only produces Confidential or Restricted.
- **Retention Periods:** Confidential = 90 days, Restricted = 30 days. These periods are defined in the ConsentRevocationPolicy and enforced by the data retention scheduler. The classification system provides the tier label; the scheduler enforces the deletion timeline.
- **Consent Dependency:** Classification only runs when consent is active (`guinevere:consent:email = true`). If consent is revoked, no new classifications are produced. Existing classified data remains until its retention period expires.
- **Audit Trail Volume:** Every email produces one classification decision log entry. At ~200 emails/day, this generates ~200 audit entries/day (~6,000/month). The audit trail must handle this volume without performance degradation. Batch writes or async logging may be needed if volume becomes an issue.
- **Financial Pattern Localization:** The financial detector supports USD ($), IDR (Rp), and EUR. Additional currencies can be added to the `FINANCIAL_PATTERNS` list. The patterns are regex-based for simplicity; if false positive rates are unacceptable, consider a lightweight NLP classifier for financial content detection.
- **Cross-Reference P12-013:** The Email Classifier (P12-013) provides category labels that drive escalation rules. This step (P12-023) applies surveillance classification ON TOP of the category classification. They are complementary: category = what the email is about, surveillance classification = how sensitive the data is.
- **Cross-Reference P12-021:** Consent state gates all classification processing. The `ConsentChecker` from P12-021 must be checked before the classifier runs.
- **Cross-Reference P12-022:** HARD STOP does not affect classification of already-received emails. Emails in the queue when HARD STOP triggers are not processed (and thus not classified) until HARD STOP clears and processing resumes.
