### Step P12-009: Email Classifier (Cascade Pattern)

**Type:** AI / Classification Engine
**Status:** Not Started
**Risk:** Medium-High
**Git Commit:** `feat(P12-009): pending`

**Goal:** Implement AI-powered email classification using a 4-tier cascade: hash cache → heuristic rules → embedding similarity → LLM fallback, achieving 95%+ accuracy while minimizing LLM cost.
**Dependencies:** P12-005 (SyncEngine provides incoming email flow)
**Cost Impact:** ~$0.50/month estimated (LLM fallback for ~5% of emails; heuristic/embedding tiers are free or near-free)
**ADR References:** ADR-023 (financial tracking — BILLING_INVOICE category links to P9 financial extraction)
**Acceptance Criteria:** AC-EMAIL-002 (emails classified within 5s), AC-EMAIL-006 (financial → P9 linked)
**Estimated Time:** 7 hours

#### Context

Every incoming email must be classified into one of 8 categories to drive routing, notification, and action decisions. Faiz chose a hybrid cascade approach based on production research: the UpGPT email-classifier achieves 78% accuracy with heuristics alone, and adding embedding similarity pushes to 85-90%. LLM classification handles the remaining ambiguous cases at ~95%+ accuracy.

The cascade pattern is essential for cost control. At 50 emails/day, classifying every email with an LLM would cost ~$1.50/month. With the cascade, only ~2-3 emails/day (5%) reach the LLM tier, reducing cost to ~$0.50/month. The hash cache tier is instant (deduplication), heuristic rules are <1ms, embedding similarity is ~100ms, and LLM classification is ~2s.

The 8 categories were confirmed by Faiz as sufficient:

| Category | Priority | Action |
|---|---|---|
| `CLIENT_WORK` | HIGH | Notify Faiz + generate draft |
| `FINANCIAL` | HIGH | Notify Faiz + link to P9 |
| `BILLING_INVOICE` | HIGH | Notify Faiz + P9 extract |
| `IMPORTANT` | MEDIUM | Notify Faiz |
| `NEWSLETTER` | LOW | Batch in daily digest |
| `PROMOTION` | LOW | Low priority, archive |
| `TRANSACTIONAL` | LOW | Classify + store |
| `SPAM_PHISHING` | BLOCK | Drop + alert Faiz |

Confidence threshold: first tier to produce confidence >0.85 wins. If no tier exceeds 0.85, the email is classified as `IMPORTANT` (safe default — better to over-notify than miss something). Classification results are stored in conversation `metadata_` for use by the Importance Scorer (P12-010).

Batch classification mode supports the historical backfill (P12 step for 30-day backfill) — classifying hundreds of emails efficiently with rate-limited LLM calls.

#### Troubleshooting
- **Issue:** Heuristic tier produces inconsistent results for same email
  - **Solution:** Ensure rules are deterministic: normalize sender email to lowercase, strip whitespace from subject/body before matching, use `re.IGNORECASE` for keyword matching. Log all matched signals for audit.
- **Issue:** Embedding tier never produces confidence >0.85
  - **Solution:** The exemplar set may be too small or not representative. Start with 5-10 exemplars per category. Use the `add_exemplar()` method to add misclassified emails as new exemplars (self-improving over time). Check embedding model is loaded correctly.
- **Issue:** LLM tier returns unparseable response
  - **Solution:** Use structured output (JSON mode) with the LLM. If the LLM doesn't support structured output, wrap the prompt with explicit JSON instructions and add retry with temperature=0. Log raw LLM response for debugging.
- **Issue:** Financial extractor misses Indonesian currency formats
  - **Solution:** Indonesian format uses `.` as thousands separator and `,` as decimal: `Rp 1.500.000,00`. The regex `Rp\s?\d{1,3}(?:[.,]\d{3})*(?:[.,]\d{2})?` handles both. Test with: `Rp 1.500.000`, `Rp1500000`, `Rp 1,500,000.00`.
- **Issue:** Batch classification hits LLM rate limits during backfill
  - **Solution:** `classify_batch()` uses `asyncio.Semaphore(5)` to limit concurrent LLM calls. If rate-limited (HTTP 429), the semaphore releases and the call retries with exponential backoff. For 1000-email backfill, expect ~50 emails to reach LLM tier, taking ~2 minutes total.
- **Issue:** `SPAM_PHISHING` false positives blocking legitimate emails
  - **Solution:** SPAM_PHISHING requires confidence >0.90 (higher threshold than other categories). If sender is in whitelist, skip SPAM check entirely. Log all BLOCK decisions with full signal list for Faiz review.

#### Notes
- The cascade order matters: hash cache first (cheapest, fastest), then heuristics (free, fast), then embedding (cheap, medium), then LLM (expensive, slow). Reversing the order wastes money.
- BILLING_INVOICE category has special handling: when classified, `FinancialExtractor` runs to extract amount and category. This data is stored in `metadata_["financial_data"]` for P9 to read later.
- The 8 categories are intentionally broad. Post-MVP, Faiz can request subcategories via Discord command, which would add a second-level classification after the primary category.
- Learned rules (Tier 1) are sender/domain → category mappings that are stored after high-confidence LLM classifications. If the LLM classifies an email from `accounting@company.com` as FINANCIAL with 0.98 confidence, a learned rule is created for that domain. Future emails from the same domain are classified instantly by the hash cache tier.
