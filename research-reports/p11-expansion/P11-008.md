### Step P11-008: Message Routing Pipeline — Intent → Agent/Command → Response

**Type:** Application
**Status:** Not Started
**Risk:** Critical
**Git Commit:** `feat(P11): pending`

**Goal:** Build the central message routing pipeline — the "spine" of the P11 WhatsApp messaging system. This async FastAPI/asyncio pipeline receives `UnifiedMessage` objects from any `ChannelAdapter` (P11-004), classifies intent via the `IntentClassifier` (P11-009), routes to either `ConversationalAgent` (P11-006) or `CommandHandler` (P11-010), formats the response via `ResponseFormatter` (P11-012), and sends it back through the originating channel. Every single message — WhatsApp, Discord future extension, any channel — flows through this pipeline exactly once, with safety gates (HARD STOP, whitelist, consent) checked before any processing.
**Dependencies:** P11-004 (ChannelAdapter interface — `UnifiedMessage` dataclass, `ChannelAdapter.send()` method), P11-005 (WhatsAppAdapter — concrete implementation returning `UnifiedMessage`), P11-006 (ConversationalAgent — NL response generation), P11-007 (ContextManager — session/memory context for agent), P11-009 (IntentClassifier — NL vs command detection, must be importable).
**Cost Impact:** $0/month (no new infrastructure; pipeline runs in-process within existing FastAPI app)
**ADR References:** ADR-022 (per-channel contract — routing must respect channel-specific contracts, e.g. WhatsAppAdapter format requirements), ADR-002 (HARD STOP — checked as first gate before any message processing, per §1 Consent-Safety Mandate)
**Acceptance Criteria:** AC-COM-001 (message routing functional — message from any channel reaches correct handler and response returns), SRS-IR-008 (safe word checked before routing — HARD STOP flag blocks all processing), P11 evidence showing end-to-end flow: WhatsApp message → pipeline → ConversationalAgent → formatted response → WhatsApp send
**Estimated Time:** 6 hours

#### Context

The message routing pipeline is the single most critical component in P11. Without it, all other components — ChannelAdapter, ConversationalAgent, CommandHandler, ResponseFormatter — are disconnected islands. The pipeline enforces the safety contract that defines Guinevere: no message is ever processed before HARD STOP is checked, no response is ever sent without consent verification, and every interaction is logged as structured metadata.

The pipeline operates as a single async entry point function `process_message(unified_message: UnifiedMessage) -> None` that is callable from any ChannelAdapter event handler. Internally, it is a sequential 9-stage pipeline with early-exit gates at stages 1-3 (safety checks) and branching at stage 5 (intent dispatch). All stages run within the same asyncio event loop; no external message broker (RabbitMQ, Kafka) is used — this is an in-process async pipeline, not a distributed system. The pipeline is stateless except for Redis reads (HARD STOP flag, whitelist, consent state, session context).

Error handling is critical: every stage has a try/except with structured logging (`structlog`), error classification (recoverable vs fatal), and graceful degradation. A failure in ConversationalAgent must NOT crash the pipeline — it must fall back to a persona-consistent error message sent back through the channel. Timeout handling: each stage has an async timeout (default 30s for agent calls, 5s for Redis reads) with `asyncio.wait_for()`.

The 9-stage flow: **(1) HARD STOP gate** — read `guinevere:hard_stop` Redis flag; if SET, silently discard message (no response, no processing — only auth fails offer a terse denial). **(2) Whitelist gate** — check `guinevere:whatsapp:whitelist` Redis set; if JID not present and whitelist is enforced, discard with optional "not authorized" response. **(3) Consent gate** — check `guinevere:consent` hash for Faiz's consent status; if comprehensive consent revoked, discard with consent reminder message. **(4) Metadata logging** — write message metadata (JID, timestamp, length, type) to Redis stream `guinevere:messages:incoming` for observability (Prometheus/Loki). **(5) Intent classification** — call `IntentClassifier.classify(message)` (P11-009) to get `IntentType.NL` or `IntentType.COMMAND`. **(6) Handler dispatch** — if NL: call `ConversationalAgent.generate_response(message, context)` with session context from ContextManager; if COMMAND: call `CommandHandler.handle(message)`. **(7) Response formatting** — pass LLM output or command response through `ResponseFormatter.format(text, channel="whatsapp")` (P11-012) for auto-split + markdown→WhatsApp conversion. **(8) Channel send** — call `originating_channel_adapter.send(to=message.sender_jid, text=formatted_response)`. **(9) Response logging** — write response metadata to Redis stream `guinevere:messages:outgoing`.

The pipeline runs inside the existing FastAPI lifespan or as a standalone async function triggered by the Neonize event loop. P11-003 (NeonizeClient wrapper) receives WhatsApp events, converts them to `UnifiedMessage`, and calls `process_message()`. The pipeline does NOT own any messaging lifecycle — it is purely a processing function.

#### Troubleshooting
- **Issue:** `uv run python -c "from src.agent.pipeline import process_message"` fails with `ImportError`
  - **Solution:** Check that all dependency modules (P11-004 through P11-012) are importable. Pipeline imports all of them. Run: `uv run python -c "from src.channels.base import ChannelAdapter; from src.agent.conversational_agent import ConversationalAgent; print('OK')"`
- **Issue:** Pipeline hangs indefinitely on stage 6 (agent call) — no response, no timeout
  - **Solution:** Verify `asyncio.wait_for()` is wrapping the agent call with a timeout. Default 30 seconds. Check: `grep -n "wait_for" src/agent/pipeline.py` should show entries for stages 1, 5, 6, 7, 8
- **Issue:** Redis connection refused on port 6380 when testing pipeline
  - **Solution:** Redis must be accessible from the local VPS. Verify: `systemctl is-active redis-server` then `redis-cli -p 6380 PING`. If Redis is on port 6379 instead, update `REDIS_PORT` pipeline config
- **Issue:** HARD STOP gate doesn't block — messages still processed when flag is `"true"`
  - **Solution:** Check that the HARD STOP check is the VERY FIRST line in `process_message()` before any other logic. Also check Redis key name: `guinevere:hard_stop` (not `hard_stop` without namespace). Run: `redis-cli -p 6380 GET guinevere:hard_stop`
- **Issue:** Pipeline works for one message but crashes on concurrent messages (race conditions)
  - **Solution:** `process_message()` is async but NOT thread-safe for shared state. Since it runs in an asyncio event loop (single-threaded), concurrent calls are fine as long as they don't share mutable state. Verify `ContextManager.get_context()` returns a deep copy, not a reference. Test with 10 concurrent messages: `asyncio.gather(*[process_message(msg) for msg in msgs])`
- **Issue:** Response sent through wrong channel (e.g., WhatsApp message gets Discord response)
  - **Solution:** The `ChannelAdapter` instance stored in `UnifiedMessage.source_adapter` (or passed through pipeline) must be the originating adapter. Verify: pipeline tracks `originating_adapter` separately and calls `originating_adapter.send()`, not a global default

#### Notes
- **THIS IS THE MOST CRITICAL STEP IN P11.** The pipeline is the spine connecting all P11 components. Every other P11 step feeds into or is consumed by this pipeline. If the pipeline is wrong, the entire P11 messaging system fails. Invest extra time in error handling, timeout management, and testing edge cases (empty messages, 10K char messages, concurrent messages, Redis failure, agent timeout).
- **Pipeline is channel-agnostic:** The `process_message()` function receives a `UnifiedMessage` and calls back to its source `ChannelAdapter`. This means the SAME pipeline handles WhatsApp today and Discord tomorrow without code changes. The only channel-specific logic is in the adapter (P11-005) and formatter (P11-012).
- **Safety-first ordering:** Stages 1-3 (HARD STOP, whitelist, consent) are strictly ordered and must execute before any message content is even examined. This is a non-negotiable consent-safety requirement per ADR-002 and PersonaSafetyPolicy §1.
- **9Router/LLM integration:** The ConversationalAgent (P11-006) is responsible for calling 9Router, not the pipeline. The pipeline only calls `agent.generate_response()` and receives the text output. LLM errors, retries, and fallback are the agent's responsibility.
- **Streaming considerations:** If P11-011 (typing indicator + streaming) is implemented, the pipeline stage 6 (handler dispatch) must yield partial chunks back to stage 8 (channel send) for progressive delivery. The current MVP design awaits full response before formatting/sending. Streaming integration is a P11 Expansion-phase optimization.
- **Cross-Reference P11-018 (Discord Mirror):** Stage 9 of the pipeline should eventually call the Discord mirror service to forward messages to Discord. For now, add a comment placeholder `# TODO: P11-018 — mirror to Discord` at the response logging stage.
- **Message deduplication:** WhatsApp may re-deliver messages (network retry, reconnection). Consider adding a lightweight deduplication check at stage 4 (metadata logging): Redis key `guinevere:messages:dedup:{message_id}` with TTL 60s. If exists, skip processing. This is optional for MVP.
- **Shared VPS constraint:** The pipeline runs in the same Python process as the FastAPI server, Discord bot, and Neonize client. Total memory for the pipeline itself is <10MB (stateless, no loaded models). Async overhead is negligible — just coroutine dispatch. No additional systemd service needed.
