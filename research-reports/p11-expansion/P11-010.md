### Step P11-010: Command Handler (`!` prefix) — Mirror Discord Slash Commands

**Type:** Application
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P11): pending`

**Goal:** Implement `CommandHandler` that processes `!`-prefixed commands on WhatsApp, providing functional parity with the 11 wired Discord slash commands. The command handler registers commands in an extensible registry, parses arguments from the command text, executes the corresponding Discord command logic, and returns formatted text responses suitable for WhatsApp (no Discord embeds — plain text with WhatsApp markdown).
**Dependencies:** P11-008 (routing pipeline — stage 6b dispatches to `CommandHandler.handle()`), P11-009 (intent classifier — provides `command_name` and `command_args` parsed from `!command`), Discord bot commands module (existing wired slash commands whose backend logic is reused)
**Cost Impact:** $0/month (pure Python reflection/routing; reuses existing Discord command backend without duplication)
**ADR References:** ADR-022 (per-channel contract — command responses formatted for WhatsApp, not Discord embeds), ADR-002 (HARD STOP reset command `!hard-stop-reset` must follow safety protocol exactly)
**Acceptance Criteria:** AC-COM-003 (command parity with Discord — all 11 wired commands have WhatsApp `!` equivalents), SRS-IR-008 (safe word works as command — `!hard-stop-reset` follows protocol), all commands return WhatsApp-formatted text responses
**Estimated Time:** 5 hours

#### Context

The Discord bot currently has 11 wired slash commands (and 22 stubs) registered through `discord.app_commands.CommandTree`. These commands are the primary operational interface to Guinevere: status checks, loop management, consent management, financial queries, HARD STOP control, memory operations, and surveillance access. WhatsApp must provide equivalent functionality via `!`-prefixed text commands so Faiz can control Guinevere even when Discord is unavailable (phone-only, mobile connection, Discord downtime).

The command handler is NOT a reimplementation of Discord command logic. It is a **thin adapter** that: (1) receives `command_name` and `command_args` from the intent classifier, (2) looks up the command in a registry, (3) executes the SAME backend function that the Discord slash command calls, (4) formats the return value as WhatsApp-compatible text (no embeds, no color codes, no interactive components). This avoids code duplication — the business logic (status checks, loop start/stop, consent management) lives in the Discord module and the WhatsApp handler calls into it.

Command registry design: a `dict[str, CommandSpec]` mapping command names to their handler functions, help text, and argument schemas. Commands are registered at module import time via a decorator `@register_command("status")`. The registry is extensible — adding a new command requires: (a) define the backend function (if not already in Discord module), (b) add a `@register_command` decorator, (c) add help text. The command handler auto-generates a `!help` command that lists all registered commands with descriptions.

WhatsApp text formatting rules (replacing Discord embeds): **(1) Bold:** `*text*` for headings, command output labels. **(2) Italic:** `_text_` for secondary info, notes. **(3) Strikethrough:** `~text~` for deprecated/historical data. **(4) Monospace:** ``` ```code``` ``` for IDs, timestamps, technical values. **(5) Line breaks:** WhatsApp supports `\n` natively — use for multi-line responses. **(6) Bullet lists:** Use `•` character (not `-`) since WhatsApp may not render markdown lists. **(7) No headers:** `#` / `##` are not supported — use `*bold on separate line*` instead. **(8) No links:** Bare URLs are auto-linkified by WhatsApp; `[text](url)` markdown links are converted to `text: url`.

#### Troubleshooting
- **Issue:** Discord command backend functions use `await ctx.respond()` or `interaction.response.send_message()` — no return value
  - **Solution:** Refactor Discord commands to separate business logic from presentation. Extract the core logic into a pure async function that returns `str` or a typed result. Then both Discord slash command handler AND WhatsApp `!command` handler call the same function. Example: `async def get_system_status() -> str:` called by both `status_slash(ctx)` and `!status` handler
- **Issue:** `!hard-stop-reset` clears the HARD STOP flag without any confirmation
  - **Solution:** The command must check: `if flag == "true": return "HARD STOP is active. Reply with !hard-stop-reset-confirm to proceed."` — then `!hard-stop-reset-confirm` actually clears it. This prevents accidental reset from message history.
- **Issue:** `!finance` command makes multiple PostgreSQL queries that take >5s
  - **Solution:** Add async timeout with `asyncio.wait_for(finance_query(), timeout=10.0)`. If timeout, return: `Finance query timed out. Try again or check Discord for full report.` Cache results for 60s in Redis to avoid repeated slow queries
- **Issue:** Command registry decorator `@register_command("status")` fails if function name conflicts
  - **Solution:** The decorator stores commands by the registered name string, not function name. Registry: `_commands: dict[str, Callable] = {}`. `@register_command("status")` maps `"status"` → function regardless of function name
- **Issue:** WhatsApp `!consent-grant all` triggers consent change but Discord doesn't know about the update
  - **Solution:** Consent changes (Redis `guinevere:consent` hash) are global state — both Discord and WhatsApp read from the same Redis key. No sync needed. If Discord has a consent cache, invalidate it on write: publish `guinevere:consent:updated` event to Redis pub/sub channel

#### Notes
- **Command Backend Reuse:** The command handler must NOT duplicate Discord business logic. Every `!command` handler should call the same backend function as its Discord slash command counterpart. If Discord commands use `ctx.respond()` directly, refactor them first to separate logic from presentation.
- **Discord → WhatsApp Command Mapping:**

|---|---|---|---|

| `/loop-start` | `!loop-start` | `start_agent_loop()` | Confirmation + current state |
| `/loop-stop` | `!loop-stop` | `stop_agent_loop()` | Confirmation + current state |

- **Command Confirmation for Destructive Operations:** `!hard-stop-reset` and `!consent-revoke` are destructive. They require a two-step confirmation: first command returns a prompt, second command (with `-confirm` suffix or reply text) executes. This mirrors Discord's confirmation modals.
- **WhatsApp-Specific Constraints:** No embeds, no buttons, no select menus, no ephemeral messages. All command output is plain text. Structure responses with clear headings (`*Section*`), bullet points (`•`), and line breaks. Test on actual WhatsApp to verify formatting renders correctly.
