### Step P11-009: Natural Language Intent Classifier — NL vs Command Detection

**Type:** Application
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P11): pending`

**Goal:** Implement `IntentClassifier` that distinguishes natural language messages (→ `ConversationalAgent`) from command messages (→ `CommandHandler`) using the `!` prefix convention. Handle edge cases: empty messages, sticker-only, forwarded messages, media-only messages. The classifier is the single decision point at pipeline stage 5 that determines which branch every message takes — NL path for conversation, command path for operations, media ack path for unsupported media, or silent discard for empty input.
**Dependencies:** P11-008 (routing pipeline — pipeline calls `IntentClassifier.classify()` at stage 5), P11-004 (ChannelAdapter interface — `UnifiedMessage` dataclass defining `text`, `message_type`, `media_type`, `is_forwarded` fields)
**Cost Impact:** $0/month (pure Python classification logic — no external API, no ML inference, no additional infrastructure)
**ADR References:** ADR-022 (command format per channel — `!` prefix chosen for WhatsApp, avoiding `/` which conflicts with file paths and `.` which appears in natural text)
**Acceptance Criteria:** AC-COM-002 (command detection accurate — `!command` messages correctly identified and parsed, NL messages correctly identified, edge cases handled gracefully with deterministic classification)
**Estimated Time:** 2 hours

#### Context

Faiz's design decision: natural language is the **primary** interaction mode on WhatsApp, commands are the **fallback**. Guinevere is first and foremost an AI companion — casual conversation flows naturally through the ConversationalAgent (P11-006). However, operational control (status checks, loop management, consent management, financial queries) needs a structured command interface. The `!` prefix was chosen over `/` (which looks like file paths: `/home`, `/status`), `.` (which appears in normal text: "I'm... not sure"), and `#` (which conflicts with WhatsApp text formatting). The `!` prefix is unambiguous, familiar from IRC/bot conventions, and rarely appears at the start of conversational sentences.

Classification logic is intentionally simple — no ML model, no regex black magic. The classifier is a pure Python async function with four classification outcomes: **(1) Text message → starts with `!` after whitespace strip → `IntentType.COMMAND`** with command name and arguments parsed from remaining text. **(2) Text message → does not start with `!` → `IntentType.NL`** routing to ConversationalAgent. **(3) Non-text message (image, audio, video, document) → `IntentType.MEDIA_ACK`** routing to MediaAcknowledgmentHandler (P11-013). **(4) Sticker-only message → `IntentType.STICKER_ACK`** also routing to media handler (MVP treats stickers same as media). **(5) Empty/whitespace-only message → `IntentType.EMPTY`** for silent discard by the pipeline. The classifier returns an `IntentResult` dataclass containing `intent_type`, optional `command_name`, optional `command_args` list, and `raw_text` for downstream handlers.

Command parsing uses simple whitespace splitting: `!loop-start --silent --reason "nightly run"` parses as `command_name="loop-start"`, `command_args=["--silent", "--reason", "nightly run"]`. No argparse-style parsing is performed here — that is the CommandHandler's responsibility (P11-010). The classifier only extracts and labels the command name and raw argument string. The classifier is implemented in `src/agent/intent_classifier.py` with a single public async method `async def classify(message: UnifiedMessage) -> IntentResult`. It is async because future versions may query context (e.g., "was the last message a command?"), though the MVP implementation is internally synchronous.

Edge case handling is explicit and exhaustive: **(a) Empty message** (text is `""`, `None`, or whitespace-only after strip): `IntentType.EMPTY` — pipeline silently discards at stage 5. **(b) Media-only message** (Neonize emits `imageMessage`, `audioMessage`, `videoMessage`, `documentMessage` events with no text body): `IntentType.MEDIA_ACK`. **(c) Sticker message** (Neonize `stickerMessage` event): `IntentType.STICKER_ACK` — for MVP, routed to same media handler. **(d) Forwarded message** (Neonize sets `IsForwarded: True`): treat as normal text — classify based on `!` prefix as usual. Forwarded text is still text. **(e) Reply with quoted text** (lines starting with `> `): strip quote prefix before classification. **(f) Very long message** (>10000 chars): classify based on `!` prefix normally; downstream handlers handle truncation.

#### Troubleshooting
- **Issue:** `!command` with no arguments raises `IndexError` when parsing
  - **Solution:** Handle split result gracefully: `parts = text.strip().split(maxsplit=1)`, then `command_name = parts[0][1:]` (strip `!`), `command_args = parts[1].split() if len(parts) > 1 else []`. Never assume args exist.
- **Issue:** Message with `!` in the middle of text (e.g., "Wow! That's amazing!") classified as COMMAND
  - **Solution:** Command detection uses `text.strip().startswith('!')` — only leading `!` triggers command routing. Verify: `"Wow! That's amazing!".strip().startswith('!')` is `False`.
- **Issue:** `UnifiedMessage` has no `is_forwarded` field → `AttributeError` on forwarded messages
  - **Solution:** Add `is_forwarded: bool = False` as optional field to `UnifiedMessage` dataclass in P11-004 (ChannelAdapter). Forwarded status comes from Neonize `proto.IWebMessageInfo.IsForwarded`. The classifier does NOT use this field for classification — forwarded text is classified normally.
- **Issue:** Sticker detection fails because Neonize sets `message_type="media"` with `media_type="sticker"` instead of `message_type="sticker"`
  - **Solution:** Check both fields in the classifier: `if message.message_type == "sticker" or message.media_type == "sticker": return IntentType.STICKER_ACK`. Test with actual Neonize sticker event payload to confirm field names.
- **Issue:** Neonize sends message with `.GetConversation()` returning `""` for media messages (empty string, not `None`)
  - **Solution:** Normalize text in classifier entry: `text = message.text if message.text else None`, then `if text is None or text.strip() == "":` handles both `None` and empty string cases.
- **Issue:** Leading whitespace before `!` (e.g., `"  !status"`) not detected as command
  - **Solution:** Always `text.strip()` before checking `startswith('!')`. The classifier must strip all leading/trailing whitespace before any classification logic.

#### Notes
- **No ML here:** Do NOT add an LLM-based intent classifier. This is a deterministic rule-based classifier. The operator (Faiz) explicitly chose `!` for commands because it is unambiguous without AI. Adding ML would add latency, cost, and unpredictability for zero benefit. The classifier must execute in <1ms.
- **Primary vs Fallback interaction:** NL is primary (most messages), commands are fallback (operational control). This means: (a) zero false negatives for NL messages — every non-`!` message goes to ConversationalAgent, (b) false positives for commands only if someone starts a conversational sentence with `!` (rare), (c) misclassification of `!` as NL only possible with leading whitespace before `!` (which is stripped before checking).
- **Forwarded messages:** Neonize's `MessageEv` has an `IsForwarded` boolean field. The WhatsAppAdapter (P11-005) should map this to `UnifiedMessage.is_forwarded`. The classifier does NOT special-handle forwarded messages — they are classified by text content alone.
- **Reply prefix stripping:** WhatsApp replies may include `> ` quoted text. The WhatsAppAdapter (P11-005) should extract the actual reply text. If it does not, the classifier strips lines starting with `> ` before classification.
- **Future expansion:** The `IntentType` enum is extensible. Reserve space for future types: `VOICE_COMMAND` (after voice transcription in Expansion phase), `SCHEDULED`, `SYSTEM`. Keep current enum lean for MVP.
- **Cross-Reference P11-013:** Media acknowledgment handler receives `IntentType.MEDIA_ACK` and `IntentType.STICKER_ACK` results. The pipeline routes these to `MediaAckHandler.send_acknowledgment()` instead of ConversationalAgent or CommandHandler.
- **Cross-Reference P11-010:** CommandHandler receives `IntentResult` with `command_name` and `command_args` already parsed. CommandHandler performs further argument parsing, validation, and execution.
