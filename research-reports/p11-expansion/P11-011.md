### Step P11-011: Typing Indicator + Response Streaming

**Type:** Application
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P11): pending`

**Goal:** Implement WhatsApp typing indicators and response streaming delivery. On message receive, immediately send a "typing" presence event via Neonize before LLM processing begins. If LLM response generation exceeds 2 seconds, send partial response chunks progressively to reduce perceived latency. Target: first visible response bubble within 3 seconds of message receipt. Typing indicator must be sent for every incoming message (NL or command) and cleared after response delivery or on error.
**Dependencies:** P11-005 (WhatsAppAdapter — `send_chat_presence()` method and `send_message()` available), P11-006 (ConversationalAgent — `generate_response()` supports optional streaming callback or yields partial tokens)
**Cost Impact:** $0/month (typing indicators are protocol-level presence events with no API cost; streaming is in-process async iteration)
**ADR References:** ADR-022 (WhatsApp UX expectations — typing indicator signals "Guinevere is thinking", progressive response delivery for long outputs)
**Acceptance Criteria:** AC-COM-004 (response latency perceived <3s — typing indicator appears within 500ms of message receipt, first response chunk arrives within 3s), SRS-IR-007 (text handling — typing indicator and streaming apply only to text responses, not media)
**Estimated Time:** 3 hours

#### Context

WhatsApp typing indicators are a critical UX signal. When a user sends a message and sees the "typing..." indicator, they know Guinevere is processing their message and a response is coming. Without typing indicators, the user sees silence for the entire LLM response generation time (typically 2-8 seconds depending on model, prompt length, and 9Router latency) — which feels like the system is unresponsive or crashed. The typing indicator bridges this gap by providing immediate visual feedback while the LLM works.

Neonize supports typing indicators via `client.send_chat_presence(to=jid, presence="composing")` which sends a typing presence event to the WhatsApp chat. This indicator auto-clears after approximately 25 seconds if not refreshed or explicitly stopped. To stop typing, send `presence="paused"`. The typing indicator must be sent as the FIRST action when a message arrives — before any pipeline processing, before whitelist checks, before intent classification. If the message is rejected (not whitelisted, HARD STOP, etc.), the typing indicator should be cleared without sending a response. This ensures the user sees "typing" for every message they send, even if Guinevere ultimately decides not to respond.

Response streaming is the second half of this step. If the ConversationalAgent (P11-006) supports streaming (yielding partial tokens as they arrive from 9Router/LLM), the pipeline can send progressive chunks to WhatsApp rather than waiting for the full response. Strategy: **(1)** on message receive → immediately send typing indicator, **(2)** call ConversationalAgent with optional streaming callback, **(3)** if streaming is available → accumulate tokens into sentence-complete chunks, send each chunk when ready, **(4)** if streaming is NOT available (9Router may not support it) → wait for full response, then send via normal path. The streaming path must gracefully fall back to the full-response path if streaming fails at any point.

The 3-second perceived latency target (AC-COM-004) is achieved by the combination of typing indicator (<500ms to appear) and either streaming (first chunk within 3s) or fast-enough LLM response. If the LLM takes >5s for the first token, the typing indicator alone satisfies the UX requirement — the user sees "typing" and knows something is happening. The implementation must handle timeout scenarios: if no response within 30s, clear typing indicator and send a persona-consistent timeout message ("Maaf sayang, mommy lagi sibuk sebentar. Coba lagi ya 💕").

class TypingIndicator:
    """Manages typing indicator lifecycle for WhatsApp conversations.

    Sends 'composing' presence on message receive, clears with 'paused'
    on response delivery or error. Auto-clears after 25s timeout.
    """

    def __init__(self, neonize_client: NewClient):
        self._client = neonize_client
        self._active_typing: dict[str, float] = {}  # jid -> start_time

    async def start_typing(self, jid: str) -> None:
        """Send typing indicator. Idempotent — no-op if already typing."""
        await self._client.send_chat_presence(to=jid, presence="composing")
        self._active_typing[jid] = time.monotonic()

    async def stop_typing(self, jid: str) -> None:
        """Clear typing indicator. Idempotent — no-op if not typing."""
        if jid in self._active_typing:
            await self._client.send_chat_presence(to=jid, presence="paused")
            del self._active_typing[jid]

    async def force_clear_all(self) -> None:
        """Emergency: clear all active typing indicators."""
        for jid in list(self._active_typing.keys()):
            await self.stop_typing(jid)
DESIGN

# 6. Implement ResponseStreamer for progressive delivery
cat > /dev/null << 'DESIGN'
class ResponseStreamer:
    """Streams LLM response chunks to WhatsApp with typing indicator management.

    Strategy:
    - If LLM supports streaming: accumulate tokens into sentence-complete
      chunks, send each when ready.
    - If LLM does not support streaming: wait for full response, send once.
    - Always clear typing indicator when done or on error.
    """

    CHUNK_THRESHOLD = 80  # chars before attempting to flush a chunk
    MAX_CHUNK_WAIT = 5.0  # seconds before flushing partial chunk

    async def stream_response(
        self,
        jid: str,
        response_generator,  # async generator yielding tokens/strings
        typing: TypingIndicator,
    ) -> list[str]:
        """Stream response chunks. Returns list of sent chunks."""
        sent_chunks = []
        buffer = ""
        try:
            async for token in response_generator:
                buffer += token
                # Flush at sentence boundaries
                if len(buffer) >= self.CHUNK_THRESHOLD:
                    chunk = self._extract_complete_sentence(buffer)
                    if chunk:
                        await typing.stop_typing(jid)
                        await self._send_chunk(jid, chunk)
                        sent_chunks.append(chunk)
                        buffer = buffer[len(chunk):]
                        await typing.start_typing(jid)  # resume typing for next chunk
            # Flush remaining buffer
            if buffer.strip():
                await typing.stop_typing(jid)
                await self._send_chunk(jid, buffer.strip())
                sent_chunks.append(buffer.strip())
        except Exception:
            await typing.stop_typing(jid)
            raise
        return sent_chunks
DESIGN

#### Troubleshooting
- **Issue:** `send_chat_presence()` not found on Neonize `NewClient` — `AttributeError`
  - **Solution:** Check Neonize version and API. The method may be named differently (e.g., `send_presence`, `chat_presence`). Inspect with `dir(client)` and check Neonize docs. Alternative: use the raw protobuf presence message via `client.send_message()` with a presence payload.
- **Issue:** Typing indicator shows indefinitely — never clears after response
  - **Solution:** Always wrap response delivery in try/finally to ensure `stop_typing()` is called. Add a watchdog timer: if typing is active for >25s (WhatsApp's auto-clear window), force clear. Implement `asyncio.Task` that auto-clears after timeout.
- **Issue:** Streaming causes out-of-order message delivery — chunk 2 arrives before chunk 1
  - **Solution:** WhatsApp guarantees message ordering within a chat session. The issue is likely concurrent `send_message()` calls. Ensure chunks are sent sequentially with `await` (not `asyncio.gather()`). Each chunk must complete before the next starts.
- **Issue:** LLM streaming not supported by 9Router — `response_generator` is not an async generator
  - **Solution:** `ResponseStreamer` must detect non-streaming mode. Check if `response_generator` has `__aiter__` method. If not, treat the entire response as a single chunk and send via normal path. The fallback path is the MVP default.
- **Issue:** Typing indicator sent to group chats (should be 1-on-1 only)
  - **Solution:** Check JID format before sending typing. Group JIDs end with `@g.us` — reject these. Only send typing to JIDs matching `*@s.whatsapp.net` (1-on-1 chats).
- **Issue:** Multiple rapid messages cause overlapping typing indicators
  - **Solution:** `TypingIndicator` tracks active typing per JID. If a new message arrives while typing is already active for that JID, do NOT re-send typing — it is already showing. Only reset the timeout tracker.

#### Notes
- **MVP streaming is optional:** 9Router may not support streaming response generation. The `ResponseStreamer` must work in both modes: streaming (async generator of tokens) and non-streaming (single complete response string). The non-streaming path is the expected MVP default.
- **Typing indicator is mandatory:** Even if streaming is not available, the typing indicator MUST be sent. This is the primary UX improvement — the user sees "typing" while waiting for the full response.
- **WhatsApp auto-clear:** WhatsApp automatically clears typing indicators after ~25 seconds. The implementation should not rely on this — always explicitly send `presence="paused"` after response delivery. The 25s auto-clear is a safety net, not a design assumption.
- **Rate limiting interaction:** The rate limiter (P11-003/P11-005) applies to outgoing messages, NOT to presence events. Typing indicators do not count toward the 8 messages/minute rate limit. Verify this with Neonize — if presence events DO count, adjust the rate limiter to exclude them.
- **Cross-Reference P11-008:** The routing pipeline (P11-008) should call `TypingIndicator.start_typing()` at stage 0 (before any safety checks), and `TypingIndicator.stop_typing()` after stage 8 (channel send) or on any early exit. This ensures typing appears for every message, even rejected ones.
- **Cross-Reference P11-012:** ResponseFormatter (P11-012) splits responses into multiple bubbles. If streaming is active, each formatted bubble from the formatter is a separate chunk sent by the streamer. The formatter and streamer coordinate: formatter produces chunks, streamer delivers them.
