#### Context

Neonize stores WhatsApp session state internally using a SQLite-backed store from whatsmeow. The `NewClient(store_path="session.db")` constructor automatically persists device registration keys, pre-keys, and noise protocol state to the specified SQLite file. This session data is **cryptographically sensitive** — it contains the device's E2E encryption identity keys and must never be stored in plaintext. Per ADR-015, all secrets at rest must be encrypted with SOPS+age.

The authentication flow has two methods: (1) **QR scan** (primary) — Neonize generates a QR code that Faiz scans with his WhatsApp mobile app, linking the VPS as a companion device; (2) **Pairing code** (fallback) — Neonize generates an 8-digit code that Faiz enters in WhatsApp's "Link a Device" screen, useful when QR scanning is impractical (e.g., SSH terminal without graphical output). Both methods use the WhatsApp Multi-Device (MD) protocol and produce identical session state.

After successful pairing, the session persists across service restarts — the SQLite file retains all keys. However, WhatsApp enforces a 14-day phone-online requirement: if Faiz's phone does not connect to WhatsApp servers at least once every 14 days, the linked device session is invalidated and re-pairing is required. This step implements session age tracking in Redis (`guinevere:whatsapp:session:paired_at`) so the Discord bot can send a reminder at day 12 ("Phone perlu online untuk maintain WhatsApp connection").

The Redis key namespace for WhatsApp is `guinevere:whatsapp:*`. The encrypted session blob is stored at `guinevere:whatsapp:session` (SOPS-encrypted, no TTL). Session metadata (paired_at, last_phone_online, jid_hash) is stored at `guinevere:whatsapp:session:meta` as a Redis hash with no TTL. Consent state is stored at `guinevere:whatsapp:consent` as a Redis hash.

"""WhatsApp session authentication via Neonize.

Handles QR scan (primary) and pairing code (fallback) authentication,
session encryption with SOPS+age, and session persistence in Redis.
"""

import hashlib
import time
from dataclasses import dataclass, field
from enum import Enum
from pathlib import Path
from typing import Optional

from neonize import NewClient


class AuthMethod(str, Enum):
    """Authentication method used for current session."""
    QR_SCAN = "qr_scan"
    PAIRING_CODE = "pairing_code"


class SessionState(str, Enum):
    """Current session authentication state."""
    UNPAIRED = "unpaired"
    PAIRING = "pairing"
    PAIRED = "paired"
    EXPIRED = "expired"
    ERROR = "error"


@dataclass
class SessionMetadata:
    """WhatsApp session metadata stored in Redis (not encrypted)."""
    state: SessionState = SessionState.UNPAIRED
    auth_method: Optional[AuthMethod] = None
    paired_at: Optional[float] = None
    last_phone_online: Optional[float] = None
    jid_hash: Optional[str] = None  # SHA-256 hash of JID, not plaintext
    session_age_days: float = field(default=0.0)

    @property
    def needs_phone_reminder(self) -> bool:
        """True if session is >12 days old (phone needed online within 14 days)."""
        if self.paired_at is None:
            return False
        age_days = (time.time() - self.paired_at) / 86400
        return age_days > 12

    @property
    def is_expired(self) -> bool:
        """True if session exceeds 14-day phone-offline threshold."""
        if self.last_phone_online is None:
            return False
        days_since_phone = (time.time() - self.last_phone_online) / 86400
        return days_since_phone > 14


# Redis key constants
REDIS_SESSION_KEY = "guinevere:whatsapp:session"
REDIS_SESSION_META_KEY = "guinevere:whatsapp:session:meta"
REDIS_CONSENT_KEY = "guinevere:whatsapp:consent"

# Session file path
SESSION_STORE_PATH = Path("/opt/guinevere/whatsapp-session/session.db")
PYTHON_EOF

"""SOPS+age encryption helpers for WhatsApp session data.

Session data is encrypted before storage in Redis per ADR-015.
Plaintext session data must never appear in Redis, logs, or evidence.
"""

import subprocess
from pathlib import Path
from typing import Optional


def sops_encrypt_bytes(plaintext: bytes, age_recipient: str) -> bytes:
    """Encrypt raw bytes using SOPS with age recipient key.

    Args:
        plaintext: Raw session data bytes to encrypt.
        age_recipient: Age public key string for encryption.

    Returns:
        SOPS-encrypted bytes.

    Raises:
        RuntimeError: If SOPS encryption fails.
    """
    result = subprocess.run(
        ["sops", "--encrypt", "--input-type", "binary",
         "--output-type", "binary", "--age", age_recipient,
         "/dev/stdin"],
        input=plaintext,
        capture_output=True,
        timeout=30,
    )
    if result.returncode != 0:
        raise RuntimeError(f"SOPS encrypt failed: {result.stderr.decode()}")
    return result.stdout


def sops_decrypt_bytes(ciphertext: bytes) -> bytes:
    """Decrypt SOPS-encrypted bytes using local age key.

    Args:
        ciphertext: SOPS-encrypted bytes.

    Returns:
        Decrypted plaintext bytes.

    Raises:
        RuntimeError: If SOPS decryption fails.
    """
    result = subprocess.run(
        ["sops", "--decrypt", "--input-type", "binary",
         "--output-type", "binary", "/dev/stdin"],
        input=ciphertext,
        capture_output=True,
        timeout=30,
    )
    if result.returncode != 0:
        raise RuntimeError(f"SOPS decrypt failed: {result.stderr.decode()}")
    return result.stdout

#### Troubleshooting
- **Issue:** `sops --encrypt` fails with "config file not found" or "no matching creation rules"
  - **Solution:** Verify `.sops.yaml` exists in repo root with correct `creation_rules` matching the age recipient. For binary input, SOPS may need `--input-type binary --output-type binary` flags explicitly. Check: `sops --encrypt --age <pubkey> --input-type binary /dev/stdin`
- **Issue:** `age-keygen -y` fails because age key file does not exist at `~/.config/sops/age/keys.txt`
  - **Solution:** Generate a new age key: `age-keygen -o ~/.config/sops/age/keys.txt`. Update `.sops.yaml` with the new public key. **WARNING:** This invalidates all existing SOPS-encrypted files — decrypt and re-encrypt them with the new key.
- **Issue:** Redis `AUTH` fails with ACL user `guinevere_core`
  - **Solution:** Verify Redis ACL configuration: `redis-cli -p 6380 ACL LIST | grep guinevere_core`. Ensure the user has permissions for `guinevere:whatsapp:*` key pattern. Check password in `.env` file matches Redis ACL config.
- **Issue:** `/opt/guinevere/whatsapp-session/` cannot be created (permission denied)
  - **Solution:** Run as root or with sudo: `sudo mkdir -p /opt/guinevere/whatsapp-session && sudo chown $(whoami):$(whoami) /opt/guinevere/whatsapp-session && sudo chmod 700 /opt/guinevere/whatsapp-session`
- **Issue:** Neonize QR code does not display in terminal (garbled output)
  - **Solution:** Use pairing code fallback instead. Neonize supports `client.connect(pair_code=True)` which generates an 8-digit alphanumeric code. Alternatively, redirect QR to a file and display as image: `pip install qrcode[pil]` and render the QR string to PNG.
- **Issue:** Session age calculation incorrect (false expired or false fresh)
  - **Solution:** Verify timestamps use Unix epoch seconds (`time.time()`), not datetime objects. Redis stores paired_at as string — convert with `float()` before arithmetic. Session expiry threshold is 14 days (1,209,600 seconds). Reminder threshold is 12 days (1,036,800 seconds).

#### Notes
- **QR Code Expiry:** WhatsApp QR codes expire quickly — first QR valid for 60 seconds, subsequent QRs for 20 seconds, with a maximum of 6 regenerations. The auth module must handle QR refresh events from Neonize and display the updated QR to Faiz in near-real-time.
- **Pairing Code Fallback:** The 8-digit pairing code (`client.connect()` with pairing mode) is slower to pair (~30-60 seconds to complete) but works over SSH without graphical terminal support. Implement as fallback when QR display fails.
- **SOPS Binary Mode:** Neonize's SQLite session file is binary data, not JSON/YAML. SOPS must use `--input-type binary --output-type binary` flags for encryption. The default SOPS format (JSON) corrupts binary data.
- **Session Data Classification:** WhatsApp session data contains E2E encryption identity keys. Per ADR-024 (Data Governance & Classification), this is CRITICAL classification level — same as financial data. Never log, print, or include in evidence files.
- **Consent Flow (Implemented in P11-004+):** The consent opt-in (`!consent-grant`) is not implemented in this step. This step only sets up the Redis key `guinevere:whatsapp:consent` and the `SessionMetadata` structure. The actual consent prompt and `!consent-grant`/`!consent-revoke` commands are part of the WhatsAppAdapter in P11-004+.
- **Cross-Channel HARD STOP (ADR-002):** The session metadata includes `jid_hash` (SHA-256 of WhatsApp JID) so the cross-channel HARD STOP handler can identify which WhatsApp session to disconnect. The hash is used instead of plaintext JID to avoid storing identifiable data in Redis metadata.
- **Phone Online Tracking:** `last_phone_online` in `SessionMetadata` is updated when Neonize reports phone connectivity events. This is separate from `paired_at` which is set once at initial pairing. The Discord reminder system (P11-008+) reads `paired_at` to calculate session age.
- **Redis Key Design:** Session data (encrypted blob) uses a simple string key (`guinevere:whatsapp:session`). Metadata uses a Redis hash (`guinevere:whatsapp:session:meta`) for efficient field-level reads without decrypting the session blob. Consent state uses a separate hash (`guinevere:whatsapp:consent`).
