### Step P11-012: Response Formatting — Auto-Split, Markdown → WhatsApp

**Type:** Application
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P11): pending`

**Goal:** Implement `ResponseFormatter` that prepares LLM output for WhatsApp delivery. Performs three transformations: (1) convert standard markdown to WhatsApp formatting (`**bold**` → `*bold*`, `_italic_` stays, `# Header` → `*Header*`, `- list` → `• list`), (2) auto-split messages exceeding 1000 characters into multiple bubbles with `(1/N) (2/N)` prefix numbering, (3) strip unsupported HTML and complex markdown (tables, images, nested links). Handles code blocks with language tags preserved as WhatsApp triple-backtick format.
**Dependencies:** P11-005 (WhatsAppAdapter `send_message()` — accepts string content, sends to JID), P11-006 (ConversationalAgent — produces raw markdown response text)
**Cost Impact:** $0/month (pure Python text transformation — no external API, no regex engine overhead)
**ADR References:** ADR-022 (WhatsApp message format — WhatsApp supports `*bold*`, `_italic_`, `~strikethrough~`, ` ```monospace``` `, no HTML, no markdown headers, no image embeds, no table rendering)
**Acceptance Criteria:** AC-COM-005 (formatting correct — markdown converted to WhatsApp-native format, no raw markdown visible to user, code blocks preserved), SRS-IR-007 (text-only output — no media generation, no HTML injection)
**Estimated Time:** 3 hours

#### Context

LLM responses from the ConversationalAgent (P11-006) are standard markdown — the LLM produces `**bold**`, `# Headers`, `- lists`, `[links](url)`, ``` ```python ``` code blocks, and occasionally tables or image references. WhatsApp does NOT render standard markdown. WhatsApp has its own formatting convention: `*bold*` (single asterisk), `_italic_` (underscore), `~strikethrough~` (tilde), and ` ```monospace``` ` (triple backtick with optional language tag). Headers, links, images, and tables are not supported. If the LLM response is sent raw to WhatsApp, the user sees asterisk clutter (`**this is bold**` instead of **this is bold**) and broken link syntax.

The `ResponseFormatter` sits between the ConversationalAgent's raw output and the WhatsAppAdapter's `send_message()` call (invoked by the routing pipeline P11-008 at stage 7). It receives a raw response string and a channel identifier (`"whatsapp"`), applies channel-specific formatting rules, and returns a `list[str]` of formatted message chunks. Each chunk is a self-contained WhatsApp message ready for delivery. The formatter is channel-aware — the same class can be extended for Discord (which supports full markdown) in the future, but P11 only implements the WhatsApp channel.

Auto-splitting is required because WhatsApp messages have a technical limit of 65,536 characters, but the practical UX limit for comfortable mobile reading is approximately 1000 characters. Long LLM responses (common for explanations, code blocks, multi-paragraph answers) must be split into multiple sequential messages. The split must occur at sentence or paragraph boundaries — never mid-word or mid-code-block. Each chunk is prefixed with `(1/N)`, `(2/N)`, etc. to indicate sequence. Maximum number of chunks per response is capped at 10 (10,000 chars effective) to prevent message flooding; if the response exceeds this, truncate with a "...(truncated)" suffix and log a warning.

Code block handling requires special care. WhatsApp supports triple-backtick code blocks with an optional language identifier (e.g., ` ```python `). The formatter preserves code blocks as-is during markdown conversion. During auto-split, code blocks must NOT be split across chunks — if a code block would straddle a chunk boundary, the entire code block goes into the next chunk. If a single code block exceeds 1000 characters, it gets its own chunk (or chunks if >2000 chars, with a `...continued...` marker).

#### Troubleshooting
- **Issue:** Regex for bold conversion double-applies — `**bold**` becomes `**bold**` instead of `*bold*`
  - **Solution:** Use careful regex ordering. Convert `**text**` → `*text*` BEFORE converting standalone `*text*` → `_text_`. Use negative lookahead/lookbehind to avoid matching `**` as two `*` characters. Test: `re.sub(r'\*\*(.+?)\*\*', r'*\1*', text)`.
- **Issue:** Italic detection conflicts with bold — `***bold italic***` produces malformed output
  - **Solution:** Handle combined bold+italic as a special case: `***text***` → `*_text_*` (WhatsApp supports nested formatting). Process `***` before `**` and `*` in the regex chain.
- **Issue:** Auto-split breaks inside a code block — chunk 1 ends with ` ```python\ndef foo(): ` and chunk 2 starts with `    return 1\n``` `
  - **Solution:** Before splitting, identify all code block regions (between ` ``` ` markers). Treat each code block as an atomic unit — never split inside it. If a code block exceeds chunk size, give it its own chunk(s).
- **Issue:** Links with complex markdown inside (e.g., `[**bold link**](url)`) not fully converted
  - **Solution:** Process link conversion BEFORE bold conversion. Strip the link syntax first: `[**bold link**](url)` → `**bold link** (url)`, then apply bold conversion: `*bold link* (url)`.
- **Issue:** Response contains emoji that breaks WhatsApp formatting (e.g., `*` emoji or `_` in unusual positions)
  - **Solution:** WhatsApp formatting markers only apply when they are at word boundaries. The formatter should not strip emoji. If formatting conflicts arise, prefer plain text over malformed formatting.
- **Issue:** `format()` called with `channel="discord"` — Discord supports full markdown, no conversion needed
  - **Solution:** The `channel` parameter controls which rule set to apply. For `"discord"`, return the raw text unchanged (Discord renders standard markdown natively). For `"whatsapp"`, apply all conversions. Default to `"whatsapp"` if unspecified.

#### Notes
- **WhatsApp formatting is limited:** Only `*bold*`, `_italic_`, `~strikethrough~`, and ` ```monospace``` ` are supported. No headers, no links, no images, no tables. The formatter must gracefully degrade all unsupported formats to plain text equivalents.
- **1000-character UX limit:** While WhatsApp allows 65,536 characters per message, mobile users find long messages difficult to read. The 1000-character split target ensures each bubble fits comfortably on a phone screen (~20-25 lines of text). This is a UX decision, not a technical constraint.
- **Code blocks are sacred:** Code blocks are the most formatting-sensitive content. They must be preserved exactly — no markdown conversion inside code blocks, no auto-split inside code blocks, no prefix numbering inside code blocks. The formatter must identify code block boundaries (triple backtick pairs) before applying any transformation.
- **Cross-Reference P11-008:** The routing pipeline calls `ResponseFormatter.format(raw_text, channel="whatsapp")` at stage 7, then iterates over the returned `list[str]` at stage 8 (channel send). Each string in the list is one WhatsApp message.
- **Cross-Reference P11-011:** If streaming is active, the ResponseFormatter may be called incrementally on partial responses. In streaming mode, the formatter should buffer until a complete sentence or paragraph is available before formatting and emitting a chunk. For MVP, the formatter is called once on the complete response — streaming integration is Expansion-phase.
- **Persona-consistent output:** The formatter does NOT modify persona content (Y4 tone, emoji, Indonesian/English mixing). It only transforms formatting markers. If the LLM response contains `sayang` and `💕`, these pass through unchanged.
- **Future Discord support:** The same `ResponseFormatter` class will serve Discord with a different rule set. Discord supports `**bold**`, `*italic*`, `~~strikethrough~~`, code blocks, links, and embeds. The `channel` parameter selects the rule set. For P11, only `"whatsapp"` is implemented.
