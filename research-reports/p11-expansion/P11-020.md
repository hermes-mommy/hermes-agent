### Step P11-020: Reconnection Handler — 3 Retry, Exponential Backoff

**Type:** Application
**Status:** Not Started
**Risk:** High
**Git Commit:** `feat(P11): pending`

**Goal:** Implement reconnection logic for WhatsApp connection drops. 3 retry attempts with exponential backoff (30s → 60s → 120s). On all failures: Discord alert + Gotify notification, mark `needs_manual_reconnect` in Redis, stop retrying. Handle 4 failure categories: session expired (new QR needed), network timeout (retry), Neonize internal error (retry with fresh client), protocol version mismatch (alert + wait for update).
**Dependencies:** P11-003 (NeonizeClient — `ConnectedEv`, `DisconnectedEv`, `PairStatusEv` event handlers), P11-019 (Discord notifications — `WhatsAppNotificationManager` for lifecycle alerts)
**Cost Impact:** $0/month (no new infrastructure; purely application logic)
**ADR References:** ADR-022 (Connection Management — WhatsApp connection lifecycle with separate handlers), ADR-032 (Operational Resilience — graduated failure responses with notification escalation)
**Acceptance Criteria:** AC-OPS-003 (auto-reconnect — system attempts automatic reconnection with exponential backoff and alerts on final failure), AC-OPS-004 (graceful degradation — WhatsApp unavailability does not crash API or other subsystems)
**Estimated Time:** 4 hours

#### Context

WhatsApp connections via Baileys/Neonize are inherently unstable — protocol changes every 2-8 weeks and network disruptions cause unexpected socket drops. Without a reconnection handler, every disconnect requires manual SSH intervention to restart the service. The Evolution API ecosystem documented a notorious false logout bug (HTTP 515 → 401 cascade) where transient server errors were mistakenly interpreted as permanent session expirations, causing unnecessary QR re-pairing cycles. The handler must distinguish real session invalidation from transient infrastructure errors to avoid spurious re-pairing.

The reconnection handler implements a finite state machine with 4 states: `CONNECTED` (normal operation), `DISCONNECTED(reason)` (transition on any Neonize `DisconnectedEv` with categorized reason), `RECONNECTING(attempt_N)` (active retry in progress, attempt counter advances), and `FAILED` (all retries exhausted, system enters degraded mode). Each state transition is logged to PostgreSQL via `ConnectionEvent` model and written to Redis key `guinevere:wa:connection:state` for real-time dashboard queries (P11-021). The `RECONNECTING` state includes a `last_error` field for diagnostic visibility.

The backoff strategy uses `attempt * 30s` increments: first retry after 30s, second after 60s, third after 120s — totalling 210s before declaring failure. Between retries, the handler waits the full backoff period (not immediate retry). If the `DISCONNECTED` reason is `NETWORK_TIMEOUT` or `NEONIZE_INTERNAL`, the retry creates a fresh Neonize client instance before attempting reconnect (the old client may have corrupted internal state). If the reason is `SESSION_EXPIRED`, no retry is attempted — the handler immediately transitions to `FAILED` and triggers a `session_expired` notification (SEV1, Discord + Gotify). If the reason is `PROTOCOL_VERSION_MISMATCH`, the handler transitions to `FAILED` with a `protocol_version` notification (SEV0, Discord + Gotify + ping Faiz) because this requires a library update.

On final failure (all retries exhausted or unrecoverable reason), the handler writes `needs_manual_reconnect` flag to Redis (`guinevere:wa:reconnect:needs_manual = "true"`), sends a `reconnect_failed` notification (SEV0: Discord + Gotify + ping Faiz), and stops the retry loop. The WhatsApp subsystem enters degraded mode — API, Discord mirror, and other subsystems continue operating normally (AC-OPS-004). When Faiz manually fixes the issue (re-pair via QR, restart service, update library), he clears the Redis flag and the handler resets to `CONNECTED`.

#### Troubleshooting
- **Issue:** Reconnection handler retries forever (doesn't stop at 3)
  - **Solution:** Verify `MAX_RETRIES = 3` constant and `ctx.attempt >= MAX_RETRIES` check in `_attempt_reconnect()`. The handler must call `_enter_failed()` when `attempt > 3` and set Redis `needs_manual_reconnect` flag. If the loop is driven by an `asyncio.Task`, verify the task is cancelled on `_enter_failed()`.
- **Issue:** `SESSION_EXPIRED` triggers retries instead of immediate failure
  - **Solution:** In `on_disconnected()`, the reason routing must check `DisconnectReason.SESSION_EXPIRED` FIRST before entering the retry loop. Add early return: `if reason == DisconnectReason.SESSION_EXPIRED: await self._enter_failed(ctx, "session_expired"); return`.
- **Issue:** Exhausted retries but no Discord notification received
  - **Solution:** Verify `_enter_failed()` calls `notification_manager.notify_reconnect_failed()`. The notification manager depends on bot being alive — if Discord bot crashed simultaneously, notifications will fail silently. Check that the notification call is wrapped in try/except with `logger.exception()` so the fail state is still written to Redis and PostgreSQL even if notification fails.
- **Issue:** Fresh client creation fails during retry
  - **Solution:** The `neonize_client_factory` callable may fail if credentials are stale. Catch `Exception` in `_attempt_reconnect()`, log the error, increment attempt counter, and continue to next retry. Do NOT transition to FAILED on factory failure — only on actual reconnect failure. Factory failure is a transient error (like NETWORK_TIMEOUT).
- **Issue:** `_categorize_reason()` maps all unknown errors to `UNKNOWN` — causes retry loop on unrecoverable errors
  - **Solution:** Add an `UNKNOWN` handling rule: if an uncategorized error occurs on attempt 3, transition to FAILED with the original error detail. Unknown errors on attempts 1-2 proceed to next retry (conservative — gives system chance to recover from novel error patterns). Log all UNKNOWN categorizations at WARNING level for future pattern addition.
- **Issue:** Rapid disconnect/reconnect cycles overwhelm PostgreSQL with connection events
  - **Solution:** Add a debounce: if a `DISCONNECTED` event occurs within 5 seconds of a previous `CONNECTED` event, increment a "flap counter" in Redis (`guinevere:wa:connection:flap_count`) instead of logging a new PostgreSQL row. If flap count exceeds 5 in 60 seconds, transition to FAILED with reason `UNKNOWN` (flap protection). This prevents database spam during unstable network conditions.

#### Notes
- **Evolution API 515 → 401 Bug Reference:** The Evolution API false logout bug (HTTP 515 from WhatsApp servers misinterpreted as session expired → 401 on next request) is a known failure pattern in Baileys-based libraries. The `_categorize_reason()` method must check for patterns like `"status code: 401"` COMBINED with `"session"` — NOT just any 401. A 401 from a rate-limited request is transient, not a session expiry. Add a secondary check: if the Neonize `authState` shows credentials are still present, treat 401 as `NETWORK_TIMEOUT` (transient) rather than `SESSION_EXPIRED` (permanent). This prevents the false logout bug from triggering unnecessary re-pairing.
- **Fresh Client Per Retry Rationale:** `NEONIZE_INTERNAL` and `NETWORK_TIMEOUT` retries create a new Neonize client instance because the old client may have corrupted internal state (stale auth cache, broken WebSocket, poisoned message queue). The fresh client starts with a clean slate while reusing the same credentials. This is more expensive per retry (client initialization ≈ 2-3 seconds) but avoids phantom errors from stale state.
- **Cross-Reference P11-003:** The NeonizeClient's `DisconnectedEv` must include a `reason` field or raw error string that this handler can consume. If P11-003 only provides a boolean or simple event without reason data, modify P11-003 to attach the underlying error to the event object. The handler cannot categorize without error context.
- **Cross-Reference P11-019:** Notifications follow the SEV matrix defined in P11-019. This handler does NOT create new notification types — it uses the 4 existing types: `connected` (SEV3), `disconnected` (SEV1), `reconnect_failed` (SEV0), `session_expired` (SEV1). The `PROTOCOL_VERSION_MISMATCH` case uses `reconnect_failed` notification type with custom description text indicating library update required.
- **Cross-Reference P11-021:** The `guinevere:wa:connection:state` Redis key is read by the health check service (P11-021) to populate the `whatsapp_connected` Prometheus gauge. The `guinevere:wa:reconnect:attempts` key feeds the `whatsapp_reconnect_attempts_total` Prometheus counter.
- **Degraded Mode Contract (AC-OPS-004):** When reconnection handler is in FAILED state, only WhatsApp message send/receive is blocked. All other Guinevere subsystems (API, Discord, memory, surveillance, financial, cost tracking) continue operating. The `needs_manual_reconnect` Redis flag serves as a circuit breaker — any WhatsApp message send attempt checks this flag first and returns a clean error (`WhatsAppUnavailableError`) instead of crashing.
- **Manual Recovery Path:** Faiz restores WhatsApp by executing one of: (a) `!wa-reconnect` command that clears `needs_manual_reconnect` Redis flag and triggers a fresh connect attempt, (b) systemd restart of `guinevere-whatsapp.service` (P11-022), or (c) QR re-pairing via `!wa-pair` command if session expired. After manual recovery, `on_connected()` resets all state to CONNECTED.
