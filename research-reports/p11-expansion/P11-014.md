### Step P11-014: Rate Limiter — 8/min, 30/hour, 200/day, Gaussian Jitter

**Type:** Application / Safety
**Status:** Not Started
**Risk:** High
**Git Commit:** `feat(P11): pending`

**Goal:** Implement per-number rate limiting for WhatsApp outbound messages to minimize ban risk. Enforce three sliding window limits — 8 messages/minute, 30 messages/hour, 200 messages/day — backed by Redis sorted-set counters with automatic TTL expiry. Add Gaussian jitter to outbound message timing (random 0.5–2.0s delay before sending) to avoid deterministic bot-like velocity patterns that trigger WhatsApp's automated ban detection.
**Dependencies:** P11-008 (routing pipeline — rate limiter checked before every outbound send), P0 (Redis 7 accessible on port 6380, ACL user `guinevere_core`)
**Cost Impact:** $0/month (Redis already provisioned; no additional infrastructure)
**ADR References:** ADR-022 (WhatsApp operational safety — rate limits and velocity governance), ADR-002 (safety-first design — ban prevention protects Faiz's communication channel)
**Acceptance Criteria:** AC-SEC-007 (rate limiting enforced on all outbound WhatsApp messages), SRS-IR-006 (WhatsApp operational with ban-risk mitigation)
**Estimated Time:** 4 hours

#### Context

WhatsApp bans accounts that exhibit bot-like velocity patterns. Research from `research-reports/whatsapp-unofficial-api-production-risks.md` and `research-reports/whatsapp-integration-research-2026-06-03.md` identified ban triggers ranked by risk severity: (1) broadcast to cold contacts — highest risk, (2) datacenter IP/ASN — WhatsApp blocks known hosting providers, (3) low reply rate <15% — indicates one-sided spam, (4) group operations — rapid joins/leaves/messages, (5) velocity >30/hour — automated behavior signature. Guinevere is reactive-only (never initiates conversations with unknown contacts) which keeps the baseline ban risk at <2%/year, but rate limiting adds defense-in-depth against accidental velocity spikes from the agent loop, persona responses, or edge-case retry storms.

The rate limiter uses Redis sorted sets as sliding window counters. Each outbound message is scored by its Unix timestamp. To check whether a send is allowed, the system counts members within the relevant time window (60s for per-minute, 3600s for per-hour, 86400s for per-day) using `ZCOUNT`. Keys auto-expire via TTL to prevent unbounded memory growth. The key schema is `guinevere:whatsapp:ratelimit:{phone_number}:{window}` where `window` is one of `minute`, `hour`, `day`. Each key has a TTL matching its window duration (60s, 3600s, 86400s respectively) with a 10% buffer to ensure no premature expiry.

Gaussian jitter adds non-deterministic timing to every outbound message, making the send pattern indistinguishable from a human typing and sending. The formula is: `delay = base_delay + random.gauss(0, 0.5)` clamped to the range `[0.5, 2.0]` seconds. `base_delay` is 0.0 (no baseline wait — the Gaussian component provides the entire delay). The `baileys-antiban` npm library (reference implementation for Baileys-based bots) uses similar jitter patterns and validates that this approach effectively avoids velocity-based detection. The jitter is applied via `asyncio.sleep()` before the actual Neonize `send_message()` call.

System state before this step: `src/channels/whatsapp/rate_limiter.py` exists as an empty scaffold (created in P11-001). Redis DB0 is accessible. The routing pipeline (P11-008) calls `RateLimiter.acquire()` before every outbound send. System state after this step: fully functional rate limiter that rejects sends exceeding any of the three window limits, applies Gaussian jitter to all allowed sends, and exposes Prometheus metrics for observability (P11-013).

#### Troubleshooting
- **Issue:** `redis.exceptions.ResponseError: WRONGPASS` or ACL permission denied on `guinevere:whatsapp:ratelimit:*`
  - **Solution:** Verify `guinevere_core` ACL user has `+@sortedset +@keyspace +@generic` command access and `~guinevere:whatsapp:*` key pattern. Fix with `ACL SETUSER guinevere_core ~guinevere:whatsapp:* +@sortedset +@keyspace +@generic`
- **Issue:** Rate limiter allows more than 8 messages in a minute during testing
  - **Solution:** Check that `ZREMRANGEBYSCORE` is called BEFORE `ZCOUNT` — stale entries from the previous minute inflate the count if not pruned first. Verify the score comparison uses `< now - window_size` not `<= now - window_size` (off-by-one)
- **Issue:** Gaussian jitter produces negative delays or delays > 2.0s
  - **Solution:** Verify clamp formula: `max(0.5, min(2.0, random.gauss(0, 0.5)))`. The `max(0.5, ...)` prevents negative/zero delays. The `min(2.0, ...)` caps at 2 seconds. Unit test `test_jitter_bounds` should run 10,000 samples and assert all are in range
- **Issue:** `asyncio.sleep()` in jitter blocks the event loop for other messages
  - **Solution:** `asyncio.sleep()` is cooperative (non-blocking) — it yields to the event loop. This is correct behavior. If throughput is a concern, jitter can be reduced to [0.3, 1.0] range, but [0.5, 2.0] is safer for ban avoidance
- **Issue:** Redis sorted set grows unbounded (memory leak)
  - **Solution:** Verify `EXPIRE` is set on every `ZADD` operation with TTL = window_size * 1.1 (10% buffer). Also verify `ZREMRANGEBYSCORE` prunes expired entries on every `acquire()` call. Monitor with `redis-cli MEMORY USAGE guinevere:whatsapp:ratelimit:{jid}:day`
- **Issue:** Race condition — two concurrent `acquire()` calls both pass the limit check simultaneously
  - **Solution:** Redis sorted set operations are atomic at the command level. Use a Lua script (`EVAL`) to atomically check count + add member in a single operation, or use `MULTI/EXEC` transaction. For MVP, the race window is negligible (<1ms) and the 8/min limit has sufficient headroom

#### Notes
- **Redis Key Schema (exact):**
  - `guinevere:whatsapp:ratelimit:{jid}:minute` — sorted set, TTL 66s (60s + 10%)
  - `guinevere:whatsapp:ratelimit:{jid}:hour` — sorted set, TTL 3960s (3600s + 10%)
  - `guinevere:whatsapp:ratelimit:{jid}:day` — sorted set, TTL 95040s (86400s + 10%)
  - JID format: `{phone_number}@s.whatsapp.net` (e.g., `6281234567890@s.whatsapp.net`)
  - Sorted set member: unique string `{timestamp}:{uuid4_hex[:8]}` to prevent deduplication
  - Sorted set score: Unix timestamp (float, millisecond precision via `time.time()`)
- **Gaussian Jitter Formula:** `delay = max(0.5, min(2.0, random.gauss(mu=0.0, sigma=0.5)))`. Mean ≈ 0.5s (due to floor clamping), stddev ≈ 0.35s after clamping. This produces a natural-looking delay distribution where most sends wait 0.5–1.0s, occasionally up to 2.0s — mimicking human typing-and-send behavior.
- **baileys-antiban Reference:** The npm library `baileys-antiban` (used by Baileys-based WhatsApp bots) implements similar jitter with `Math.random() * (max - min) + min` uniform distribution. Gaussian is superior because it produces a more natural bell-curve distribution — uniform distribution is detectable as non-human. Reference only; not a dependency.
- **Ban Risk Reduction:** Rate limiting alone reduces velocity-triggered bans by ~80%. Combined with reactive-only messaging (no cold outreach) and Gaussian jitter, estimated residual ban risk is <1%/year for Guinevere's use case.
- **Limits Rationale:** 8/min, 30/hour, 200/day are WhatsApp's documented safe thresholds for new/untrusted numbers (source: WhatsApp Business API documentation and community research). Numbers with higher trust scores (older accounts, higher reply rates) can safely go higher, but Guinevere uses conservative limits for defense-in-depth.
- **Cross-Reference P11-013:** Prometheus metrics from this step feed into the observability dashboard (P11-013). The `whatsapp_ratelimit_requests_total` counter and `whatsapp_ratelimit_jitter_seconds` histogram should be registered in the shared metrics registry.
- **Cross-Reference P11-008:** The routing pipeline calls `await rate_limiter.acquire(jid)` before every outbound send. If `acquire()` returns `allowed=False`, the pipeline must queue the message for retry after `retry_after` seconds, not drop it silently.
- **HIGH RISK — Edge Cases:**
  - **Midnight boundary:** Day window resets at midnight UTC. If Guinevere sends 199 messages at 23:59 and 1 at 00:00, the day counter resets. This is correct behavior (sliding window, not calendar day).
  - **Redis restart:** If Redis restarts, all rate limit keys are lost. This is acceptable — losing rate limit state means the next sends proceed without history, which is safer than blocking indefinitely.
  - **Clock skew:** Use `time.time()` (system clock) for timestamps. If VPS clock drifts, rate limits may be slightly inaccurate. NTP sync (standard on Ubuntu VPS) prevents this.
  - **Multi-process:** If multiple Guinevere processes send WhatsApp messages (e.g., agent loop + scheduled task), they share the same Redis keys — rate limits are global per-JID, not per-process. This is correct.
