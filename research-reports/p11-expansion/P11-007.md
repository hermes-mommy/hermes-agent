### Step P11-007: Conversation Context Manager — 10-Message Sliding Window, Shared Memory

**Type:** Application / Data Layer
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P11): pending`

**Goal:** Implement `ContextManager` that maintains a 10-message sliding window of conversation history per channel, backed by PostgreSQL. Cross-channel shared memory pool — WhatsApp and Discord conversations contribute to the same memory (Guinevere remembers across channels). Context is injected into LLM prompts as conversation history. Long-term memory recall uses the existing `recall_memories()` pipeline from P3.
**Dependencies:** P3 (Memory system — `src/memory/` with `recall_memories()`, `write_pipeline`, `embeddings` functional), P11-006 (ConversationalAgent — `src/agent/conversational_agent.py` exists and accepts context parameter)
**Cost Impact:** $0/month (uses existing PostgreSQL instance + existing memory system)
**ADR References:** ADR-004 (Memory Architecture — PostgreSQL for persistent storage, Redis for cache), ADR-006 (Data Classification — conversation data = INTERNAL classification level), ADR-022 (shared memory across channels — WhatsApp and Discord contribute to the same memory pool)
**Acceptance Criteria:** AC-MEM-001 (conversation context maintained — last 10 messages available for LLM prompt injection), AC-CORE-003 (cross-channel memory — WhatsApp conversation visible when Faiz talks on Discord), SRS-IR-009 (message dedup — content_hash prevents duplicate storage)
**Estimated Time:** 5 hours

#### Context

Faiz wants Guinevere to remember conversations across Discord and WhatsApp. If Faiz discusses something on WhatsApp in the morning, Guinevere should reference it when Faiz talks on Discord in the evening. This cross-channel memory is a core differentiator from a simple chatbot — it makes Guinevere a persistent companion that knows Faiz's context regardless of which interface he uses. The `ContextManager` is the component that enables this.

The `ContextManager` has two responsibilities that work together: (1) SHORT-TERM context — a 10-message sliding window per channel that is injected directly into each LLM call as conversation history. This gives the LLM immediate conversational awareness (what was just said). (2) LONG-TERM memory integration — when a conversation turn is stored, it is also written to the existing memory pipeline (`src/memory/write_pipeline.py`) so that `recall_memories()` can surface relevant past conversations from any channel. This gives the LLM deep contextual awareness (what Faiz talked about last week on WhatsApp).

The PostgreSQL schema adds a new `conversations` table that stores every conversation turn with metadata: `channel_type` (which channel), `sender_id` (who said it), `content` (what was said), `content_hash` (for deduplication), `role` (user vs assistant), `response_to_id` (for threading), and `created_at` (for time-ordering and sliding window queries). All conversation data is classified as INTERNAL per ADR-006. The table uses TimescaleDB hypertable partitioning by `created_at` for efficient time-range queries (the sliding window is a time-based query).

The 10-message sliding window is queried per-channel (last 10 messages from WhatsApp when responding on WhatsApp, last 10 from Discord when responding on Discord). However, the long-term memory recall is cross-channel — `recall_memories()` searches the entire memory pool regardless of which channel the memory originated from. This means the LLM sees: (a) the last 10 messages from the CURRENT channel as conversation history, and (b) relevant memories from ALL channels as contextual background. This design gives natural conversation flow on the current channel while maintaining cross-channel awareness.

    Responsibilities:
    1. Store conversation turns in PostgreSQL (conversations table)
    2. Retrieve last N messages per channel (sliding window for LLM prompt)
    3. Write to long-term memory pipeline (recall_memories integration)
    4. Deduplicate via content_hash
    5. Optional Redis cache for hot sliding window data
    """

    def __init__(self, db_session, memory_writer=None, redis_client=None):

        self._memory_writer = memory_writer
        self._redis = redis_client

        2. Check for duplicate (content_hash exists) -> skip if dup (SRS-IR-009)

        4. INSERT assistant response into conversations table (response_to_id -> user turn)

        6. Invalidate Redis cache for this channel's sliding window
        7. Return (user_turn_id, assistant_turn_id)

#### Troubleshooting
- **Issue:** `alembic upgrade head` fails with "relation conversations already exists"
  - **Solution:** A previous partial migration may have created the table. Drop it manually: `psql -c "DROP TABLE IF EXISTS conversations CASCADE" guinevere`, then re-run `alembic upgrade head`.
- **Issue:** TimescaleDB `create_hypertable` fails because table already has data
  - **Solution:** TimescaleDB requires the table to be empty when converting to hypertable (unless using `migrate_data => true`). Ensure migration runs on a clean table, or use: `SELECT create_hypertable('conversations', 'created_at', chunk_time_interval => INTERVAL '1 week', migrate_data => true)`.
- **Issue:** Sliding window query is slow (>100ms) on large conversation history
  - **Solution:** Verify `idx_conversations_channel_time` index exists. If table has >100K rows, consider adding a composite index: `(sender_id, channel_type, created_at DESC)`. TimescaleDB chunk exclusion should skip old chunks automatically.
- **Issue:** `content_hash` unique constraint causes insert failures for legitimate repeated messages (e.g., Faiz sends "ok" multiple times)
  - **Solution:** Include `timestamp` in the hash computation so that "ok" sent at different times produces different hashes. The hash should be `SHA-256(sender_id + content + timestamp_iso)` — this allows the same content at different times but prevents exact duplicates (same content, same timestamp, same sender).
- **Issue:** Redis cache returns stale data after `store_turn()`
  - **Solution:** Ensure cache invalidation happens atomically with the database insert. Use `DELETE guinevere:context:{channel}:{sender}:window` immediately after `store_turn()` completes. Do not use TTL-based expiry as the sole invalidation strategy.
- **Issue:** `format_context_for_prompt()` produces output exceeding LLM context window
  - **Solution:** The sliding window is capped at 10 messages by design. If individual messages are very long (>500 chars), truncate content in the prompt format to first 300 chars with "...(truncated)" suffix. Total prompt context from history should not exceed 4000 tokens.

#### Notes
- The `conversations` table is the SINGLE source of truth for conversation history across ALL channels. Every channel adapter's messages end up here. This is the mechanism that enables cross-channel memory (ADR-022).
- The 10-message sliding window is SHORT-TERM context — it's injected directly into the LLM prompt for immediate conversational awareness. LONG-TERM context comes from `recall_memories()` which searches the entire memory pool using embedding similarity. These two layers work together: sliding window = "what we just talked about", recall = "what we've talked about before that's relevant now".
- Per-channel sliding window means: when responding on WhatsApp, the LLM sees the last 10 WhatsApp messages. When responding on Discord, the LLM sees the last 10 Discord messages. But the long-term recall is cross-channel — memories from WhatsApp can surface when responding on Discord.
- Message deduplication (SRS-IR-009) uses `content_hash` with `UNIQUE` constraint. If Faiz sends the exact same message at the exact same timestamp from the same channel (e.g., duplicate delivery due to network issue), the second insert is silently ignored via `ON CONFLICT DO NOTHING`.
- All conversation data is classified as INTERNAL per ADR-006. Message content is stored in PostgreSQL but NEVER logged to application logs or Loki — only metadata (timestamp, channel, direction) appears in logs.
- Cross-reference P11-006 for how `ContextManager.get_context()` feeds into `ConversationalAgent.process()`. Cross-reference P11-005 for how `WhatsAppAdapter` triggers `store_turn()` via the routing pipeline.
- The `session_id` field groups related conversation turns into sessions. A new session starts after 30 minutes of inactivity. This enables future analytics ("how many conversations per day") without affecting the sliding window logic.
- TimescaleDB 1-week chunk interval is appropriate for conversation data (~50-200 messages/day expected). Chunks older than 90 days can be compressed via TimescaleDB compression policy for storage efficiency.
