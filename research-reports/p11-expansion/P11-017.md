### Step P11-017: Number Whitelist + Access Control

**Type:** Application / Security
**Status:** Not Started
**Risk:** High
**Git Commit:** `feat(P11): pending`

**Goal:** Implement WhatsApp number whitelist enforcing Faiz-only access for MVP. Only messages from whitelisted phone numbers are processed by the routing pipeline. Non-whitelisted senders are silently ignored — no response, no acknowledgment, no error message, no typing indicator. This prevents both unauthorized access (security) and ban risk from responding to unknown contacts (WhatsApp reply rate is a ban trigger). Whitelist stored in Redis set at `guinevere:whatsapp:whitelist`. Admin commands `!whitelist-add`, `!whitelist-remove`, `!whitelist-list` stubbed for future multi-user support.
**Dependencies:** P11-008 (routing pipeline — whitelist check is the first gate in the pipeline, before consent/HARD STOP/rate limit), P0 (Redis 7 accessible on port 6380)
**Cost Impact:** $0/month (Redis already provisioned; Redis sets are O(1) memory for small whitelist)
**ADR References:** ADR-022 (identity binding — cross-channel identity binding must be documented), ADR-002 (access control — Faiz-only operator), SRS-IR-010 (Faiz-only identity binding for WhatsApp channel)
**Acceptance Criteria:** SRS-IR-010 (only Faiz's phone number processed — all other senders silently dropped), AC-SEC-001 (access control enforced at message intake level)
**Estimated Time:** 2 hours

#### Context

WhatsApp is fundamentally more exposed than Discord. Discord operates within a private server where only members can send messages — server membership provides a natural access control boundary. WhatsApp operates on phone-number-based addressing with no server isolation: anyone who has Faiz's phone number (or discovers it) can send messages directly to the connected WhatsApp account. This creates two risks: (1) security risk — unauthorized persons could interact with Guinevere and potentially extract information, trigger actions, or manipulate persona behavior; (2) ban risk — responding to unknown contacts lowers WhatsApp's calculated reply rate, which is a known ban trigger (reply rate <15% flags the account as spam-like).

The whitelist approach solves both risks simultaneously. By silently dropping all non-whitelisted messages — no response at all, not even "this number is not authorized" — Guinevere avoids any interaction pattern that WhatsApp's automated detection could flag as suspicious. A "not authorized" response to unknown senders would still count as a reply, maintaining the reply rate, but it also signals that the number is active and automated, which could attract more unwanted messages. Silent drop is the safest approach.

The whitelist is stored as a Redis set at `guinevere:whatsapp:whitelist` containing JID (Jabber ID) strings in the format `{phone_number}@s.whatsapp.net` (e.g., `6281234567890@s.whatsapp.net`). Redis sets provide O(1) `SISMEMBER` lookups — checking whitelist membership adds negligible latency to the routing pipeline. The initial whitelist contains exactly one entry: Faiz's phone number, set during P11-002 setup or via the `!whitelist-add` admin command after deployment. Admin commands (`!whitelist-add <jid>`, `!whitelist-remove <jid>`, `!whitelist-list`) are stubbed in this step for future multi-user support but restricted to Faiz-only execution via sender ID authentication.

System state before: WhatsApp adapter (P11-008) processes all incoming messages regardless of sender. System state after: whitelist check is the FIRST gate in the routing pipeline, non-whitelisted senders receive zero response, and the whitelist is manageable via admin commands.

#### Troubleshooting
- **Issue:** Faiz's messages are being silently dropped (whitelist not seeded)
  - **Solution:** Verify whitelist contains Faiz's JID: `redis-cli -p 6380 --user guinevere_core -a "$REDIS_PASSWORD" SISMEMBER guinevere:whatsapp:whitelist "FAIZ_JID_HERE"`. If returns 0, seed the whitelist: `redis-cli -p 6380 --user guinevere_core -a "$REDIS_PASSWORD" SADD guinevere:whatsapp:whitelist "FAIZ_JID_HERE"`. Verify JID format — must be `{digits}@s.whatsapp.net` with no `+`, spaces, or dashes.
- **Issue:** JID format mismatch — Neonize provides JID in different format than expected
  - **Solution:** Log the raw sender JID from Neonize `MessageEv` event: `logger.debug("raw_sender_jid", jid=event.sender)`. Compare with expected format. Neonize/whatsmeow may use `:{device}` suffix (e.g., `6281234567890:1@s.whatsapp.net` for multi-device). Strip the device suffix before whitelist comparison: `jid.split(":")[0] + "@s.whatsapp.net"`.
- **Issue:** Group messages trigger consent prompts or errors instead of silent drop
  - **Solution:** Whitelist check MUST be the first gate. Group JIDs use `@g.us` domain (e.g., `1234567890-1234567890@g.us`). The whitelist only contains `@s.whatsapp.net` JIDs, so group messages are automatically dropped. Verify group JID domain is not accidentally added to whitelist.
- **Issue:** `!whitelist-add` command adds malformed JID
  - **Solution:** Validate JID format with regex `^\d{10,15}@s\.whatsapp\.net$` before adding. Reject and respond with error message if invalid: "Invalid JID format. Expected: {phone_number}@s.whatsapp.net (10-15 digits)."
- **Issue:** Redis set grows unexpectedly (someone added many JIDs)
  - **Solution:** For MVP, whitelist should contain exactly 1 member (Faiz). Monitor with Prometheus gauge `whatsapp_whitelist_size`. Alert if size > 5. Admin commands are Faiz-only — unauthorized additions are impossible if auth is correctly implemented. Check `!whitelist-list` output for unexpected entries.
- **Issue:** Whitelist check adds noticeable latency to message processing
  - **Solution:** Redis `SISMEMBER` is O(1) and typically completes in <0.1ms on localhost. If latency is observed, check Redis connection pooling — each `is_whitelisted()` call should reuse a pooled connection, not create a new one. Verify Redis is on localhost (not remote) for sub-millisecond latency.

#### Notes
- **JID Format (exact):**
  - Standard 1:1 chat: `{phone_number}@s.whatsapp.net`
  - Phone number: country code + subscriber number, digits only, no `+`, no spaces, no dashes
  - Indonesian mobile: `62` (country) + `8xx` (mobile prefix) + subscriber number
  - Example: `6281234567890@s.whatsapp.net` (13 digits total before `@`)
  - Multi-device suffix (whatsmeow): `:{device_id}` appended before `@` — must be stripped for whitelist comparison
  - Group JIDs: `{creator}-{timestamp}@g.us` — different domain, NOT whitelisted
  - Broadcast JIDs: `status@broadcast` — different domain, NOT whitelisted
  - Validation regex: `^\d{10,15}@s\.whatsapp\.net$`
- **Silent Drop Behavior (exact):**
  - Incoming message from non-whitelisted sender arrives at Neonize event handler
  - `WhitelistManager.is_whitelisted(sender_jid)` returns `False`
  - Adapter handler returns immediately — no further processing
  - NO response message sent (not "unauthorized", not "busy", not anything)
  - NO typing indicator shown (Neonize `send_chatstate` not called)
  - NO read receipt sent (Neonize `mark_read` not called — though read receipts may be automatic at protocol level)
  - Message content NOT logged (privacy — unknown sender's message is not Guinevere's data)
  - Sender JID logged at INFO level for observability: `logger.info("whatsapp_whitelist_drop", sender=jid)`
  - Prometheus counter incremented: `whatsapp_whitelist_drops_total`
- **Redis Key Schema (exact):**
  - Key: `guinevere:whatsapp:whitelist` (set type, no TTL — permanent)
  - Members: JID strings (e.g., `6281234567890@s.whatsapp.net`)
  - Initial members: 1 (Faiz's JID only)
  - Maximum practical members: ~100 (Redis sets handle millions, but MVP scope is small)
- **Admin Commands (stubbed for future):**
  - `!whitelist-add {jid}` — adds JID to set, requires Faiz sender auth
  - `!whitelist-remove {jid}` — removes JID from set, requires Faiz sender auth
  - `!whitelist-list` — returns all whitelisted JIDs, requires Faiz sender auth
  - These commands are implemented as command handlers in the WhatsApp adapter, parsed before message forwarding to the agent loop
  - Non-Faiz senders: commands ignored (treated as regular message → dropped by whitelist)
- **Cross-Reference P11-008:** Whitelist check is the FIRST gate in the routing pipeline. The pipeline order is: (1) whitelist (this step) → (2) consent (P11-016) → (3) HARD STOP (P11-015) → (4) safe word (P11-016) → (5) rate limiter (P11-014) → (6) message processing. Whitelist first ensures non-authorized senders never trigger downstream safety mechanisms or consent prompts.
- **Cross-Reference P11-016:** Consent check (P11-016) only runs for whitelisted senders. Non-whitelisted senders never see the consent prompt — they get silent drop.
- **Ban Risk Mitigation:** Responding to unknown contacts lowers WhatsApp's calculated reply rate, which is a ban trigger (<15% reply rate flags the account). Silent drop maintains a 100% reply rate for whitelisted conversations and 0% interaction with unknown senders — the cleanest possible profile.
- **HIGH RISK — Edge Cases:**
  - **Faiz changes phone number:** New JID must be added to whitelist before the old JID is removed. If old JID is removed first, Faiz is locked out of WhatsApp. Mitigation: Discord channel remains available for `!whitelist-add` commands.
  - **Neonize device suffix:** whatsmeow appends `:{device_id}` to JIDs for multi-device support. The whitelist stores base JIDs (no device suffix). The adapter must strip the device suffix before comparison: normalize `6281234567890:1@s.whatsapp.net` → `6281234567890@s.whatsapp.net`.
  - **Redis unreachable during whitelist check:** Default to deny (drop the message). Log error: `logger.error("whitelist_redis_unreachable", ...)`. This is deny-by-default — safer than allowing all messages when Redis is down.
  - **WhatsApp voice/video calls from non-whitelisted:** Neonize may fire a `CallEv` event. The whitelist check should also apply to call events — silently reject/ignore calls from non-whitelisted senders. Verify Neonize's call event API and add call rejection to the whitelist gate.
  - **Message from whitelisted sender in a group context:** If Faiz adds Guinevere to a group, group messages arrive with the group JID as sender (`@g.us`), not individual JIDs. These are dropped (not whitelisted). This is correct for MVP — group support is out of scope.
