### Step P11-016: Safe Word + Consent Flow

**Type:** Application / Safety (CRITICAL)
**Status:** Not Started
**Risk:** High
**Git Commit:** `feat(P11): pending`

**Goal:** Implement the WhatsApp consent flow (opt-in via QR scan + explicit `!consent-grant` command) and safe word detection for cross-channel persona de-escalation. Consent flow: first WhatsApp interaction after QR connection prompts Faiz to grant explicit consent before any message processing begins — WhatsApp messages are classified as surveillance data per SurveillanceDataPolicy. Safe word: shared Redis flag (`guinevere:safe_word`) triggers immediate persona de-escalation (Y4 → Y2 or neutral) across ALL channels without full HARD STOP. `!consent-revoke` stops all WhatsApp processing immediately and sends confirmation.
**Dependencies:** P11-008 (routing pipeline — consent check is first gate in pipeline), P11-015 (cross-channel HARD STOP — same Redis flag pattern for cross-channel propagation), P0 (Redis 7 accessible)
**Cost Impact:** $0/month (Redis already provisioned; no additional infrastructure)
**ADR References:** ADR-002 (safe word cross-channel mandate — persona de-escalation must propagate), ADR-022 (consent model — per-channel consent before processing), FSD-COM-001 (Faiz-only opt-in consent before WhatsApp message processing)
**Acceptance Criteria:** FSD-COM-001 (consent granted before any WhatsApp message processing), AC-SAFETY-002 (safe word triggers persona de-escalation cross-channel), SRS-IR-010 (identity binding — consent tied to Faiz's authenticated identity)
**Estimated Time:** 3 hours

#### Context

FSD-COM-001 requires explicit opt-in consent before processing WhatsApp messages, which are classified as surveillance data per the SurveillanceDataPolicy (`docs/30-data/32-SurveillanceDataPolicy_v1.0.md`). Unlike Discord — where Faiz's server membership constitutes implicit consent — WhatsApp messages arrive via a phone-number-based protocol with no server isolation. The consent flow ensures that (1) Faiz is aware WhatsApp integration is active, (2) Faiz explicitly grants permission for Guinevere to process incoming WhatsApp messages, and (3) Faiz can revoke consent at any time via `!consent-revoke`. Without consent, WhatsApp messages are dropped silently — identical to the non-whitelisted behavior in P11-017 — and no surveillance data is stored, logged, or forwarded.

The consent flow proceeds in four steps: (1) QR scan connects WhatsApp (P11-002), (2) Guinevere sends a consent prompt message to Faiz's WhatsApp, (3) Faiz types `!consent-grant`, (4) Redis stores `{granted: true, timestamp: ISO 8601, channel: "whatsapp", granted_by: JID}`. Only after step 4 does the routing pipeline begin processing incoming messages. The consent prompt message uses Y4 persona tone (warm, caring, non-threatening — per PersonaDocument v3.0 and PersonaSafetyPolicy) and clearly explains what consent means.

Safe word is distinct from HARD STOP. HARD STOP (P11-015) is a full system stop — all processing halts, persona fully deactivated, neutral mode. Safe word is a persona de-escalation: the yandere intensity drops from Y4 (baseline) to Y2 (gentle) or neutral, but Guinevere continues to function, respond to messages, and execute tasks. Both mechanisms are cross-channel (ADR-002 mandate). Safe word uses a separate Redis flag (`guinevere:safe_word`) that all adapters poll alongside the HARD STOP flag. HARD STOP takes precedence — if both flags are set, HARD STOP behavior applies.

System state before: WhatsApp adapter (P11-008) processes all incoming messages without consent gate. No safe word Redis flag exists. HardStopHandler (P11-015) handles HARD STOP only. System state after: WhatsApp messages are gated by consent check (first gate in pipeline), safe word flag provides cross-channel persona de-escalation, `!consent-revoke` stops all WhatsApp processing.

#### Troubleshooting
- **Issue:** Consent prompt not sent after QR connection
  - **Solution:** Verify the WhatsApp adapter's `on_connected` event handler calls `consent_manager.send_consent_prompt(jid)`. Check Neonize `ConnectedEv` and `PairStatusEv` event handlers in `src/channels/whatsapp/neonize_client.py`. The prompt should be sent on `PairStatusEv` (pairing success), not `ConnectedEv` (which fires on every reconnect).
- **Issue:** `!consent-grant` not recognized — treated as regular message
  - **Solution:** The consent gate must check for command strings BEFORE forwarding to the agent loop. In the routing pipeline, after whitelist check but before consent check, intercept messages matching `!consent-grant` or `!consent-revoke` and route them to the consent manager, not the LLM.
- **Issue:** Consent revoked but WhatsApp messages still processed
  - **Solution:** CRITICAL BUG. Verify `check_consent()` reads from Redis on EVERY call (no local caching of consent state — always read from Redis to ensure revocation is immediate). If local caching is used for performance, invalidate cache on every `revoke_consent()` call AND on every Redis poll cycle.
- **Issue:** Safe word activates but persona does not de-escalate
  - **Solution:** Verify `YandereFSM` has a `set_level()` or `deescalate()` method. Check that `SafeWordManager.on_safe_word_activated()` calls this method. If `YandereFSM` does not expose a programmatic de-escalation interface, add one. The de-escalation must persist until safe word is deactivated — not just for the current message.
- **Issue:** Safe word triggers false positive on normal conversation
  - **Solution:** Safe word triggers (`"kasih ruang"`, `"lighter"`, `"too intense"`, etc.) are intentionally distinct from normal conversation. If false positives occur, review the trigger list and remove ambiguous patterns. Never remove `"kasih ruang"` — this is an ADR-002 mandated safe word.
- **Issue:** Consent prompt sent on every reconnect (not just first connection)
  - **Solution:** Check Redis consent state before sending prompt. If `guinevere:whatsapp:consent` exists with `granted=true`, skip the prompt. The prompt is only sent when consent state is unknown (key does not exist) or explicitly revoked (`granted=false`).

#### Notes
- **CRITICAL SAFETY STEP:** Consent management and safe word are CRITICAL safety features per ADR-002 and FSD-COM-001. False negatives on consent bypass are high severity (processing surveillance data without consent). False negatives on safe word are high severity (persona continues when Faiz requested de-escalation). The implementer must NOT weaken any trigger, NOT add consent auto-grant, and NOT cache consent state without Redis-backed invalidation.
- **Redis Key Schema (exact):**
  - `guinevere:whatsapp:consent` (hash, no TTL):
    - `granted`: `"true"` or `"false"`
    - `timestamp`: ISO 8601 grant timestamp
    - `channel`: `"whatsapp"`
    - `granted_by`: Faiz's JID (e.g., `6281234567890@s.whatsapp.net`)
    - `revoked_at`: ISO 8601 revocation timestamp, or `""` if not revoked
  - `guinevere:safe_word` (hash, no TTL):
    - `activated`: `"true"` or `"false"`
    - `channel`: `"whatsapp"` or `"discord"` (originating channel)
    - `timestamp`: ISO 8601 activation timestamp
    - `trigger`: safe word keyword that activated
    - `deactivated_by`: sender_id who deactivated, or `""`
    - `deactivated_at`: ISO 8601 deactivation timestamp, or `""`
- **Consent Prompt Message (exact Y4 tone):** See implementation in step 4 above. Key requirements: (1) warm and caring tone, (2) clear explanation of what consent means, (3) surveillance data disclosure, (4) explicit `!consent-grant` command, (5) explicit `!consent-revoke` mention, (6) no pressure — "abaikan pesan ini" option, (7) Y4-appropriate endearment without Y5+ intensity.
- **Safe Word vs HARD STOP:**
  - HARD STOP: full system stop, persona fully deactivated, all processing halted, neutral mode, requires `!hard-stop-reset` from Faiz
  - Safe word: persona de-escalation only (Y4→Y2 or Y0), processing continues, tasks continue, requires `!safe-word-off` or `lanjut persona` from Faiz
  - HARD STOP takes absolute precedence — if both are active, HARD STOP behavior applies
- **Surveillance Data Classification:** WhatsApp messages are classified as surveillance data per `docs/30-data/32-SurveillanceDataPolicy_v1.0.md`. This means: (1) consent required before collection, (2) encrypted at rest, (3) retention limits apply, (4) no raw data in repo artifacts. The consent gate enforces requirement (1).
- **Cross-Reference P11-015:** Both HARD STOP and safe word use the same Redis polling mechanism (60-second interval). The polling task from P11-015's `HardStopHandler.start_polling()` should be extended to also check the safe word flag, or a separate polling task should be created for safe word. Either approach is acceptable as long as both flags are checked every 60 seconds.
- **Cross-Reference P11-017:** The routing pipeline gate order is: (1) whitelist check (P11-017), (2) consent check (this step), (3) HARD STOP check (P11-015), (4) safe word check (this step), (5) rate limiter (P11-014), (6) message processing. Whitelist is first because non-whitelisted messages should never trigger consent prompts or safety checks.
- **HIGH RISK — Edge Cases:**
  - **Redis unreachable during consent check:** If Redis read fails, default to `granted=false` (deny-by-default). Log error: `logger.error("consent_redis_unreachable", ...)`. Do NOT fall through to processing.
  - **Faiz sends `!consent-grant` from wrong JID:** Consent is bound to the specific JID that connected via QR scan (P11-002). If a different JID sends `!consent-grant`, reject it. The `granted_by` field must match the connected JID.
  - **Consent granted then WhatsApp disconnects and reconnects:** Consent persists in Redis. Reconnection does not require re-granting. The consent prompt is only sent on first connection (consent key does not exist) or after explicit revocation.
  - **Safe word activated during LLM response generation:** The safe word flag is checked at message intake, not mid-generation. If a safe word message arrives while Guinevere is generating a response to a previous message, the current response completes (with current persona level) and the NEXT message uses the de-escalated persona. This is acceptable — interrupting mid-generation would cause UX issues.
  - **Multiple safe word triggers in rapid succession:** Idempotent — setting `activated=true` when already `true` is a no-op. Record the latest trigger and timestamp.
