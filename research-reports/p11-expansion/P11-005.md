#### Context

The `WhatsAppAdapter` is the bridge between Neonize's event-driven API and Guinevere's unified channel layer. Neonize (pure Python wrapper around whatsmeow Go library) provides message events via async callbacks with JID-based addressing (`628123456789@s.whatsapp.net`). The adapter must translate these WhatsApp-native events into `UnifiedMessage` objects that the ConversationalAgent (P11-006) can process without knowing the source channel. This is the first concrete `ChannelAdapter` implementation and serves as the reference implementation for future adapters (Gmail, X, Wearable).

Incoming message handling follows a strict pipeline: (1) receive Neonize message event, (2) extract sender JID and validate against whitelist (Faiz's number only — SRS-IR-010), (3) check if message contains media and reject with acknowledgment text if so (SRS-IR-007), (4) convert text content to `UnifiedMessage` with proper `channel_type=ChannelType.WHATSAPP`, (5) compute `content_hash` for deduplication (SRS-IR-009), (6) pass to the routing pipeline (P11-008). Any message from a non-whitelisted JID is silently ignored and logged at metadata level only (no content logged per logging policy).

Outgoing message handling reverses the flow: (1) receive response string from ConversationalAgent, (2) check if response exceeds 1000 characters and split into multiple bubbles if needed, (3) send typing indicator (`client.send_chat_presence(to=jid, presence="composing")`) before each chunk with appropriate delay, (4) send each chunk via `NeonizeClient.send_message()`, (5) mark the originating message as read (read receipt). The 1000-character split limit is below WhatsApp's 65,536 character message limit to ensure comfortable reading on mobile devices.

Ban risk is a real concern when using unofficial WhatsApp APIs from datacenter IPs. The adapter enforces WhatsApp's native rate limits (8 messages/minute, 30/hour, 200/day) with Gaussian jitter on response timing to avoid velocity-based detection patterns. The adapter is reactive-only — it never initiates messages to unknown contacts. These mitigations are implemented via the rate limiter module (`src/channels/whatsapp/rate_limiter.py` from P11-003) which the adapter consults before every outgoing message.

#### Troubleshooting
- **Issue:** `TypeError: Can't instantiate abstract class WhatsAppAdapter with abstract methods send_message`
  - **Solution:** Ensure ALL abstract methods from `ChannelAdapter` are implemented with matching signatures. Check `async` vs sync consistency — if base is `async`, adapter must be `async`.
- **Issue:** Neonize message event has no `.Chat` or `.GetBody()` attributes
  - **Solution:** Check Neonize version (0.3.18+). Message API may have changed. Inspect event object with `dir(event)` and `type(event)`. Refer to Neonize source or docs for current attribute names.
- **Issue:** WhatsApp bans the connected number after adapter starts sending messages
  - **Solution:** Immediately stop the service. Verify rate limiter is active and limits are enforced (8/min, 30/hr, 200/day). Check that typing indicators include natural delays. Ensure responses are reactive-only (never initiate to unknown contacts). Consider residential proxy if datacenter IP is the cause. Wait 24-48 hours before reconnecting. Use a different number for testing if possible.
- **Issue:** `split_response()` produces empty chunks or loses content
  - **Solution:** Add edge case handling for empty input, single-character input, and input with only whitespace. Verify that reassembling all chunks produces the original text (minus split-point whitespace).
- **Issue:** Typing indicator shows indefinitely (never stops)
  - **Solution:** Always send `presence="paused"` after message send, even on error. Wrap send in try/finally to ensure typing is stopped. Add a timeout (10s max) after which typing is force-stopped.
- **Issue:** JID format mismatch — Neonize returns `628123456789:1@s.whatsapp.net` (with device suffix)
  - **Solution:** Strip device suffix in `normalize_jid()`: `jid.split("@")[0].split(":")[0]`. Store normalized JIDs in whitelist for consistent comparison.

#### Notes
- **Ban risk awareness:** This is the highest-risk step in P11 for WhatsApp account bans. The adapter is the point where Guinevere interacts with WhatsApp's servers. All ban risk mitigations (rate limiting, typing delays, reactive-only messaging, no broadcast) MUST be enforced at this layer. Test extensively with a secondary number before connecting Faiz's primary number.
- Neonize uses the unofficial Multi-Device (MD) WhatsApp protocol. Protocol breaks occur every 2-8 weeks when WhatsApp updates their servers. The adapter must handle connection errors gracefully and trigger the reconnection handler from P11-003.
- The media acknowledgment text ("belum bisa proses media") should be persona-consistent (Y4 sugar mommy tone) but clearly indicate the limitation. Exact wording will be refined during implementation.
- WhatsApp message IDs are different from Discord message IDs. The `message_id` field in `UnifiedMessage` stores the Neonize-native ID. Cross-channel deduplication uses `content_hash` (SHA-256 of sender + content + timestamp), not message IDs.
- Cross-reference P11-003 for NeonizeClient API details (connection, event types, session management). Cross-reference P11-008 for the routing pipeline that receives `UnifiedMessage` from this adapter.
- Group messages MUST be ignored — 1-on-1 only per requirements (decision #24). Check if incoming message is from a group JID (format: `120363xxx@g.us`) and silently discard.
- The adapter does NOT implement the ConversationalAgent integration directly. It only converts events to `UnifiedMessage` and passes them to the routing pipeline. The ConversationalAgent (P11-006) is invoked by the router, not by the adapter.
