### Step P11-021: Health Check + Grafana Monitoring — 60s Interval

**Type:** Application
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P11): pending`

**Goal:** Health check service running every 60 seconds, publishing Prometheus metrics for Grafana. Metrics: `whatsapp_connected` (gauge), `whatsapp_messages_received_total` (counter), `whatsapp_messages_sent_total` (counter), `whatsapp_response_latency_seconds` (histogram), `whatsapp_reconnect_attempts_total` (counter), `whatsapp_session_age_seconds` (gauge), `whatsapp_rate_limit_hits_total` (counter). Grafana dashboard via grafanalib (same P9-010 pattern).
**Dependencies:** P11-003 (NeonizeClient — connection state source), P11-020 (ReconnectionHandler — `guinevere:wa:reconnect:attempts` key), P8 (Prometheus + Grafana infrastructure — `prometheus.yml`, Grafana provisioning), P9-010 (grafanalib pattern — Python → JSON → Grafana provisioning directory)
**Cost Impact:** $0/month (Prometheus + Grafana already running from P8)
**ADR References:** ADR-032 (Observability — all subsystems expose Prometheus metrics queryable via Grafana), ADR-022 (Connection monitoring — health check for WhatsApp connection lifecycle)
**Acceptance Criteria:** AC-OPS-002 (Metrics published — Prometheus scrapes all 7 WhatsApp metrics every 60s), AC-OPS-005 (Grafana dashboard — dedicated WhatsApp panel showing connection state, message throughput, reconnect history, session age, rate limits)
**Estimated Time:** 5 hours

#### Context

The Guinevere monitoring stack is fully operational from P8: Prometheus 2.x scrapes application metrics on a configurable interval (default 15s), Grafana 10.x auto-provisions dashboards from JSON files in `/etc/grafana/provisioning/dashboards/`, and Loki aggregates application logs. P9-010 established the grafanalib pattern: Python source files define Grafana dashboards programmatically (using grafanalib's builder API), a build script serializes them to JSON, and the JSON files are copied to Grafana's provisioning directory. This approach provides version control for dashboard definitions and eliminates manual Grafana UI configuration. P11-021 extends this exact pattern to WhatsApp health monitoring.

The health check service is a single `asyncio.Task` spawned during WhatsApp client initialization (P11-003). It runs an infinite loop with a 60-second interval, pinging the Neonize client connection state, querying Redis for session metadata, checking rate limit counters, and updating 7 Prometheus metrics. The Prometheus client library (`prometheus_client`) exposes metrics on the existing application metrics endpoint (same HTTP server used by P9-010). Prometheus scrapes this endpoint every 15 seconds (configured in `prometheus.yml`), so metrics are available within 75 seconds of any state change (60s check interval + 15s scrape interval).

The Grafana dashboard provides 6 panels: (1) Connection State — gauge showing current connection status with color-coded thresholds, (2) Message Throughput — time series of received/sent messages per minute, (3) Reconnect History — time series of reconnect attempt count with alert threshold overlay, (4) Session Age — gauge showing session uptime with 12-day warning threshold, (5) Rate Limit Hits — stacked bar chart of rate limit violations per hour/day, (6) Response Latency — histogram heatmap showing AI response time distribution. Each panel uses PromQL queries targeting the `whatsapp_*` metric namespace.

Alert rules are configured in Prometheus alerting rules (not Grafana alerting, per P9-010 convention): (1) `whatsapp_connected == 0` for >5 minutes → SEV0 Discord alert via P11-019 notification system, (2) `whatsapp_session_age_seconds > 1036800` (12 days) → SEV2 warning (phone offline reminder — WhatsApp disconnects after 14 days), (3) `whatsapp_rate_limit_hits_total` increasing >10/hour → SEV1 Discord alert (abnormal rate limit pressure indicates misconfigured limits or adversarial input).

#### Prometheus Metrics Specification

| Metric Name | Type | Labels | Unit | Description | Threshold / Alert |
|---|---|---|---|---|---|
| `whatsapp_connected` | Gauge | `device` | — | 1 if connected, 0 if disconnected/reconnecting/failed | `==0` for >5min → SEV0 alert |
| `whatsapp_messages_received_total` | Counter | `device` | messages | Total WhatsApp messages received since process start | — |
| `whatsapp_messages_sent_total` | Counter | `device` | messages | Total WhatsApp messages sent since process start | — |
| `whatsapp_response_latency_seconds` | Histogram | `device` | seconds | Time from message received to AI response sent | Buckets: 0.5, 1, 2, 5, 10, 30, 60 |
| `whatsapp_reconnect_attempts_total` | Counter | `device`, `reason` | attempts | Total reconnection attempts since process start | — |
| `whatsapp_session_age_seconds` | Gauge | `device` | seconds | Age of current WhatsApp session from `connected_at` timestamp | `>1036800` (12 days) → SEV2 warning |
| `whatsapp_rate_limit_hits_total` | Counter | `device`, `window` | hits | Total rate limit violations since process start | >10/hour increase → SEV1 alert |

**Histogram buckets for `whatsapp_response_latency_seconds`:**
`[0.5, 1.0, 2.0, 5.0, 10.0, 30.0, 60.0]` — covers typical AI response times from fast (<1s) to very slow (>60s).

**Counter vs Gauge semantics:**
- **Gauges** (`whatsapp_connected`, `whatsapp_session_age_seconds`): updated every 60s from live state. Can go up or down.
- **Counters** (`messages_received_total`, `messages_sent_total`, `reconnect_attempts_total`, `rate_limit_hits_total`): incremented on each event. Never decrease. Reset on process restart (Prometheus `rate()` function handles this correctly).

**Redis key sources for each metric:**
- `whatsapp_connected` ← `guinevere:wa:connection:state` (written by P11-020 ReconnectionHandler)
- `whatsapp_messages_received_total` ← `guinevere:wa:messages:received` (written by P11-015 message router)
- `whatsapp_messages_sent_total` ← `guinevere:wa:messages:sent` (written by P11-015 message router)
- `whatsapp_response_latency_seconds` ← `guinevere:wa:response:latency:last` (written by P11-015 message router on each response)
- `whatsapp_reconnect_attempts_total` ← `guinevere:wa:reconnect:attempts` (written by P11-020 ReconnectionHandler)
- `whatsapp_session_age_seconds` ← `guinevere:wa:session:created_at` (written by P11-003 NeonizeClient on connected event)
- `whatsapp_rate_limit_hits_total` ← `guinevere:wa:ratelimit:hits:{minute,hour,day}` (written by P11-005 rate limiter)

#### Troubleshooting
- **Issue:** Prometheus shows no `whatsapp_*` metrics after scraping
  - **Solution:** Verify the metrics endpoint is running and includes WhatsApp metrics. Check `src/monitoring/whatsapp_metrics.py` is imported before the Prometheus HTTP server starts. If metrics are defined after `start_http_server()`, they may not be registered in the collector registry. Import order matters: define all metrics → start HTTP server.
- **Issue:** Grafana dashboard panels show "No data"
  - **Solution:** Prometheus may not yet have scraped enough data points. Wait for at least 2 scrape cycles (30s) and refresh the dashboard. If still no data, check that the Prometheus scrape target for port 9100 is UP: `curl http://localhost:9090/api/v1/targets | grep "whatsapp\|9100"`.
- **Issue:** `whatsapp_session_age_seconds` always shows 0
  - **Solution:** The Redis key `guinevere:wa:session:created_at` is written by P11-003 NeonizeClient on connected event. If P11-003 hasn't wired the `connected_at` write yet, the gauge will show 0. Verify the key exists: `redis-cli -p 6380 --user guinevere_core GET guinevere:wa:session:created_at`. If missing, P11-003 needs to write `datetime.now(timezone.utc).isoformat()` on every successful connection.
- **Issue:** Health check crashes on Redis connection timeout
  - **Solution:** The `_check_once()` method must wrap Redis queries in try/except with `logger.exception()`. On Redis failure, set all gauges to 0 (unknown state) and log the error. The health check must never crash the main WhatsApp process — use `asyncio.shield()` or catch all exceptions at the task level.
- **Issue:** Alert rules not loaded by Prometheus after reload
  - **Solution:** Verify the alert rules file path is listed in `prometheus.yml` under `rule_files:`. Check Prometheus configuration is valid: `curl -s http://localhost:9090/api/v1/status/config`. If the reload failed, check Prometheus logs: `journalctl -u prometheus -n 20`.
- **Issue:** `whatsapp_connected` gauge flickers between 0 and 1 rapidly
  - **Solution:** This indicates the connection state in Redis (`guinevere:wa:connection:state`) is flapping. The ReconnectionHandler (P11-020) should debounce state changes — if state changes more than 5 times in 60 seconds, it's a flap condition. The health check should read the Redis key once per 60s cycle and not react to transient mid-cycle changes.

#### Notes
- **grafanalib Pattern (P9-010):** The dashboard definition file follows the exact pattern from P9-010: import `grafanalib.core` as `G`, define a `Dashboard` object with `panels` list, each panel is a `TimeSeries`, `Gauge`, `Stat`, or `Heatmap` with `targets` containing `PromQL` expressions. The build script runs `generate-dashboard` to serialize the Python object to JSON. This approach provides version control, code review, and CI validation for dashboard definitions.
- **Counter Reset Semantics:** Prometheus counters reset to 0 on process restart. This is expected and handled correctly by PromQL `rate()` and `increase()` functions, which detect counter resets and adjust calculations. Do NOT use `absent()` or manual reset logic — Prometheus handles this natively.
- **Histogram Bucket Selection:** The latency buckets `[0.5, 1.0, 2.0, 5.0, 10.0, 30.0, 60.0]` are tuned for AI response times: sub-second responses are fast, 1-2s is typical, 5-10s is slow, 30-60s indicates LLM timeout or complex agent loops. Buckets above 60s are not included because responses taking >60s indicate a problem that should trigger an alert, not just monitoring.
- **Label Cardinality:** The `device` label has a single value (`faiz`) — Guinevere serves one operator. The `reason` label on `reconnect_attempts_total` has 5 values (matching `DisconnectReason` enum). The `window` label on `rate_limit_hits_total` has 3 values (`minute`, `hour`, `day`). Total cardinality: 7 metrics × max 5 label values = 35 time series. Well within Prometheus limits (default 100,000).
- **Cross-Reference P9-010:** This step uses the same grafanalib infrastructure, build script, and provisioning directory as P9-010. Do NOT create a separate build script or provisioning path — extend the existing ones.
- **Cross-Reference P11-019:** The `!wa-status` Discord command queries the same Redis keys that the health check reads. Both consume the same data sources — the health check writes to Prometheus (long-term storage), while `!wa-status` reads directly from Redis (real-time query).
- **Cross-Reference P11-020:** The `whatsapp_reconnect_attempts_total` counter is incremented by the health check reading `guinevere:wa:reconnect:attempts` from Redis. The ReconnectionHandler WRITES this key; the health check READS it and exposes it as a Prometheus counter.
- **60s Check Interval Rationale:** 60 seconds balances freshness vs resource usage. WhatsApp connection drops typically last minutes to hours, not seconds — a 60s interval catches outages within 1-2 minutes. More frequent checks (e.g., 10s) would waste Redis connections and CPU without proportional monitoring benefit.
