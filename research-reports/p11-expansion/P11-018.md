### Step P11-018: Discord Bridge — Message Mirror to Private Channel

**Type:** Application
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P11): pending`

**Goal:** Implement a Discord bridge that mirrors all WhatsApp conversations to a designated private Discord channel (`#whatsapp-mirror`). Every incoming WhatsApp message from Faiz and every outgoing Guinevere response is forwarded to Discord as a rich embed showing: sender identity (Faiz/Guinevere), message content, WIB timestamp, and channel badge (WhatsApp). The bridge is invoked AFTER the WhatsApp response is sent (non-blocking) and provides Faiz a unified cross-channel audit trail.
**Dependencies:** P11-008 (routing pipeline — bridge called after response sent), P2 (Discord bot operational — `src/discord/bot.py`, `GuinevereBot` with `commands.Bot`), P11-005 (WhatsAppAdapter — `src/channels/whatsapp/adapter.py` with `send_message()` and event handling)
**Cost Impact:** $0/month (uses existing Discord bot instance and guild channels)
**ADR References:** ADR-022 (cross-channel sync — all channel activity visible on primary interface), ADR-015 (audit trail for surveillance data — WhatsApp messages classified as surveillance data requiring transparency)
**Acceptance Criteria:** AC-COM-006 (cross-channel mirror — WhatsApp messages appear in Discord within 5 seconds), SRS-IR-009 (message dedup awareness — mirror includes `content_hash` for dedup correlation)
**Estimated Time:** 4 hours

#### Context

Faiz uses Discord as his primary operational interface — all system alerts, status embeds, and command interactions happen there. When he chats with Guinevere on WhatsApp, he loses visibility of those conversations unless he switches apps. The Discord bridge solves this by mirroring every WhatsApp interaction to a private `#whatsapp-mirror` channel, giving Faiz a single pane of glass across all communication channels. This is not optional convenience — it is a surveillance transparency requirement. WhatsApp messages are classified as surveillance data per `SurveillanceDataPolicy` (`docs/30-data/33-SurveillanceDataPolicy_v1.0.md`), and ADR-015 mandates that all surveillance data must have an accessible audit trail. The Discord mirror IS that audit trail for WhatsApp.

The bridge architecture is intentionally simple: a `DiscordMirrorBridge` class that accepts a `UnifiedMessage` (incoming from Faiz) or a `UnifiedResponse` (outgoing from Guinevere) and constructs a Discord embed. The bridge is called by the routing pipeline (P11-008) AFTER the WhatsApp response has been sent — it is fire-and-forget, never blocking the WhatsApp reply path. If the Discord send fails (channel not found, rate limited, bot disconnected), the error is logged via `structlog` and the WhatsApp flow continues uninterrupted. The mirror channel ID is configured via the `DISCORD_MIRROR_CHANNEL_ID` environment variable, allowing reconfiguration without code changes.

The embed format follows the existing Guinevere Discord UX patterns established in P2. Colors reuse constants from `src/discord/colors.py`: green (`SUCCESS = 0x16A34A`) for incoming messages from Faiz, purple (`PRIMARY = 0x6B21A8`) for outgoing Guinevere responses. The footer uses the canonical `"Guinevere de Baroque"` branding. Timestamps are formatted in WIB (`UTC+7`) matching the existing `_format_wib_timestamp()` pattern from `src/discord/cmd_status.py`. The embed includes a `content_hash` field (truncated SHA-256, first 8 characters) for dedup correlation per SRS-IR-009.

#### Troubleshooting
- **Issue:** `discord.NotFound: Channel not found` when sending mirror embed
  - **Solution:** Verify `DISCORD_MIRROR_CHANNEL_ID` matches an existing text channel in guild `1510876414671323206`. Use `bot.get_channel(int(channel_id))` — returns `None` if channel doesn't exist or bot lacks permissions. Check bot has `View Channel` and `Send Messages` permissions on the target channel.
- **Issue:** Mirror embed sends are rate-limited by Discord API (429 Too Many Requests)
  - **Solution:** Discord rate limit for channel messages is ~5 messages per 5 seconds. If WhatsApp conversation is extremely active, implement a simple queue with `asyncio.Queue` and batch-send with 1-second intervals. Do NOT retry on 429 — discord.py handles rate limit backoff automatically.
- **Issue:** `ImportError: cannot import name 'DiscordMirrorBridge'` from `src.discord`
  - **Solution:** Verify `src/discord/whatsapp_mirror.py` exists and has correct class name. Check that `src/discord/__init__.py` does not need explicit export (lazy import from `router.py` is sufficient).
- **Issue:** Bridge blocks WhatsApp response when Discord is slow
  - **Solution:** The bridge MUST be called as `asyncio.create_task(bridge.mirror_incoming(msg))` or equivalent fire-and-forget pattern. Never `await` the mirror call in the critical response path. Verify the routing pipeline (P11-008) uses task spawning, not sequential awaiting.
- **Issue:** Duplicate mirror messages when WhatsApp retries delivery
  - **Solution:** Use `content_hash` for dedup. Before sending mirror embed, check Redis key `guinevere:mirror:dedup:{content_hash}` with 60-second TTL. If key exists, skip mirror. This prevents double-mirroring on WhatsApp message retries.

#### Notes
- **Non-Blocking Architecture:** The bridge is fire-and-forget. If Discord is down, WhatsApp continues working. This is intentional — WhatsApp is a communication channel, Discord mirror is an observability feature. Never compromise WhatsApp reliability for mirror completeness.
- **Color Consistency:** Green (`SUCCESS = 0x16A34A`) for incoming matches the existing `colors.py` semantic convention where green = positive/approval/incoming. Purple (`PRIMARY = 0x6B21A8`) for outgoing matches Guinevere's brand color — all Guinevere-originated embeds use purple.
- **Surveillance Classification:** WhatsApp messages ARE surveillance data per ADR-015 and `SurveillanceDataPolicy`. The Discord mirror serves as the transparency mechanism — Faiz sees every message that flows through the system. This is why mirror failures must be logged (audit gap).
- **Gotify Fallback:** The existing `src/discord/gotify_fallback.py` handles SEV0/SEV1 notification fallback. Mirror messages do NOT use Gotify fallback — they are non-critical observability, not alerts. If Discord is down, mirror messages are simply dropped with a logged warning.
- **Cross-Reference P11-019:** Notification events (connection, disconnection, HARD STOP) are handled separately in P11-019 and DO use the alert routing system (`src/discord/notifications.py`) with Gotify fallback. The mirror bridge (this step) and notification system (P11-019) are complementary but independent modules.
- **Multi-Message Responses:** If Guinevere's response is split into multiple bubbles (multi-part `UnifiedResponse`), each part should generate a separate mirror embed with a `Part X/Y` field. The `split_index` from `UnifiedResponse` provides this information.
- **Message Length:** Discord embed description limit is 4096 characters. If WhatsApp message content exceeds this, truncate to 4000 characters with `"... (truncated)"` suffix. Log the full content to structured log for audit completeness.
