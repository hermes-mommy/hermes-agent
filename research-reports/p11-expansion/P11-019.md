### Step P11-019: Discord Bridge — Notifications + Status Embed

**Type:** Application
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P11): pending`

**Goal:** Implement a Discord notification system for WhatsApp connection lifecycle events and a `!wa-status` command that returns a rich status embed. Notifications fire on 6 distinct events: connection established, connection lost, reconnection failure, session expiry, HARD STOP trigger, and phone offline warning. The `!wa-status` command queries Neonize connection state, Redis session age, PostgreSQL conversation count (last 24h), Redis rate limit counters, and last message timestamp, returning all metrics in a single Discord embed.
**Dependencies:** P11-018 (Discord mirror bridge infrastructure — `src/discord/whatsapp_mirror.py`), P11-003 (connection event handlers — `src/channels/whatsapp/neonize_client.py` with `ConnectedEv`/`DisconnectedEv`), P11-020 (reconnection handler — `src/channels/whatsapp/reconnection.py`), P2 (Discord bot — `src/discord/bot.py` with `GuinevereBot`, command prefix `!`)
**Cost Impact:** $0/month (uses existing Discord bot, Redis, PostgreSQL — no new services)
**ADR References:** ADR-022 (operational visibility — WhatsApp health visible on primary interface), ADR-032 (Observability — all subsystem health queryable via unified dashboard)
**Acceptance Criteria:** AC-OPS-002 (observability — WhatsApp connection status visible in Discord without manual checking), AC-COM-007 (connection event notifications — all 6 lifecycle events produce Discord embeds within 10 seconds)
**Estimated Time:** 3 hours

#### Context

Faiz manages Guinevere primarily through Discord. When WhatsApp is running as a secondary communication channel, he needs immediate visibility into its health without SSH-ing to the VPS or checking logs manually. The existing Discord notification system (`src/discord/notifications.py`) already handles SEV-based alert routing with 5 severity levels, channel-specific routing (`system-health`, `cost-tracker`, `guinevere-status`, `audit-log`), color-coded embeds via `src/discord/colors.py`, and Gotify push fallback (`src/discord/gotify_fallback.py`) for SEV0/SEV1 alerts. P11-019 extends this pattern to WhatsApp-specific lifecycle events.

The 6 notification events cover the full WhatsApp connection lifecycle: (1) connected — session authenticated and operational, (2) disconnected — connection lost unexpectedly, (3) reconnection failed — automatic retry exhausted, (4) session expired — Neonize session needs re-pairing, (5) HARD STOP triggered — safe word activated on WhatsApp channel, (6) phone offline warning — linked device offline >12 days (WhatsApp disconnects after 14 days). Each event maps to a specific severity level in the existing SEV matrix: connected = SEV3 (informational), disconnected = SEV1 (alert), reconnection failed = SEV0 (critical), session expired = SEV1 (alert), HARD STOP = SEV0 (critical, ping Faiz), phone offline = SEV2 (warning). SEV0 and SEV1 events automatically trigger Gotify fallback via the existing `send_fallback()` mechanism.

The `!wa-status` command follows the text-prefix pattern already configured in `GuinevereBot` (`command_prefix="!"`) and mirrors the embed structure of the existing `/status` command (`src/discord/cmd_status.py`). However, unlike `/status` which is a slash command, `!wa-status` uses the text command pattern because WhatsApp-related commands may need to work in channels where slash commands are less convenient. The status embed queries 5 data sources: Neonize client state (connected/disconnected/reconnecting), Redis key `guinevere:wa:session:created_at` (session age), PostgreSQL conversation table (message count last 24h), Redis keys `guinevere:wa:ratelimit:*` (current rate limit counters), and Redis key `guinevere:wa:last_message_at` (last activity timestamp). All values are assembled into a single embed with 7 fields.

#### Troubleshooting
- **Issue:** `!wa-status` command not recognized by the bot
  - **Solution:** Verify the command is registered via `bot.add_command()` or the `@bot.command(name="wa-status")` decorator in `setup_hook()`. The bot uses `command_prefix="!"` (see `src/discord/bot.py` line 115). If using text commands, ensure `process_commands()` is called in `on_message` (already implemented at line 345).
- **Issue:** Notification embed sends fail silently (no message appears in Discord)
  - **Solution:** Check that the target channel exists. Notifications route through `send_alert()` in `notifications.py` which uses SEV-based channel routing. SEV0/SEV1 → `#system-health`, SEV2 → `#cost-tracker`, SEV3 → `#guinevere-status`. Verify these channels exist in guild `1510876414671323206`. Alternatively, configure a dedicated `DISCORD_WA_ALERTS_CHANNEL_ID` to override default routing.
- **Issue:** Gotify fallback not firing for SEV0/SEV1 WhatsApp events
  - **Solution:** Verify `GOTIFY_APP_TOKEN` is set in environment. The `send_fallback()` function in `src/discord/gotify_fallback.py` returns `False` silently if token is missing (logged as `gotify_fallback_disabled`). Check Gotify is running: `curl http://localhost:8081/version`.
- **Issue:** `!wa-status` shows "N/A" for all fields
  - **Solution:** Redis keys may not be populated yet. Verify WhatsApp client is connected and writing session data. Check Redis keys exist: `redis-cli -p 6380 --user guinevere_core KEYS "guinevere:wa:*"`. If keys are empty, the Neonize client (P11-003) may not be writing session metadata yet — this is expected before P11-003 is fully wired.
- **Issue:** Rate limit fields show "0/0" instead of actual values
  - **Solution:** Rate limit counters are written by `src/channels/whatsapp/rate_limiter.py` (P11-005). If the rate limiter is not yet active, counters will be zero. This is a valid state — display "0/8", "0/30", "0/200" to show limits are configured even if no messages have been sent.
- **Issue:** `!wa-status` accessible by non-Faiz users
  - **Solution:** Enforce Faiz-only access using `is_faiz_interaction()` from `src/discord/commands.py` or equivalent message author check. For text commands, check `message.author.id` against the configured Faiz user ID. Match the pattern used in `cmd_status.py` where `is_faiz_interaction()` gates access.

#### Notes
- **SEV Mapping Consistency:** The 6 WhatsApp events map to existing SEV levels in `notifications.py` SEV_MATRIX. This means WhatsApp notifications automatically inherit channel routing, color assignment, and Gotify fallback behavior from the existing alert infrastructure. No new routing logic is needed — only new event types that call `send_alert()`.
- **`!wa-status` vs `/status`:** The existing `/status` command is a slash command with 11 fields covering the entire Guinevere system. The `!wa-status` command is WhatsApp-specific with 7 fields. These are complementary — `/status` may eventually include a WhatsApp field, but `!wa-status` provides deeper WhatsApp-specific metrics (rate limits, session age) that don't belong in the general status embed.
- **HARD STOP Cross-Channel:** When HARD STOP is triggered on WhatsApp, the notification embed in Discord serves dual purpose: (1) alert Faiz immediately, and (2) provide audit trail that HARD STOP was triggered and from which channel. The `cmd_safeword.py` handler already manages HARD STOP state — P11-019 adds the Discord notification call when the trigger originates from WhatsApp.
- **Phone Offline 12-Day Warning:** WhatsApp disconnects linked devices after 14 days of phone inactivity. The 12-day warning gives Faiz a 2-day buffer to open WhatsApp on his phone. This check should run on a periodic timer (e.g., every 6 hours) comparing `last_phone_seen` timestamp from Neonize against the current time. The timer can be implemented as an `asyncio.Task` spawned during WhatsApp client startup (P11-003).
- **Gotify Fallback Pattern:** The existing `send_fallback()` in `src/discord/gotify_fallback.py` accepts `title`, `description`, and `severity` parameters. SEV0 maps to Gotify priority 10, SEV1 to priority 7. WhatsApp notification events reuse this exact interface — no changes to `gotify_fallback.py` are needed.
- **Cross-Reference P11-018:** The message mirror bridge (P11-018) handles conversation content mirroring. This step (P11-019) handles connection lifecycle notifications and status queries. They share the same Discord channel configuration but serve different purposes: mirror = content audit trail, notifications = operational health.
- **Cross-Reference P11-005:** Rate limit counter Redis keys (`guinevere:wa:ratelimit:{minute,hour,day}`) are written by the rate limiter in P11-005. The `!wa-status` command READS these keys but does not write them.
- **Dedup Correlation:** Mirror embeds from P11-018 include `content_hash` for dedup. Notification embeds do NOT include `content_hash` because they are system events, not conversation messages.
