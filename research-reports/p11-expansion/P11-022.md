#### Context

ADR-022 mandates that the WhatsApp service runs as a **separate systemd unit** from the main Guinevere API. This isolation ensures that WhatsApp-specific crashes (protocol breaks, Neonize panics, session expirations) do not cascade to the API, Discord bot, or other subsystems. If `guinevere-whatsapp.service` crashes, only WhatsApp messaging is affected — Discord continues operating, memory recall works, financial tracking persists, and surveillance collection continues. The existing `guinevere-api.service` (P10-004) remains the parent process for all other subsystems.

The systemd unit follows the hardening pattern established in P10-004. Key security constraints: `NoNewPrivileges=true` prevents privilege escalation, `ProtectSystem=strict` makes the filesystem read-only except for explicitly allowed paths, `PrivateTmp=true` isolates `/tmp` from other services. The caveat for WhatsApp is `MemoryDenyWriteExecute=true` — this hardening flag blocks execution of code in memory-mapped writable regions, which is incompatible with Python C extensions. The `neonize` library wraps a Go binary via CGo/FFI, which may require writable+executable memory for JIT or dynamic linking. This must be tested: if `MemoryDenyWriteExecute=true` causes Neonize to crash, disable it and document the exception.

The unit file uses `Restart=on-failure` with `RestartSec=10` — systemd will automatically restart the service after a non-zero exit code or signal, with a 10-second delay. This complements (not replaces) the application-level reconnection handler (P11-020). The two layers work together: P11-020 handles connection drops WITHIN a running process (no restart needed for transient network issues), while systemd handles process-level crashes (OOM, segfault, unhandled exception). `StartLimitBurst=3` and `StartLimitIntervalSec=60` prevent infinite restart loops — if the service fails 3 times within 60 seconds, systemd stops trying and an alert fires.

The operational runbook documents all manual procedures that Faiz or an on-call agent may need to perform. Each procedure is step-by-step with exact commands, expected output, and failure recovery. The runbook covers 5 scenarios: (1) initial QR setup — first-time WhatsApp pairing, (2) session recovery — re-pairing after session expiry, (3) protocol break recovery — updating Neonize after WhatsApp changes their protocol, (4) ban recovery — handling WhatsApp temporary/permanent account bans, (5) phone-offline handling — managing the 14-day phone inactivity deadline.

#### Systemd Unit File Example

```ini
# /etc/systemd/system/guinevere-whatsapp.service
# Guinevere WhatsApp Channel — separate unit per ADR-022
# Isolation: WhatsApp crash does not affect API, Discord, or other subsystems

[Unit]
Description=Guinevere WhatsApp Channel (Neonize)
Documentation=https://github.com/nicnicnicnic/nicnicnicnic
After=network-online.target guinevere-api.service redis.service
Wants=network-online.target
Requires=redis.service

[Service]
Type=simple
User=guinevere
Group=guinevere
WorkingDirectory=/opt/guinevere

# Environment: load SOPS-decrypted secrets
EnvironmentFile=/opt/guinevere/.env.whatsapp
Environment=PYTHONUNBUFFERED=1
Environment=PYTHONDONTWRITEBYTECODE=1

# Entry point: WhatsApp service module
ExecStart=/opt/guinevere/.venv/bin/python -m src.channels.whatsapp.service

# Restart policy: restart on failure with 10s delay
Restart=on-failure
RestartSec=10
StartLimitBurst=3
StartLimitIntervalSec=60

# Logging: stdout/stderr to journald
StandardOutput=journal
StandardError=journal
SyslogIdentifier=guinevere-whatsapp

# Resource limits
LimitNOFILE=65536
TimeoutStopSec=30

# Hardening (P10-004 pattern)
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
PrivateDevices=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
RestrictSUIDSGID=true
LockPersonality=true
RestrictRealtime=true
RestrictNamespaces=true
SystemCallArchitectures=native

# Read-write paths: WhatsApp session data and Neonize auth state
ReadWritePaths=/opt/guinevere/data/whatsapp /opt/guinevere/logs /opt/guinevere/.neonize_auth

# NOTE: MemoryDenyWriteExecute=true is OMITTED intentionally.
# Neonize wraps Go via CGo/FFI which may require writable+executable memory.
# Test with MemoryDenyWriteExecute=true first; if Neonize crashes, keep it disabled.
# See runbook §Troubleshooting for testing procedure.

[Install]
WantedBy=multi-user.target
```

Initializes NeonizeClient, ReconnectionHandler, HealthCheck, and runs the event loop.

class WhatsAppService:
    def __init__(self) -> None: ...
    async def start(self) -> None: ...
    async def stop(self) -> None: ...
    async def _graceful_shutdown(self, signal_name: str) -> None: ...

async def main() -> None:
    service = WhatsAppService()
    loop = asyncio.get_running_loop()
    for sig in (signal.SIGINT, signal.SIGTERM):

#### Runbook Content

The runbook file `runbooks/whatsapp-operations.md` must cover these 5 operational procedures:

**Procedure 1: Initial QR Setup**
```
1. Stop the service: sudo systemctl stop guinevere-whatsapp
2. Clear old auth state: rm -rf /opt/guinevere/.neonize_auth/*
3. Start in foreground for QR display: sudo -u guinevere /opt/guinevere/.venv/bin/python -m src.channels.whatsapp.service --qr-mode=terminal
4. Scan QR code with WhatsApp app on phone (Settings > Linked Devices > Link a Device)
5. Wait for "Connected" confirmation in terminal output
6. Press Ctrl+C to stop foreground process
7. Start as service: sudo systemctl start guinevere-whatsapp
8. Verify: sudo systemctl status guinevere-whatsapp
```

**Procedure 2: Session Recovery (Session Expired)**
```
1. Check Discord notification or !wa-status for session_expired event
2. Verify Redis flag: redis-cli -p 6380 --user guinevere_core GET guinevere:wa:reconnect:needs_manual
3. Stop service: sudo systemctl stop guinevere-whatsapp
4. Clear auth state: rm -rf /opt/guinevere/.neonize_auth/*
5. Clear Redis reconnect flag: redis-cli -p 6380 --user guinevere_core DEL guinevere:wa:reconnect:needs_manual
6. Re-pair: follow Procedure 1 steps 3-8
```

**Procedure 3: Protocol Break Recovery**
```
1. Discord alert fires: "WhatsApp Reconnection Failed — protocol_version_mismatch"
2. Check Neonize GitHub releases for protocol update
3. Update Neonize: uv pip install --upgrade neonize
4. Test locally: sudo -u guinevere /opt/guinevere/.venv/bin/python -m src.channels.whatsapp.service --test-connect
5. If test passes: sudo systemctl restart guinevere-whatsapp
6. If test fails: rollback Neonize version, document issue, wait for upstream fix
7. Verify: sudo systemctl status guinevere-whatsapp && sudo journalctl -u guinevere-whatsapp -n 10
```

**Procedure 4: Ban Recovery**
```
1. Check WhatsApp app on phone for ban notification (temporary or permanent)
2. If TEMPORARY ban (24-72 hours):
   a. Wait for ban to expire — do NOT attempt reconnect during ban
   b. Set Redis flag to prevent auto-reconnect: redis-cli -p 6380 --user guinevere_core SET guinevere:wa:reconnect:needs_manual "banned"
   c. Monitor ban expiry via phone app
   d. After ban expires: clear flag and follow Procedure 2
3. If PERMANENT ban:
   a. Document ban details in incident log
   b. Disable WhatsApp integration: sudo systemctl stop guinevere-whatsapp && sudo systemctl disable guinevere-whatsapp
   c. Appeal through WhatsApp (Settings > Help > Contact Us)
   d. If appeal succeeds: follow Procedure 1 (fresh pairing)
   e. If appeal fails: WhatsApp channel remains disabled; Discord continues as primary
```

**Procedure 5: Phone Offline Handling**
```
1. Discord warning fires at 12 days: "WhatsApp Phone Offline >12 Days"
2. Open WhatsApp on phone — this resets the 14-day countdown
3. Verify phone is online: !wa-status shows "Phone Last Seen" < 12 days
4. If phone cannot be accessed (lost/stolen/broken):
   a. WhatsApp will auto-disconnect after 14 days of phone inactivity
   b. When auto-disconnect occurs: session_expired notification fires
   c. Follow Procedure 2 to re-pair with new phone
5. Preventive: keep phone charged and connected to internet at least once every 12 days
```

#### Troubleshooting
- **Issue:** `systemctl start guinevere-whatsapp` fails immediately with "failed to start"
  - **Solution:** Check journal logs: `sudo journalctl -u guinevere-whatsapp -n 50 --no-pager`. Common causes: (1) missing `.env.whatsapp` file — decrypt from SOPS, (2) Python import error — run `sudo -u guinevere /opt/guinevere/.venv/bin/python -c "from src.channels.whatsapp.service import WhatsAppService"` to test imports, (3) permission denied — verify `/opt/guinevere/data/whatsapp` and `.neonize_auth` are owned by `guinevere:guinevere`.
- **Issue:** Neonize crashes with `SIGSYS` when `MemoryDenyWriteExecute=true` is set
  - **Solution:** This confirms that Neonize's Go/CGo FFI requires writable+executable memory. Remove `MemoryDenyWriteExecute=true` from the unit file. Document the exception in the runbook §Known Exceptions. This is an acceptable trade-off — the Go binary is a trusted dependency, and the security risk is limited to the Neonize process scope.
- **Issue:** Service restarts infinitely despite `StartLimitBurst=3`
  - **Solution:** Verify `StartLimitIntervalSec=60` is set (default may be 10s on older systemd). Check systemd version: `systemctl --version`. If version < 245, the `StartLimitIntervalSec` directive may need to be in the `[Unit]` section instead of `[Service]`. Run `sudo systemctl reset-failed guinevere-whatsapp` to reset the start counter after fixing the root cause.
- **Issue:** Service starts but WhatsApp never connects (stuck in RECONNECTING)
  - **Solution:** Check if auth state exists: `ls -la /opt/guinevere/.neonize_auth/`. If directory is empty, session needs initial QR pairing — follow runbook Procedure 1. If auth state exists but connection fails, check Redis: `redis-cli -p 6380 --user guinevere_core GET guinevere:wa:connection:state`. If state is `failed`, clear the flag: `redis-cli -p 6380 --user guinevere_core DEL guinevere:wa:reconnect:needs_manual`.
- **Issue:** `ProtectSystem=strict` causes "Read-only file system" errors
  - **Solution:** The service needs write access to specific paths. Verify `ReadWritePaths` includes all directories the service writes to: `/opt/guinevere/data/whatsapp` (session data), `/opt/guinevere/logs` (log files), `/opt/guinevere/.neonize_auth` (Neonize auth state). If additional paths are needed, add them to `ReadWritePaths` and run `sudo systemctl daemon-reload`.
- **Issue:** Service starts but other systemd services report dependency failures
  - **Solution:** Verify `After=` and `Requires=` directives. `guinevere-whatsapp` requires `redis.service` — if Redis is down, WhatsApp won't start (expected behavior). `After=guinevere-api.service` is ordering only (not a hard requirement) — WhatsApp can start even if API is down, but should start after API for consistent logging.

#### Notes
- **Isolation Contract (ADR-022):** The fundamental design decision is that WhatsApp runs in its own process. If the Neonize library segfaults, only `guinevere-whatsapp.service` crashes — `guinevere-api.service` (Discord bot, API, memory, surveillance, financial) continues running. This is non-negotiable per ADR-022.
- **MemoryDenyWriteExecute Caveat:** This is the ONE hardening flag that may need to be disabled for WhatsApp. Python C extensions that wrap native code (like Neonize's Go/CGo bridge) often use `mmap` with `PROT_EXEC` for dynamic code generation. If Neonize works with this flag enabled, keep it — it's a significant security hardening. If it fails, the trade-off is acceptable because Neonize is a controlled dependency running in a sandboxed user account.
- **Restart Layering:** There are TWO restart layers: (1) application-level — P11-020 ReconnectionHandler handles connection drops without process restart, (2) systemd-level — `Restart=on-failure` handles process crashes. The application handler is tried first for transient issues. If the process itself dies (unhandled exception, OOM, segfault), systemd restarts the entire process. The ReconnectionHandler's state in Redis (`guinevere:wa:connection:state`) survives process restarts, so the new process picks up where the old one left off.
- **StartLimitBurst Protection:** `StartLimitBurst=3` with `StartLimitIntervalSec=60` prevents the "restart storm" anti-pattern where a broken service continuously crashes and restarts, flooding logs and consuming CPU. After 3 failures in 60 seconds, systemd gives up and marks the service as `failed (Result: start-limit-hit)`. Recovery requires manual `sudo systemctl reset-failed guinevere-whatsapp` followed by investigating the root cause before restarting.
- **Environment File Security:** The `.env.whatsapp` file contains the Redis password, database URL, and phone number. It must be encrypted at rest using SOPS+age (ADR-015). The unit file references it via `EnvironmentFile=` which reads the plaintext file at startup. The plaintext file should have permissions `0600` owned by `guinevere:guinevere` and should be regenerated from SOPS on each deployment.
- **Cross-Reference P10-004:** This unit follows the exact same hardening pattern as `guinevere-api.service` from P10-004. The differences are: (1) separate `ExecStart` for WhatsApp module, (2) WhatsApp-specific `ReadWritePaths`, (3) `Requires=redis.service` (API may use `Wants=`), (4) `MemoryDenyWriteExecute` caveat documented.
- **Cross-Reference P11-020:** The ReconnectionHandler handles connection drops within the running process. If the handler's retry loop exhausts all 3 attempts, it sets `needs_manual_reconnect` in Redis. The systemd service continues running — it does NOT crash. Faiz can trigger a manual reconnect via Discord command (`!wa-reconnect`) which clears the Redis flag and initiates a fresh connection attempt. Only if the Python process itself crashes does systemd intervene.
- **Runbook Location:** The runbook lives in `runbooks/whatsapp-operations.md` following the project convention (see `runbooks/dr/` for disaster recovery runbooks). The runbook is version-controlled in the repository and can be referenced by agents during incident response.
