#### Context

P11-023 is the **phase gate test** for the entire WhatsApp integration. Individual step tests (unit + integration per step) verify that each component works in isolation. P11-023 verifies that ALL components work together as a coherent system — messages flow from WhatsApp through intent detection, agent processing, response generation, and back to WhatsApp; Discord mirror captures the conversation; rate limits are enforced; reconnection handles real disconnects; Grafana dashboards show live metrics; and health checks detect anomalies. No component can be tested in true isolation for cross-cutting concerns like HARD STOP propagation or rate limiter interaction with the message pipeline.

The test infrastructure requires a **second phone** (or WhatsApp Web on a test account) to send scripted test messages to Guinevere's WhatsApp number. The test script (`tests/e2e/whatsapp/test_full_flow.py`) orchestrates the test sequence: it sends messages via the test phone, waits for responses (with configurable timeouts), asserts on response content and timing, checks Discord mirror embeds, verifies Prometheus metrics, and triggers simulated disconnects to test reconnection. Some steps require manual intervention (QR scan, phone interaction) — these are documented as manual steps with clear pass/fail criteria.

The 9 test scenarios cover the full user-facing behavior matrix: normal operation (scenarios 1-3), safety mechanisms (scenarios 4-6), operational resilience (scenarios 7-9). Each scenario has explicit setup, actions, assertions, expected timing, and cleanup. Scenarios are independent — a failure in one does not block the others. The test runner reports individual scenario results and an aggregate PASS/FAIL verdict. P11 GATE passes only when ALL 9 scenarios PASS.

"""Scenario 6: Rate limiter blocks messages exceeding per-minute limit."""
import pytest
import asyncio

@pytest.mark.e2e
@pytest.mark.scenario_6
async def test_rate_limiter_blocks(helper: WhatsAppTestHelper, redis_client):
    """Send 12 messages in 60s and verify messages 9-12 are rate-limited."""
    # Reset rate limit counters
    redis_client.delete("guinevere:wa:ratelimit:minute")
    
    responses_received = 0
    rate_limit_rejections = 0
    
    for i in range(12):
        await helper.send_message(TEST_PHONE_NUMBER, f"rate-test-{i+1}")
        response = await helper.wait_for_response(TEST_PHONE_NUMBER, timeout=10)
        if response:
            if "rate limit" in response.lower() or "terlalu cepat" in response.lower():
                rate_limit_rejections += 1
            else:
                responses_received += 1
        await asyncio.sleep(4)  # Spread across ~48 seconds (within 60s window)
    
    # First 8 should get responses, 9-12 should be rate-limited
    assert responses_received >= 6, f"Expected >=6 normal responses, got {responses_received}"
    assert rate_limit_rejections >= 2, f"Expected >=2 rate limit rejections, got {rate_limit_rejections}"
    assert responses_received + rate_limit_rejections >= 10, \
        f"Total accounted responses too low: {responses_received + rate_limit_rejections}/12"

#### Troubleshooting
- **Issue:** Scenario 2 fails — no response received within 30s
  - **Solution:** Check that ConversationalAgent is processing messages: `sudo journalctl -u guinevere-whatsapp -n 30 --no-pager | grep -i "agent\|intent\|response"`. Verify Hermes Agent is reachable via 9Router. Check Redis queue: `redis-cli -p 6380 --user guinevere_core LLEN guinevere:wa:message:queue`. If queue is growing but no responses, the agent may be failing silently — check application logs for exceptions.
- **Issue:** Scenario 4 (HARD STOP) fails — persona state not neutralized
  - **Solution:** The HARD STOP handler (`cmd_safeword.py`) must recognize `HARD STOP` from WhatsApp channel, not just Discord. Verify the WhatsApp message router forwards `HARD STOP` to the safe word handler. Check: `grep -n "HARD STOP\|hard_stop\|safe_word" src/channels/whatsapp/message_router.py`. The handler must set `guinevere:persona:state = "neutral"` in Redis.
- **Issue:** Scenario 5 (Discord Mirror) fails — message not found in mirror channel
  - **Solution:** Verify `DiscordMirrorBridge` is initialized and listening for WhatsApp messages: `sudo journalctl -u guinevere-whatsapp -n 20 --no-pager | grep -i "mirror"`. Check Discord bot has write permissions to the mirror channel. Verify channel ID: `redis-cli -p 6380 --user guinevere_core GET guinevere:discord:mirror_channel_id`.
- **Issue:** Scenario 6 (Rate Limiter) fails — all 12 messages get responses (no rate limiting)
  - **Solution:** Verify rate limiter is active: `redis-cli -p 6380 --user guinevere_core GET guinevere:wa:ratelimit:config:minute`. If the limit is set to 0 or missing, the rate limiter is disabled. The per-minute limit should be 8 (configurable). Also check that the rate limiter is wired into the message pipeline — messages must pass through `RateLimiter.check()` before reaching the ConversationalAgent.
- **Issue:** Scenario 7 (Reconnection) takes >300s or never reconnects
  - **Solution:** Verify the simulated disconnect actually breaks the Neonize WebSocket. If using `kill -SIGUSR1` on the Neonize subprocess, verify the signal reaches the right PID. Check reconnection handler logs: `sudo journalctl -u guinevere-whatsapp --no-pager | grep -i "reconnect\|disconnect\|backoff"`. If the handler sees the disconnect but fails all 3 retries, check Neonize auth state: `ls -la /opt/guinevere/.neonize_auth/`. If auth state was corrupted by the simulated disconnect, session re-pairing is needed.
- **Issue:** Scenario 8 (Grafana Metrics) fails — metrics show 0 or no data
  - **Solution:** Prometheus may not have scraped the metrics endpoint yet. Check scrape status: `curl -s http://localhost:9090/api/v1/targets | grep -A5 "9100"`.   - **Solution:** The health check task may not have been spawned.   - **Solution:** Scenario 7 (reconnection) and Scenario 9 (health check wait) are the longest. Run them separately or increase the `--timeout` flag. Consider parallelizing independent scenarios: scenarios 1-3 can run before scenarios 8-9 (which need data from earlier scenarios). Use `pytest-xdist` for parallel execution if available.
