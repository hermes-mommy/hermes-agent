### Step P11-015: Cross-Channel HARD STOP — Shared Redis Flag

**Type:** Application / Safety (CRITICAL)
**Status:** Not Started
**Risk:** High
**Git Commit:** `feat(P11): pending`

**Goal:** Extend the existing `HardStopHandler` (currently in-memory-only, Discord-specific at `src/core/services/hard_stop_handler.py`) to support cross-channel HARD STOP activation via a shared Redis flag. When HARD STOP is triggered on ANY channel (WhatsApp or Discord), set Redis flag `guinevere:hard_stop` that ALL channel adapters poll every 60 seconds. HARD STOP on WhatsApp = stop responding on ALL channels. Reset requires explicit `!hard-stop-reset` command from Faiz only. Emergency response sent on the channel that triggered the HARD STOP.
**Dependencies:** P11-008 (routing pipeline — HARD STOP checked before message processing), P2 (Discord bot operational — existing `HardStopHandler` in `src/core/services/hard_stop_handler.py`), P0 (Redis 7 accessible on port 6380)
**Cost Impact:** $0/month (Redis already provisioned; polling adds negligible load)
**ADR References:** ADR-002 (HARD STOP protocol — global architectural override, safe word mandate, cross-channel enforcement), ADR-022 (cross-channel safety — safe word must work identically across all channels)
**Acceptance Criteria:** AC-SAFETY-001 (HARD STOP works cross-channel — trigger on WhatsApp stops Discord, trigger on Discord stops WhatsApp), SRS-IR-008 (safe word cross-channel propagation)
**Estimated Time:** 4 hours

#### Context

Currently `HardStopHandler` at `src/core/services/hard_stop_handler.py` is a pure in-memory dataclass (149 lines) that detects HARD STOP keywords in messages via exact triggers (`"hard stop"`, `"hardstop"`, `"safe word"`, `"safeword"`, `"hentikan"`, `"berhenti"`) and semantic regex patterns. It maintains a `SafetyState` enum (NORMAL/SAFE), logs events to an in-memory list, and returns a neutral response string. This works for Discord-only because there is only one process handling messages. With P11 adding WhatsApp as a second channel, the in-memory handler is insufficient: (1) HARD STOP triggered on WhatsApp must propagate to Discord, (2) HARD STOP triggered on Discord must propagate to WhatsApp, (3) the state must survive process restarts (Redis-backed, not in-memory).

ADR-002 mandates HARD STOP as a "global architectural override" — a genuine safe word must "pause persona escalation, stop punishment framing, enter neutral/supportive mode" across the entire system. ADR-022 explicitly states "safe word must work identically across all channels" and "safe-word activation pauses persona escalation on every channel simultaneously." This is a CRITICAL safety requirement — false negatives are high severity (ADR-002 risk assessment). The implementation must guarantee that no channel continues processing after HARD STOP activation, even if the triggering message arrived on a different channel.

The solution uses a Redis hash as a shared coordination flag. Key `guinevere:hard_stop` stores a JSON-serialized object: `{"triggered": true/false, "channel": "whatsapp"/"discord"/null, "timestamp": 1717400000.0, "trigger": "hard stop", "reset_by": null}`. All channel adapters poll this key every 60 seconds via an async background task. When the flag is set, all adapters stop processing incoming messages and return the neutral response. The `!hard-stop-reset` admin command (Faiz-only, authenticated by sender ID) clears the flag and restores NORMAL state across all channels. The existing `HardStopHandler` class is extended (not replaced) — the `check()` method now also writes to Redis, and a new `check_remote()` method reads the Redis flag for cross-channel propagation.

System state before: `HardStopHandler` is in-memory-only, works for Discord exclusively, state lost on process restart. System state after: `HardStopHandler` backed by Redis, cross-channel HARD STOP propagation with 60-second polling interval, state survives process restarts, reset requires Faiz authentication.

#### Troubleshooting
- **Issue:** HARD STOP on WhatsApp does not propagate to Discord within 60 seconds
  - **Solution:** Verify polling task is running in both adapters. Check Discord adapter: `grep -n "start_polling\|check_remote" src/discord/bot.py`. Check WhatsApp adapter: `grep -n "start_polling\|check_remote" src/channels/whatsapp/adapter.py`. Verify Redis connectivity from both processes. Add debug logging to the poll loop: `logger.debug("hard_stop_poll", flag_state=...)`.
- **Issue:** `!hard-stop-reset` accepted from non-Faiz user
  - **Solution:** CRITICAL SAFETY BUG. Verify `authorized_ids` set contains ONLY Faiz's Discord user ID and Faiz's WhatsApp JID. Check that `sender_id` comparison is exact string match (no substring, no case-insensitive). Add unit test that exhaustively tests rejection for similar-looking IDs.
- **Issue:** HARD STOP state lost after Redis restart
  - **Solution:** Redis `guinevere:hard_stop` hash has no TTL (by design — HARD STOP persists until explicit reset). If Redis restarts and the key is lost, the system defaults to NORMAL state. This is an acceptable trade-off: Redis restarts are rare and monitored, and the risk of false-negative (continuing in SAFE when should be NORMAL) is lower than false-positive (stuck in SAFE after Redis recovery). Document this in evidence.
- **Issue:** Polling task crashes silently — no HARD STOP propagation
  - **Solution:** Wrap polling loop in try/except with `logger.exception` and automatic restart. Use `asyncio.Task.add_done_callback` to detect task death and respawn. Consider adding a Prometheus counter `hard_stop_poll_errors_total` for alerting.
- **Issue:** Race condition — HARD STOP triggered and reset within same 60-second poll interval
  - **Solution:** This means the flag is set and cleared between polls. The adapter never sees the flag. This is acceptable: the 60-second interval is a maximum propagation delay. If Faiz triggers HARD STOP and immediately resets, the system briefly continued in the pre-trigger state — which is consistent with Faiz's intent to reset.
- **Issue:** Backward compatibility — existing Discord bot tests fail because `HardStopHandler.__init__` now requires `redis_client`
  - **Solution:** Make `redis_client` parameter optional with `None` default. When `redis_client is None`, fall back to in-memory-only mode (existing behavior). This preserves all existing tests and Discord-only operation. Redis integration activates only when a client is provided.

#### Notes
- **CRITICAL SAFETY STEP:** This is a CRITICAL-risk implementation per ADR-002. False negatives (failing to detect HARD STOP) are high severity. Every edge case must be tested. The implementer must NOT skip any test case, NOT weaken trigger patterns, and NOT add "smart" filtering that might suppress genuine HARD STOP messages.
- **Redis Key Schema (exact):**
  - Key: `guinevere:hard_stop` (hash, no TTL — persists until explicit reset)
  - Fields:
    - `triggered`: `"true"` or `"false"` (string, not boolean — Redis hash values are strings)
    - `channel`: `"whatsapp"` or `"discord"` or `""` (originating channel)
    - `timestamp`: ISO 8601 string (e.g., `"2026-06-03T12:00:00.000Z"`)
    - `trigger`: the keyword or regex pattern that activated HARD STOP
    - `reset_by`: Faiz's sender_id who performed reset, or `""` if not yet reset
    - `reset_at`: ISO 8601 reset timestamp, or `""` if not yet reset
- **Polling Mechanism:** Each `ChannelAdapter` runs `HardStopHandler.start_polling(stop_event)` as an `asyncio.Task` during `connect()`. The task loops: `await self.check_remote()` → `await asyncio.sleep(60)`. On `disconnect()`, set `stop_event` to terminate the task. The 60-second interval means worst-case propagation delay is 60 seconds — acceptable for safety (HARD STOP is not a sub-second real-time requirement).
- **Emergency Response Routing:** When HARD STOP is triggered, the neutral response (`get_neutral_response()`) is sent ONLY on the channel that received the triggering message. Other channels stop processing silently on their next poll cycle — they do NOT send a "HARD STOP activated on another channel" message, which could confuse or alarm.
- **Backward Compatibility:** `HardStopHandler(redis_client=None)` preserves existing in-memory-only behavior. All existing Discord tests pass unchanged. Redis integration is opt-in via constructor parameter.
- **Cross-Reference P11-016:** The safe word mechanism (P11-016) uses a SEPARATE Redis flag (`guinevere:safe_word`) for persona de-escalation without full HARD STOP. Both flags are checked in the routing pipeline — HARD STOP takes precedence over safe word.
- **Cross-Reference P11-008:** The routing pipeline must call `await hard_stop_handler.check_remote()` BEFORE any message processing. If `True`, return the neutral response immediately without forwarding to the agent loop, LLM, or persona engine.
- **Faiz-Only Reset:** `authorized_ids` must contain exactly two entries: Faiz's Discord user ID (from `config.OWNER_ID` or equivalent) and Faiz's WhatsApp JID (from P11-002 setup). No other IDs are authorized. This is hardcoded, not configurable at runtime — changing it requires a code change and redeployment.
- **HIGH RISK — Edge Cases:**
  - **Redis unreachable during trigger:** If Redis write fails when HARD STOP is triggered, the local in-memory state still switches to SAFE. The trigger channel gets the neutral response. Other channels continue normally until the next successful Redis write (retry logic: attempt Redis write on every subsequent trigger check). Log error: `logger.error("hard_stop_redis_write_failed", ...)`.
  - **Multiple simultaneous triggers:** If HARD STOP is triggered on both channels simultaneously (unlikely but possible), the Redis flag is set by whichever write completes last. The `trigger` field records the last trigger, which is acceptable — the important thing is `triggered=true`.
  - **Process crash during reset:** If the process crashes between clearing Redis and restoring local state, the Redis flag is cleared but local state may still be SAFE. Next poll cycle reads Redis (flag cleared) and restores NORMAL. Maximum delay: 60 seconds.
