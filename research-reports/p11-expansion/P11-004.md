### Step P11-004: ChannelAdapter Abstract Interface + UnifiedMessage

**Type:** Library / Interface Design
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P11): pending`

**Goal:** Design and define the `ChannelAdapter` abstract base class and `UnifiedMessage` dataclass that serve as the multi-channel abstraction layer. `ChannelAdapter` provides a uniform interface for all messaging channels (Discord, WhatsApp, future Gmail/X). `UnifiedMessage` normalizes incoming messages from any channel into a common format (sender_id, content, timestamp, channel_type, metadata). This is reusable for P12 (Gmail), P13 (X Auto Poster), P14 (Wearable).
**Dependencies:** P5 (Agent Loop — `src/core/services/llm_router.py`, `src/core/services/hard_stop_handler.py` available), P11-001 (project structure created — `src/channels/` directory exists)
**Cost Impact:** $0/month (interface design only; no infrastructure)
**ADR References:** ADR-022 (per-channel contract — ChannelAdapter is the contract enforcement mechanism), ADR-002 (safe word cross-channel — requires channel-agnostic message format so HARD STOP keyword is detected uniformly)
**Acceptance Criteria:** AC-COM-001 (channel abstraction defined — all channels implement `ChannelAdapter` interface), SRS-IR-009 (message dedup across channels — requires unified format with content_hash for deduplication)
**Estimated Time:** 4 hours

#### Context

Currently Guinevere only has Discord as a messaging channel (`src/discord/bot.py` with 22 files). The Discord bot uses discord.py's `commands.Bot` framework with slash commands — there is no natural language processing, no media handling beyond basic embeds, and no conversation context management. The bot responds to explicit commands (`/status`, `/loop-start`, `/surveillance-status`) but does not engage in LLM-powered conversation. For P11 we need a channel-agnostic abstraction layer so that the ConversationalAgent (P11-006) does not need to know which channel a message originated from.

The `ChannelAdapter` abstract base class defines the contract: every channel must implement `connect()`, `disconnect()`, `send_message()`, `to_unified_message()`, and `from_unified_response()`. The `UnifiedMessage` dataclass normalizes all incoming messages into a standard format regardless of whether they arrive via WhatsApp's JID-based addressing (`628123456789@s.whatsapp.net`), Discord's user ID system, or future Gmail email addresses. This unified format includes `sender_id`, `content`, `timestamp`, `channel_type`, and an extensible `metadata` dict for channel-specific fields.

This abstraction is critical for the entire multi-channel roadmap. P12 (Gmail) will implement `GmailAdapter`, P13 (X Auto Poster) will implement `XAdapter`, and P14 (Wearable) will implement `WearableAdapter`. All will produce `UnifiedMessage` objects that flow into the same ConversationalAgent pipeline. Without this step, each future channel would require its own bespoke integration with the agent loop, persona engine, and memory system — tripling the implementation effort for each new channel.

The interface also enables cross-channel features: HARD STOP triggered on WhatsApp propagates to Discord via a shared Redis flag that all adapters poll (ADR-002). Message deduplication across channels uses `content_hash` on `UnifiedMessage` objects (SRS-IR-009). The Discord adapter refactor (future P11-012 or separate step) will implement the same `ChannelAdapter` interface, replacing the direct discord.py event handling with the unified pipeline.

#### Troubleshooting
- **Issue:** `ImportError: cannot import name 'ChannelAdapter' from 'src.channels'`
  - **Solution:** Verify `__init__.py` exports the class. Check that `base.py` is in the correct path and has no syntax errors.
- **Issue:** `TypeError: Can't instantiate abstract class ChannelAdapter` when trying to use directly
  - **Solution:** This is expected behavior — `ChannelAdapter` is abstract. Concrete adapters (WhatsAppAdapter in P11-005) must implement all abstract methods.
- **Issue:** `content_hash` produces different values for same input across runs
  - **Solution:** Ensure SHA-256 input is deterministic — normalize `sender_id` to lowercase, strip whitespace from `content`, and use ISO format for `timestamp`. Do not include mutable metadata in hash computation.
- **Issue:** Redis connection for `check_hard_stop()` fails because adapter initializes before Redis is ready
  - **Solution:** Use lazy Redis connection (connect on first `check_hard_stop()` call, not in `__init__`). Follow the same pattern as `src/core/services/hard_stop_handler.py`.

#### Notes
- This step is the FOUNDATION for the entire multi-channel architecture. P11-005 (WhatsAppAdapter), P12 (GmailAdapter), P13 (XAdapter), P14 (WearableAdapter) all implement `ChannelAdapter`.
- `UnifiedMessage.metadata` is intentionally a `dict` (not a typed dataclass) to accommodate channel-specific fields without bloating the core schema. Each adapter documents its own metadata keys.
- ADR-002 (safe word cross-channel) is enforced via `check_hard_stop()` — every adapter MUST check this before processing a message. If HARD STOP is active, the adapter sends an emergency response and does not route to ConversationalAgent.
- ADR-022 (per-channel contract) maps directly to `ChannelAdapter` — the abstract methods ARE the contract. Any channel that does not implement all methods cannot be registered.
- The `UnifiedResponse` dataclass (outgoing direction) should mirror `UnifiedMessage` with additional fields: `response_text`, `typing_duration_ms`, `split_index` (for multi-bubble responses).
- Cross-reference P11-005 (WhatsAppAdapter implementation) for the first concrete adapter. Cross-reference P11-006 (ConversationalAgent) for how `UnifiedMessage` flows into the LLM pipeline.
- Do NOT implement any concrete adapter in this step. This step is purely the interface definition. Concrete implementations come in P11-005 (WhatsApp) and future steps (Discord refactor, Gmail, X, Wearable).
- The `message_id` field in `UnifiedMessage` must be unique per channel but NOT globally unique — deduplication uses `content_hash`, not `message_id`.
