### Step P9-005: SMS Parsing Pipeline (Unified Regex + Indonesian Decimal)

**Type:** Application
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P9): pending`

**Goal:** Build a unified SMS parser that pops raw SMS from Redis queue, identifies the sending bank via sender/pattern matching, extracts structured transaction fields including Indonesian decimal amounts, and writes normalized records to `financial.transactions`.
**Dependencies:** P9-004 (Tasker webhook endpoint receiving SMS and pushing to Redis `financial.sms_queue`), P9-002 (TransactionRepository CRUD layer), P9-001 (financial schema validated with all classification columns).
**Cost Impact:** $0/month (application logic only; Redis and PostgreSQL already provisioned)
**ADR References:** ADR-023 (Financial Data Integration Strategy — Tasker notification capture, confidence scoring, regex adapter maintenance), ADR-024 (Data Classification — all financial data = CRITICAL), ADR-030 (Redis DB assignments — financial queue on shared Redis instance)
**Acceptance Criteria:** AC-FIN-005 (SMS parsing and transaction storage operational with bank-specific regex patterns)
**Estimated Time:** 4 hours

#### Context

Raw SMS notifications captured by P9-004 arrive in Redis list `financial.sms_queue` as JSON blobs containing `sender`, `body`, `received_at`, and `device_id`. This step builds the parser daemon that continuously polls via `BRPOP`, identifies the issuing bank from the sender field or message body pattern, extracts amount/type/merchant/timestamp using per-bank regex, normalizes Indonesian decimal conventions (Rp1.500.000,75 = 1500000.75), assigns confidence scores per ADR-023 (high for BRI verified, medium for reconstructed BCA/Mandiri/BNI/Jenius), and writes to `financial.transactions` via the TransactionRepository from P9-002. Unparseable SMS land in a dead letter queue (`financial.sms_dead_letter`) for manual review. Parsing errors from regex mismatches or bank format changes are the primary operational risk per ADR-023 — each bank adapter must be independently maintainable and versioned.

#### Troubleshooting

- **Issue:** `BRPOP` hangs indefinitely with empty queue.
  - **Solution:** Consumer loop uses `BRPOP` with 30-second timeout; on timeout, loop logs heartbeat and re-polls. This is normal idle behavior, not a bug.
- **Issue:** BRI regex matched but amount extracted as `None`.
  - **Solution:** Check SMS body encoding — Tasker may send mixed UTF-8/Latin-1. Run body through `unicodedata.normalize("NFKC", body)` before regex matching.
- **Issue:** Duplicate transactions appearing from same SMS.
  - **Solution:** Idempotency key is `SHA256(body + received_at)`. Verify `received_at` precision from Tasker is millisecond-level. If same SMS arrives with different `received_at` timestamps, use `body` hash only and accept first-write-wins.
- **Issue:** Bank format changed (regex returns zero matches for previously working pattern).
  - **Solution:** SMS goes to dead letter queue automatically. Add `confidence < 0.5` flagging log alert. Create a new regex adapter version; do not modify existing adapter without adding test cases for old format. Per ADR-023: regex adapters break silently with app updates — this is expected maintenance burden.

#### Notes

- Each bank parser is a separate class implementing a `BankParser` protocol (`parse(sms_body: str) -> ParsedTransaction | None`). Adding a new bank means adding one class — no changes to the consumer loop.
- Indonesian decimal convention: dots are thousands separators, comma is decimal. `"Rp1.500.000,75"` normalizes to `Decimal("1500000.75")` before PostgreSQL insert (column type `NUMERIC(18,2)`).
- BCA/Mandiri/BNI/Jenius regex patterns are RECONSTRUCTED from documentation. Each must carry a `needs_real_device_verification=True` flag and default `confidence=0.7`. BRI patterns are verified against real device samples and carry `confidence >= 0.9`.
- Consumer runs as a single-threaded asyncio daemon — 1000 SMS/month is well within single-thread capacity. If volume increases, scale horizontally with Redis list sharding.
- No scraping of e-wallet apps per AC-FIN-005 and ADR-023 explicit prohibition. This is notification capture only via Android `NotificationListenerService`.
- Dead letter queue is a Redis list with 7-day TTL. Manual review required for anything that lands here. Alert via Discord if `LLEN financial.sms_dead_letter > 0` for more than 1 hour.
