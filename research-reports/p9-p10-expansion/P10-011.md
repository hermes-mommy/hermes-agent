### Step P10-011: Key Rotation Procedure

**Type:** Security
**Status:** ⬜ Not Started
**Risk:** High
**Git Commit:** `feat(P10): key rotation procedures`

**Goal:** Unified key rotation procedure for SOPS age keys, LLM provider API keys, and database passwords using dual-credential zero-downtime pattern.
**Dependencies:** P0-019 (PostgreSQL + PgBouncer operational), P0-020 (Redis operational), SOPS+age encryption fully configured, LLM provider API keys managed via SOPS
**Cost Impact:** $0/month (procedural, no additional infrastructure)
**ADR References:** ADR-015, ADR-008
**Acceptance Criteria:** AC-SEC-003, AC-SEC-006, AC-FIN-004
**Estimated Time:** 4 hours

#### Context

ADR-015 requires regular secrets rotation with documented procedures, and ADR-008 mandates encryption-at-rest for all credentials. The SecretsRotationRunbook (`docs/20-security/23-SecretsRotationRunbook_v1.0.md`) defines three rotation surfaces: (1) SOPS age keys — annual rotation plus emergency rotation on compromise, (2) LLM provider API keys — quarterly rotation plus emergency, (3) database passwords — quarterly rotation plus emergency. Each uses a dual-credential zero-downtime pattern: create the new credential, deploy it alongside the old, verify the new works, then revoke the old. This approach avoids any service interruption. Emergency rotation (suspected compromise) skips zero-downtime — immediate revoke and replace. All rotations are logged with timestamp, rotated-by identity, and reason. AC-FIN-004 requires cost optimization safety during rotation — no double-billing from overlapping API keys.

#### Commands

```bash
# ============================
# STEP A: SOPS Age Key Rotation
# ============================

# A1. Generate new age key with date-stamped comment
AGE_KEY_FILE="/home/guinevere/.config/sops/age/keys.txt"
NEW_AGE_KEY=$(age-keygen -o /tmp/guinevere-new-age-key.txt 2>&1)
NEW_PUBLIC_KEY=$(grep "public key" /tmp/guinevere-new-age-key.txt | awk '{print $NF}')
echo "# Rotated $(date -I) — previous key archived" | cat - /tmp/guinevere-new-age-key.txt "$AGE_KEY_FILE" > /tmp/merged-keys.txt

# A2. Update all SOPS files with new public key
find /home/guinevere/config/ -name "*.enc.*" -o -name "*.sops.*" | while read f; do
    sops updatekeys --add "$NEW_PUBLIC_KEY" "$f"
done

# A3. Verify decryption works with new key
find /home/guinevere/config/ -name "*.enc.*" -o -name "*.sops.*" | while read f; do
    sops --decrypt "$f" > /dev/null && echo "OK: $f" || echo "FAIL: $f"
done

# A4. Backup old key to secure offline location
PREV_KEY_BACKUP="/home/guinevere/config/key-backups/age-key-$(date +%Y%m%d).txt"
cp "$AGE_KEY_FILE" "$PREV_KEY_BACKUP"
chmod 600 "$PREV_KEY_BACKUP"

# A5. Replace keys file with merged version
mv /tmp/merged-keys.txt "$AGE_KEY_FILE"
chmod 600 "$AGE_KEY_FILE"
rm /tmp/guinevere-new-age-key.txt

# A6. Remove old public key from SOPS files (after confirming all services work)
#    Wait 24 hours before running this to ensure no issues:
OLD_PUBLIC_KEY="age1..."  # Replace with actual old public key
find /home/guinevere/config/ -name "*.enc.*" -o -name "*.sops.*" | while read f; do
    sops updatekeys --rm "$OLD_PUBLIC_KEY" "$f"
done

echo "SOPS age key rotation complete. New public key: $NEW_PUBLIC_KEY"

# ============================
# STEP B: LLM API Key Rotation
# ============================

# B1. Create new API key at provider (example: 9Router)
#     Log into provider dashboard and generate new key
#     Store new key temporarily:
NEW_API_KEY="nr-sk-..."  # Replace with actual new key
PROVIDER="9router"

# B2. Add new key alongside existing in SOPS file
#     Edit .sops.yaml or encrypted env file to include both:
sops /home/guinevere/config/env.secrets.enc.yaml
#     Add: NINEROUTER_API_KEY_NEW: <new_key>
#     Keep: NINEROUTER_API_KEY: <old_key>

# B3. Update application to try new key first, fall back to old
#     This is the dual-credential pattern:
cat >> /home/guinevere/guinevere/src/core/llm_client.py << 'DUALEOF'

# Dual-credential rotation: try NEW key, fall back to OLD
import os
_primary_key = os.getenv("NINEROUTER_API_KEY_NEW") or os.getenv("NINEROUTER_API_KEY")
_fallback_key = os.getenv("NINEROUTER_API_KEY") if os.getenv("NINEROUTER_API_KEY_NEW") else None
DUALEOF

# B4. Restart services to pick up dual credentials
sudo systemctl restart guinevere-api.service guinevere-bot.service guinevere-worker.service

# B5. Verify new key works by checking metrics/logs
#     Check for API call success rates with new key
journalctl -u guinevere-api --since "5 min ago" | grep -i "api.key.rotation"

# B6. Revoke old key at provider (after confirming new key works for 30+ minutes)
#     Log into provider dashboard and revoke old key
#     Remove old key from SOPS file:
sops /home/guinevere/config/env.secrets.enc.yaml
#     Remove: NINEROUTER_API_KEY: <old_key>
#     Rename: NINEROUTER_API_KEY_NEW -> NINEROUTER_API_KEY

# B7. Remove dual-credential fallback code (optional, safe to keep)
#     Restart services again if code changed

echo "$PROVIDER API key rotation complete. Old key revoked."

# ============================
# STEP C: Database Password Rotation
# ============================

# C1. Generate new password
NEW_DB_PASS=$(openssl rand -base64 32)
echo "New DB password generated (stored in memory only)"

# C2. Create new PostgreSQL user with new password (dual-credential)
sudo -u postgres psql << PSQLEOF
CREATE USER guinevere_new WITH PASSWORD '$NEW_DB_PASS';
GRANT guinevere_role TO guinevere_new;
ALTER USER guinevere_new WITH LOGIN;
PSQLEOF

# C3. Update SOPS-encrypted connection strings
#     Add new connection string while keeping old:
sops /home/guinevere/config/env.secrets.enc.yaml
#     Add: DATABASE_URL_NEW: postgresql+asyncpg://guinevere_new:<new_pass>@localhost:5432/guinevere
#     Keep: DATABASE_URL: postgresql+asyncpg://guinevere:<old_pass>@localhost:5432/guinevere

# C4. Update PgBouncer config to include new user
cat >> /etc/pgbouncer/userlist.txt << PBEOF
"guinevere_new" "$NEW_DB_PASS"
PBEOF
sudo systemctl reload pgbouncer

# C5. Update application connection (dual-credential pattern, same as API keys)
#     Application reads DATABASE_URL_NEW first, falls back to DATABASE_URL

# C6. Restart application services
sudo systemctl restart guinevere-api.service guinevere-bot.service guinevere-worker.service

# C7. Verify new credentials work (check DB connection pool metrics)
sudo -u postgres psql -c "SELECT usename, count(*) FROM pg_stat_activity GROUP BY usename;"

# C8. Remove old user after confirming new works (30+ minutes)
sudo -u postgres psql -c "DROP USER IF EXISTS guinevere;"
sudo -u postgres psql -c "ALTER USER guinevere_new RENAME TO guinevere;"

# C9. Clean up SOPS file — remove old connection string, rename new
sops /home/guinevere/config/env.secrets.enc.yaml
#     Remove: DATABASE_URL: ...
#     Rename: DATABASE_URL_NEW -> DATABASE_URL

# C10. Reload pgbouncer to remove old user
sudo systemctl reload pgbouncer

echo "Database password rotation complete."

# ============================
# STEP D: Rotation Schedule Tracking
# ============================

# Update rotation schedule log
cat >> /home/guinevere/config/rotation-schedule.json << ROTEOF
{
  "last_rotations": {
    "sops_age_key": "$(date -I)",
    "ninerouter_api_key": "$(date -I)",
    "database_password": "$(date -I)"
  },
  "next_due": {
    "sops_age_key": "$(date -I -d '+1 year')",
    "ninerouter_api_key": "$(date -I -d '+3 months')",
    "database_password": "$(date -I -d '+3 months')"
  }
}
ROTEOF

# ============================
# STEP E: Emergency Rotation
# ============================

# Emergency rotation (suspected compromise) — SKIP zero-downtime:
# 1. IMMEDIATELY revoke all existing credentials at providers
# 2. Generate all new credentials
# 3. Replace all SOPS files with new credentials
# 4. Restart all services
# 5. Verify services operational
# 6. Log incident with timestamp and reason
# 7. Notify Faiz via Discord direct message

EMERGENCY_REASON="suspected_credential_leak"
echo "EMERGENCY ROTATION: $EMERGENCY_REASON at $(date -Iseconds)" >> /home/guinevere/logs/emergency-rotations.log
# Proceed with steps C1-C10 but SKIP the dual-credential waiting period
# Revoke old credentials FIRST before restarting services
```

#### Troubleshooting

- **Issue:** SOPS decrypt fails after rotation
  - **Solution:** Verify the new age key file at `/home/guinevere/.config/sops/age/keys.txt`. Check that the new public key was added to each SOPS file with `sops updatekeys --add`. If still failing, restore the old key from backup at `/home/guinevere/config/key-backups/` and retry.

- **Issue:** New API key not yet propagated at provider
  - **Solution:** Some providers have a propagation delay (typically 1-5 minutes). Wait 5 minutes and retry. Check provider dashboard to confirm the key status is "Active." If the key shows "Pending," it has not propagated yet.

- **Issue:** Database connection refused after password rotation
  - **Solution:** PgBouncer connection pool may hold stale connections. Flush the pool: `sudo -u postgres psql -p 6432 -c "RECONNECT;"` or reload pgbouncer. If connections still fail, verify the userlist.txt in `/etc/pgbouncer/` has the correct password hash. Use `pb_passwd` to generate the SCRAM-SHA-256 hash required by PgBouncer.

- **Issue:** Dual-credential fallback code causes LLM call failures
  - **Solution:** If the fallback key is also invalid, both attempts fail. Ensure at least one key is valid throughout the rotation window. Check provider dashboard to confirm the "old" key has not been accidentally revoked before the new key is verified.

- **Issue:** Rotation interrupted mid-process leaving partial state
  - **Solution:** The dual-credential pattern is designed to be resilient to interruption. If rotation is interrupted after creating the new credential but before revoking the old, the system continues to work (both credentials exist). Complete the remaining steps: verify new works, revoke old, clean up.

#### Notes

- Emergency rotation (suspected compromise) is the one case where zero-downtime is intentionally violated — security takes precedence over availability. Immediately revoke the compromised credential, replace it, restart services, and accept the brief interruption.
- All rotations MUST be logged with: timestamp (ISO 8601), rotated-by (operator identity), reason (scheduled/emergency), credentials rotated (which surfaces), and verification result (pass/fail).
- Database rotation requires PgBouncer `pool_mode=transaction` (configured in P0-019). This allows connections using different credentials to coexist in the pool during the rotation window. Session-level pooling would cause issues as sessions would pin to a specific user.
- The dual-credential code in the application (trying NEW key, falling back to OLD) should be a permanent design pattern, not temporary code. This makes all future rotations seamless. Consider making it a generic `RotatingCredential` utility class.
- SOPS age key backup: store the old key file in at least two offline locations (encrypted USB drive, password manager secure note). If the old key is lost AND the new key fails, all SOPS-encrypted files become permanently unreadable.
