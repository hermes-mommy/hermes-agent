### Step P10-008: GitHub Actions CI Pipeline

**Type:** Infrastructure
**Status:** ⬜ Not Started
**Risk:** Medium
**Git Commit:** `feat(P10): GitHub Actions CI pipeline`

**Goal:** CI workflow running on every push and PR with ruff lint, mypy type check, pytest with coverage, bandit security scan, and PostgreSQL + Redis service containers.
**Dependencies:** None (Phase 10 groundwork); P10-007 (self-deploy) depends on this step passing.
**Cost Impact:** $0/month (GitHub-hosted runners, free tier: 2000 min/month)
**ADR References:** ADR-016, ADR-029
**Acceptance Criteria:** AC-OPS-005, AC-OPS-006
**Estimated Time:** 4 hours

#### Context

ADR-016 mandates a CI gate before any deployment to main. ADR-029 requires automated testing for the safety-critical classification of Guinevere systems. The CI workflow must serve as the single source of truth for code quality before P10-007 (self-deploy via systemd timer) can trigger. All checks must pass on every push and pull request to `main` and `develop` branches. The workflow uses GitHub-hosted `ubuntu-latest` runners with Docker service containers for PostgreSQL 16 and Redis 7 integration tests.

#### Pre-flight Checks
- [ ] GitHub repository `github.com/fazulfi/guinevere` exists and is accessible
- [ ] `pyproject.toml` or `requirements.txt` has `[dev]` extras defined (ruff, mypy, pytest, pytest-cov, bandit, types-* stubs)
- [ ] `alembic.ini` and migration directory `migrations/` are present in repo
- [ ] Test suite exists at `tests/` with at least baseline integration tests
- [ ] GitHub Actions is enabled for the repository (Settings > Actions > Allow all actions)
- [ ] Branch protection rules can be configured on `main` (Settings > Branches > Add rule)

#### Commands

```bash
# 1. Create CI workflow directory
mkdir -p .github/workflows

# 2. Write the CI workflow file
cat > .github/workflows/ci.yml << 'CIEOF'
name: Guinevere CI

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main, develop]
  workflow_dispatch:

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint-and-type:
    name: Lint & Type Check
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
      - name: Install dependencies
        run: pip install -e ".[dev]"
      - name: ruff lint
        run: ruff check src/ --output-format=github
      - name: mypy type check
        run: mypy src/ --strict --show-error-codes --no-error-summary

  test:
    name: Test (Pytest + Coverage)
    runs-on: ubuntu-latest
    timeout-minutes: 15
    needs: lint-and-type
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_DB: guinevere_test
          POSTGRES_USER: guinevere
          POSTGRES_PASSWORD: testpass
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10
      redis:
        image: redis:7-alpine
        ports:
          - 6379:6379
        options: >-
          --health-cmd "redis-cli ping"
          --health-interval 5s
          --health-timeout 5s
          --health-retries 5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
      - name: Install dependencies
        run: pip install -e ".[dev,test]"
      - name: Run alembic migrations
        env:
          DATABASE_URL: postgresql+asyncpg://guinevere:testpass@localhost:5432/guinevere_test
          REDIS_URL: redis://localhost:6379/0
        run: alembic upgrade head
      - name: Run pytest with coverage
        env:
          DATABASE_URL: postgresql+asyncpg://guinevere:testpass@localhost:5432/guinevere_test
          REDIS_URL: redis://localhost:6379/0
          ENV: ci
        run: pytest tests/ -v --cov=src --cov-report=term-missing --cov-report=xml --cov-fail-under=80 --timeout=30
      - name: Upload coverage to artifact
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: coverage.xml
          retention-days: 7

  security:
    name: Security Scan
    runs-on: ubuntu-latest
    timeout-minutes: 5
    needs: lint-and-type
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
      - name: Install dependencies
        run: pip install bandit
      - name: bandit security scan
        run: bandit -r src/ -ll -f sarif -o bandit-results.sarif
        continue-on-error: true
      - name: Upload bandit SARIF
        if: always()
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: bandit-results.sarif
          category: bandit
      - name: Check bandit high-severity findings
        run: |
          bandit -r src/ -ll -f json -o /tmp/bandit.json
          python -c "
          import json,sys
          r=json.load(open('/tmp/bandit.json'))
          high=[i for i in r.get('results',[]) if i.get('issue_severity','').lower() in ('high',)]
          if high:
              print(f'FAIL: {len(high)} high-severity finding(s)')
              sys.exit(1)
          print('PASS: No high-severity findings')
          "
CIEOF

# 3. Stage, commit, and push the CI workflow
git add .github/workflows/ci.yml
git commit -m "feat(P10): add GitHub Actions CI pipeline"

# 4. Push to trigger first CI run
git push origin main

# 5. Configure branch protection on main (GitHub Settings > Branches)
#    - Require status checks: lint-and-type, test, security
#    - Require branches to be up to date before merging
#    - Do not allow bypassing the above settings
```

#### Troubleshooting

- **Issue:** mypy reports errors from missing third-party stubs
  - **Solution:** Add `types-redis`, `types-requests`, `types-python-dateutil` to `[dev]` extras in `pyproject.toml`. Run `pip install -e ".[dev]"` to verify.

- **Issue:** pytest fixture timeout during service container startup
  - **Solution:** Increase `--health-retries` on PostgreSQL service container from 10 to 20 (maximum 100-second wait). Adjust `--timeout` flag on pytest to 60 seconds for slow integration tests.

- **Issue:** bandit reports false positives (e.g., subprocess usage in deploy script)
  - **Solution:** Add `# nosec B404` comment with justification on the specific line. Document each exclusion in `docs/setup-evidence/P10/STEP-P10-008/bandit-exclusions.md`.

- **Issue:** `pip install` fails due to missing system dependencies
  - **Solution:** Add `sudo apt-get update && sudo apt-get install -y libpq-dev` before `pip install`. The `ubuntu-latest` runner image includes most common libraries, but asyncpg may need `libpq-dev`.

- **Issue:** Coverage falls below 80% threshold
  - **Solution:** Do NOT lower the threshold. Identify uncovered paths with `--cov-report=term-missing`, file follow-up task to add tests for uncovered critical paths. Temporarily accept failure if coverage gap is in non-critical code paths with documented justification.

#### Notes

- CI timeout target: under 10 minutes total (lint-and-type + test run in parallel with security). Concurrency group prevents wasted minutes on iterative pushes.
- Coverage threshold: 80% minimum. If codebase coverage is below 80% at time of implementation, set threshold to current value + 5% and file a P10 follow-up task to reach 80%.
- Service containers use ephemeral PostgreSQL 16 and Redis 7 instances. No data persists between CI runs. Database is created fresh each run via `POSTGRES_DB` env var.
- The `ubuntu-latest` runner (currently Ubuntu 24.04) includes Python 3.12 and Docker out of the box. GitHub free tier provides 2000 minutes/month — CI jobs consume roughly 3 minutes per run (~660 runs/month free tier capacity).
- Branch protection must be configured manually via GitHub Settings UI. This cannot be automated via workflow file alone. Document the exact settings in evidence.
- SARIF upload to GitHub Code Scanning provides in-UI security findings without blocking the pipeline. The explicit high-severity check after bandit ensures critical issues still block CI.
