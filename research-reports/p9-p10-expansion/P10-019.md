### Step P10-019: Load Testing (k6)

**Type:** Testing
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P10): pending`

**Goal:** Load test the Guinevere API using k6 to validate p95 latency < 500ms under realistic load patterns, establish performance baseline, and identify breaking points before production use.
**Dependencies:** P10-002 (PostgreSQL Tuning), P10-003 (Redis Tuning), P10-017 (Pool Monitoring). k6 installed on a test machine within Tailscale network. All Guinevere services running under systemd.
**Cost Impact:** $0/month (k6 is open-source, test executed from existing Tailscale machine)
**ADR References:** ADR-018 (Defense-in-Depth Architecture)
**Acceptance Criteria:** AC-CORE-005 (System meets availability SLO -- 99.5% uptime with p95 latency < 500ms for API endpoints)
**Estimated Time:** 4 hours

#### Context

Research findings (Phase 9 expansion) recommend k6 over locust for load testing: JavaScript test scripts (familiar syntax), lower resource overhead on the test machine, built-in Prometheus metrics export, and native HTML report generation. Three test scenarios: 1) Normal load: 10 concurrent users for 5 minutes (simulates typical single-operator usage), 2) Peak load: 50 concurrent users for 5 minutes (simulates heavy usage burst), 3) Stress test: ramp from 1 to 200 concurrent users to identify breaking point. Targets: p95 < 500ms for standard API endpoints, p95 < 2s for /finance report endpoint (heavy PostgreSQL query), error rate < 1%, zero OOM kills, CPU sustained < 80%. Test from inside Tailscale network (realistic access pattern). Monitor pool metrics (P10-017) and system resources during test. Results establish the baseline SLO for AC-CORE-005.

import http from "k6/http";
import { check, sleep, group } from "k6";
import { Rate, Trend, Counter } from "k6/metrics";

// Custom metrics
const errorRate = new Rate("errors");
const healthCheckDuration = new Trend("health_check_duration");
const apiLatency = new Trend("api_latency");
const financeLatency = new Trend("finance_latency");

// Configuration from environment or defaults
const BASE_URL = __ENV.BASE_URL || "http://100.x.x.x:NNNN";
const HEALTH_URL = `${BASE_URL}/health/deep`;
const SHALLOW_URL = `${BASE_URL}/health/shallow`;

// --- Scenario 1: Normal Load (10 VUs, 5 min) ---
export let normal_load_options = {
  scenarios: {
    normal_load: {
      executor: "constant-vus",
      vus: 10,
      duration: "5m",
      exec: "normalLoad",
    },
  },
  thresholds: {
    http_req_duration: ["p(95)<500", "p(99)<1000"],
    errors: ["rate<0.01"],
    "http_req_duration{name:financeReport}": ["p(95)<2000"],
  },
};

export function normalLoad() {
  group("Health Checks", function () {
    let shallow = http.get(SHALLOW_URL, { tags: { name: "shallowHealth" } });
    check(shallow, { "shallow 200": (r) => r.status === 200 });
    healthCheckDuration.add(shallow.timings.duration);

    let deep = http.get(HEALTH_URL, { tags: { name: "deepHealth" } });
    check(deep, { "deep 200": (r) => r.status === 200 });
    healthCheckDuration.add(deep.timings.duration);
    errorRate.add(deep.status !== 200);
  });

  group("API Endpoints", function () {
    let resp = http.get(`${BASE_URL}/api/v1/status`, { tags: { name: "apiStatus" } });
    apiLatency.add(resp.timings.duration);
    errorRate.add(resp.status >= 400);
  });

  group("Finance Report (simulated)", function () {
    let resp = http.get(`${BASE_URL}/finance/report`, {
      tags: { name: "financeReport" },
      timeout: "5s",
    });
    financeLatency.add(resp.timings.duration);
    // Finance report may return 404 if not configured -- that's OK for load test
    errorRate.add(resp.status >= 500);
  });

  sleep(1);
}

// --- Scenario 2: Peak Load (50 VUs, 5 min) ---
export let peak_load_options = {
  scenarios: {
    peak_load: {
      executor: "constant-vus",
      vus: 50,
      duration: "5m",
      exec: "peakLoad",
    },
  },
  thresholds: {
    http_req_duration: ["p(95)<500", "p(99)<2000"],
    errors: ["rate<0.01"],
    "http_req_duration{name:financeReport}": ["p(95)<3000"],
  },
};

export function peakLoad() {
  // Same as normalLoad but with 50 concurrent users
  normalLoad();
}

// --- Scenario 3: Stress Test (ramp to failure) ---
export let stress_test_options = {
  scenarios: {
    stress_test: {
      executor: "ramping-vus",
      startVUs: 1,
      stages: [
        { duration: "2m", target: 50 },
        { duration: "3m", target: 50 },
        { duration: "2m", target: 100 },
        { duration: "3m", target: 100 },
        { duration: "2m", target: 150 },
        { duration: "3m", target: 150 },
        { duration: "2m", target: 200 },
        { duration: "3m", target: 200 },
        { duration: "2m", target: 0 },
      ],
      exec: "stressTest",
    },
  },
};

export function stressTest() {
  let resp = http.get(SHALLOW_URL);
  errorRate.add(resp.status !== 200);

  if (resp.status === 200) {
    sleep(0.5);
  } else {
    // When errors start, slow down to avoid cascading
    sleep(2);
  }
}

// --- Summary handler ---
export function handleSummary(data) {
  return {
    "docs/setup-evidence/P10/STEP-P10-019/k6-summary.json": JSON.stringify(data, null, 2),
    stdout: `
=== K6 Load Test Summary ===
Duration: ${data.state.testRunDurationMs / 1000}s
Total Requests: ${data.metrics.http_reqs.values.count || 0}
Error Rate: ${(data.metrics.errors ? data.metrics.errors.values.rate * 100 : 0).toFixed(2)}%

HTTP Request Duration (ms):
  avg: ${data.metrics.http_req_duration.values.avg.toFixed(2)}
  p50: ${data.metrics.http_req_duration.values.med.toFixed(2)}
  p90: ${data.metrics.http_req_duration.values["p(90)"].toFixed(2)}
  p95: ${data.metrics.http_req_duration.values["p(95)"].toFixed(2)}
  p99: ${data.metrics.http_req_duration.values["p(99)"].toFixed(2)}
  max: ${data.metrics.http_req_duration.values.max.toFixed(2)}
===========================
`,
  };
}

    pg_waiting=$(psql -h 127.0.0.1 -p 6432 -U pgbouncer -d pgbouncer -t -c "SELECT SUM(cl_waiting) FROM (SELECT cl_waiting FROM show_pools WHERE database != 'pgbouncer') t" 2>/dev/null || echo "0")

    echo "$(date +%H:%M:%S),$pg_active,$pg_waiting,$redis_conn,$redis_mem"
    sleep 10
  done

#### Troubleshooting
- **Issue:** k6 OOM on test machine (not the target VPS)
  - **Solution:** Reduce VUs or duration. If test machine is low-spec (1GB RAM), limit to 50 VUs max. Use `--compatibility-mode=base` to reduce k6 overhead. Test machine should have at least 2GB RAM for 50+ VUs
- **Issue:** "connection refused" errors at the start of peak load test
  - **Solution:** Check rate limiter (P10-013) is not blocking the test traffic. If rate limiter triggers, either: 1) temporarily disable during load test: `redis-cli DEL "ratelimit:*"`, or 2) configure k6 scenarios to stay within rate limits. Remember to re-enable after test
- **Issue:** p95 latency exceeds target even at 10 VUs
  - **Solution:** Check pg_stat_statements for slow queries dominating. Check if PostgreSQL is doing a CHECKPOINT or VACUUM during test. Check if Redis eviction is occurring and causing latency spikes. Check CPU throttling on VPS (shared CPU can cap performance)
- **Issue:** /finance/report endpoint returns 404 throughout test
  - **Solution:** The finance report endpoint may not be implemented yet (P9 phase). k6 error rate metric only counts >=500 status codes. 404 is treated as "endpoint not found" and not counted as error. Verify with: `curl -s -o /dev/null -w "%{http_code}" http://100.x.x.x:NNNN/finance/report`
- **Issue:** Stress test crashes Guinevere services (OOM kill)
  - **Solution:** Increase MemoryMax in systemd service file (see P10-004). Reduce connection pool sizes. Add request queuing. This is valuable data -- the breaking point IS the test result. Document the VU count at crash and recovery behavior
- **Issue:** k6 `--out json` file is empty or corrupted
  - **Solution:** Ensure the output directory exists: `mkdir -p docs/setup-evidence/P10/STEP-P10-019/`. Check disk space on test machine. Use `--out csv=` as fallback output format

#### Notes
- Load test from INSIDE Tailscale network (not public internet). This represents realistic access patterns -- Guinevere is accessed via Tailscale only (ADR-019)
- Never load test from public internet. Shared VPS: schedule during low-usage window to avoid impacting Aizanta services. Coordinate with Aizanta operator if possible
- The k6 JSON output files can be imported into Grafana for visualization. Alternatively, export to CSV and use pandas/matplotlib for custom analysis
- Results establish the BASELINE for AC-CORE-005 (99.5% availability with p95 < 500ms). All future performance changes are compared against this baseline
- If p95 targets cannot be met at 10 VUs, this is a blocking issue -- performance optimization needed before MVP gate (P10-021). Common fixes: add database query indexes, increase PgBouncer pool size, enable Redis pipelining, add FastAPI response caching
- The stress test "ramp to failure" identifies the ceiling. This drives capacity planning: when do we need to scale up VPS, add read replicas, or shard Redis?
- k6 scenarios can be added to CI pipeline (P10-007/009) as a performance regression gate. Use `k6 run --vus 10 --duration 1m` for CI (short run)
- Resource monitoring (CPU, memory, pool metrics) is captured during test for correlation: did latency spike because of CPU? Pool exhaustion? Disk I/O?
