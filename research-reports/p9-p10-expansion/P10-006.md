### Step P10-006: Disaster Recovery Drill

**Type:** Testing
**Status:** Not Started
**Risk:** High
**Git Commit:** `feat(P10): pending`

**Goal:** Simulate complete VPS failure and restore Guinevere from backup within RTO (4 hours), validating the full disaster recovery procedure end-to-end and producing a postmortem with improvement recommendations.
**Dependencies:** P10-005 complete (backup test passed — S3 and R2 uploads verified, restore procedure validated), DR plan reviewed (`docs/40-operations/43-DisasterRecoveryPlan_v1.0.md`), Faiz notified and drill window approved.
**Cost Impact:** $0/month (uses existing test infrastructure, no permanent new resources)
**ADR References:** ADR-025 (Backup Strategy), ADR-032 (Dual-Provider Backup)
**Acceptance Criteria:** AC-OPS-003 (Full system restore within 4-hour RTO from backup), AC-OPS-004 (Incident handling produces evidence, timeline, containment, recovery, and postmortem)
**Estimated Time:** 6 hours

#### Context

Annual disaster recovery drill required for production readiness. Simulates worst-case scenario: the VPS (hostdata.id 4C/16GB, Ubuntu 24.04) becomes completely unavailable — all services down, no SSH access, no Tailscale connectivity. Recovery procedure follows the DR plan at `docs/40-operations/43-DisasterRecoveryPlan_v1.0.md`: 1) Provision replacement VPS (or use isolated test environment on same VPS), 2) Install base dependencies (Python, PostgreSQL, Redis, systemd service files), 3) Restore from the latest backup (S3 primary, R2 fallback), 4) Verify all services operational, 5) Document complete timeline with timestamps. RTO target: 4 hours (AC-OPS-003). RPO target: 24 hours (acceptable data loss window). Incident handling per AC-OPS-004: produces evidence, detailed timeline, containment actions, recovery steps, and a formal postmortem filed within 24 hours. Shared VPS constraint: drill must NOT impact Aizanta services running on the same host — use isolated ports, directories, and service names.

#### Commands

```bash

# PHASE 1: SIMULATE FAILURE
# ============================================================

# 1. Document drill start time
echo "DR_DRILL_START=$(date -Iseconds)" \
  > docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt
echo "DRILL_TYPE=Simulated VPS Failure (Complete Outage)" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt

# 2. Record pre-drill state (what's running, what data exists)
systemctl list-units --type=service --state=running | grep guinevere \
  > docs/setup-evidence/P10/STEP-P10-006/pre-drill-running-services.txt
psql -U guinevere -h localhost -d guinevere \
  -c "SELECT schemaname, tablename, n_live_tup FROM pg_stat_user_tables ORDER BY schemaname, tablename" \
  > docs/setup-evidence/P10/STEP-P10-006/pre-drill-table-counts.txt
redis-cli -p 6380 INFO keyspace \
  > docs/setup-evidence/P10/STEP-P10-006/pre-drill-redis-keyspace.txt

# 3. Simulate failure: stop all Guinevere services (DO NOT stop PostgreSQL/Redis — those are shared with Aizanta)
echo "$(date -Iseconds): Stopping all Guinevere services" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt
for svc in $(systemctl list-units --type=service --no-legend | grep guinevere | awk '{print $1}'); do
  echo "  Stopping $svc"
  systemctl stop "$svc"
done
echo "$(date -Iseconds): All Guinevere services STOPPED — simulating VPS failure" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt

# ============================================================
# PHASE 2: RECOVERY FROM BACKUP
# ============================================================

# 4. Create isolated recovery environment (simulating new VPS provisioning)
RESTORE_BASE="/tmp/dr-drill"
mkdir -p "${RESTORE_BASE}/pgdata" "${RESTORE_BASE}/redis" \
  "${RESTORE_BASE}/configs" "${RESTORE_BASE}/app"

echo "$(date -Iseconds): Recovery environment created at ${RESTORE_BASE}" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt

# 5. Download backup from S3 (primary — idcloudhost Jakarta)
echo "$(date -Iseconds): Downloading backup from S3" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt
LATEST_BACKUP=$(aws s3 ls s3://guinevere-backups/ \
  --endpoint-url https://s3.idcloudhost.com \
  | sort | tail -1 | awk '{print $2}')
aws s3 sync "s3://guinevere-backups/${LATEST_BACKUP}" \
  "${RESTORE_BASE}/backup/" \
  --endpoint-url https://s3.idcloudhost.com \
  2>&1 | tee docs/setup-evidence/P10/STEP-P10-006/s3-download-output.txt

# 6. If S3 download fails, fall back to R2 (Cloudflare — secondary)
if [ ! -f "${RESTORE_BASE}/backup/postgresql-"*.dump ]; then
  echo "$(date -Iseconds): S3 download failed — falling back to R2" \
    >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt
  rclone sync "r2:guinevere-backups/${LATEST_BACKUP}" \
    "${RESTORE_BASE}/backup/" \
    --progress \
    2>&1 | tee docs/setup-evidence/P10/STEP-P10-006/r2-download-output.txt
fi

echo "$(date -Iseconds): Backup download complete" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt

# 7. Install base dependencies (simulating fresh VPS)
#    Note: On shared VPS, dependencies are already installed. On a real new VPS:
#    apt update && apt install -y python3.12 python3.12-venv postgresql-client-16 redis-tools git curl
#    This step is SKIPPED on shared VPS but DOCUMENTED as a real step
echo "$(date -Iseconds): Base dependency check (skip on shared VPS — already present)" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt

# 8. Restore PostgreSQL to isolated test cluster
echo "$(date -Iseconds): Starting PostgreSQL restore" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt
export PGDATA="${RESTORE_BASE}/pgdata"
initdb -D "${PGDATA}" --username=guinevere
pg_ctl -D "${PGDATA}" -l "${RESTORE_BASE}/pg-restore.log" start -o "-p 5433"
sleep 5
createdb -p 5433 -U guinevere guinevere_restore
psql -p 5433 -U guinevere -d guinevere_restore \
  -c "CREATE EXTENSION IF NOT EXISTS timescaledb"
psql -p 5433 -U guinevere -d guinevere_restore \
  -c "CREATE EXTENSION IF NOT EXISTS vector"

# Restore the database dump
pg_restore -p 5433 -U guinevere -d guinevere_restore \
  --verbose --no-owner --no-acl -j 2 \
  "${RESTORE_BASE}/backup/postgresql-"*.dump \
  2>&1 | tee docs/setup-evidence/P10/STEP-P10-006/pg-restore-output.txt

echo "$(date -Iseconds): PostgreSQL restore complete" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt

# 9. Restore Redis to isolated test instance
echo "$(date -Iseconds): Starting Redis restore" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt
redis-server --port 6381 --dir "${RESTORE_BASE}/redis" --daemonize yes
sleep 2
cp "${RESTORE_BASE}/backup/redis-"*.rdb "${RESTORE_BASE}/redis/dump.rdb"
redis-cli -p 6381 SHUTDOWN NOSAVE
redis-server --port 6381 --dir "${RESTORE_BASE}/redis" --daemonize yes
sleep 2
redis-cli -p 6381 PING && echo "Redis restore: OK" || echo "Redis restore: FAILED"
echo "$(date -Iseconds): Redis restore complete" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt

# 10. Deploy application from Git
echo "$(date -Iseconds): Deploying application from Git" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt
cd "${RESTORE_BASE}/app"
git clone https://github.com/faizz/guinevere.git .
uv sync --frozen
echo "$(date -Iseconds): Application deployed" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt

# 11. Restore encrypted configuration files
echo "$(date -Iseconds): Restoring configuration files" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt
sops --decrypt "${RESTORE_BASE}/backup/configs-"*.tar.gz.enc \
  > "${RESTORE_BASE}/configs/restored-configs.tar.gz"
tar -xzf "${RESTORE_BASE}/configs/restored-configs.tar.gz" \
  -C "${RESTORE_BASE}/configs/"
# Verify critical configs exist
ls -la "${RESTORE_BASE}/configs/etc/guinevere/" \
  > docs/setup-evidence/P10/STEP-P10-006/configs-restored.txt
echo "$(date -Iseconds): Configuration files restored" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt

# 12. Application health check — test endpoints
echo "$(date -Iseconds): Running health checks" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt

# DB connectivity
psql -p 5433 -U guinevere -d guinevere_restore \
  -c "SELECT 1 AS db_connectivity" \
  > docs/setup-evidence/P10/STEP-P10-006/health-check-db.txt 2>&1

# Redis connectivity
redis-cli -p 6381 PING \
  > docs/setup-evidence/P10/STEP-P10-006/health-check-redis.txt 2>&1

# Data integrity — compare key metrics with pre-drill state
PG_ROWS_AFTER=$(psql -p 5433 -U guinevere -d guinevere_restore \
  -t -c "SELECT count(*) FROM financial.transactions")
REDIS_KEYS_AFTER=$(redis-cli -p 6381 DBSIZE)

  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt
echo "REDIS_KEYS_RESTORED=${REDIS_KEYS_AFTER}" \
  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt

# 13. Document drill completion

  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt

# Calculate total duration
START_SEC=$(date -d "$(grep DR_DRILL_START docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt | cut -d'=' -f2)" +%s)
END_SEC=$(date -d "$(grep DR_DRILL_END docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt | cut -d'=' -f2)" +%s)

  >> docs/setup-evidence/P10/STEP-P10-006/drill-timeline.txt
```

#### Troubleshooting
- **Issue:** S3 download fails — backup not found or access denied
  - **Solution:** Trigger R2 fallback immediately (step 6). If R2 also fails, the backup is unrecoverable — this is a CRITICAL finding. Verify credentials, bucket policies, and backup schedule. Escalate to Faiz immediately
- **Issue:** PostgreSQL restore fails — "role 'guinevere' does not exist"
  - **Solution:** Create the role in the test cluster: `createuser -p 5433 -s guinevere`. pg_restore requires the role to exist before restoring objects owned by it
- **Issue:** TimescaleDB extension not available in test cluster — `CREATE EXTENSION timescaledb` fails
  - **Solution:** Install TimescaleDB on the test environment or add it to shared_preload_libraries in the test postgresql.conf. If not possible, skip hypertable data restore and document the gap
- **Issue:** Restore time exceeding 4 hours — backup too large, network too slow, or disk I/O bottleneck
  - **Solution:** For the drill: document the bottleneck and stop if > 6 hours. For future DR: consider incremental backups (WAL archiving) to reduce restore time, upgrade network bandwidth, or increase pg_restore parallelism (`-j 4`)
- **Issue:** Aizanta services disrupted during drill — port conflict or resource contention
  - **Solution:** Immediately stop test instances (step 14) and restart Aizanta services. This is why we use separate ports (5433, 6381, 8081) — verify they don't conflict before starting

#### Notes
- DR drill MUST be scheduled during a low-usage window with Faiz's explicit approval. The drill temporarily stops all Guinevere services (step 3) — this is a controlled outage
- Shared VPS: the drill does NOT stop PostgreSQL, Redis, or any Aizanta services. Only Guinevere application services are stopped. Database and Redis are shared infrastructure — we simulate their unavailability by restoring to separate test instances
- If RTO > 4 hours, identify bottlenecks and create a concrete improvement plan in the postmortem. Common bottlenecks: backup download time (network), pg_restore speed (I/O), missing dependencies (documentation gap)
- RPO of 24 hours means the latest backup must be no older than 24 hours. If backup age > 24 hours, this is a FAIL for RPO. The backup cron job (daily) should ensure this
- Postmortem must be filed within 24 hours per AC-OPS-004. It must include: detailed timeline, what worked, what didn't, root causes, and concrete action items with owners and deadlines
- The DR plan at `docs/40-operations/43-DisasterRecoveryPlan_v1.0.md` is the authoritative reference. If the drill reveals gaps in the plan, update the plan as an action item in the postmortem
- This drill simulates a complete VPS failure. A real DR would also involve DNS/domain failover (Caddy config), Tailscale reconnection, and Discord bot reconnection — these are noted but may not be fully testable in a drill environment
