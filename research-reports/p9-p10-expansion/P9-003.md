#### Context

Budget enforcement is the primary control mechanism for Guinevere's $30/month hard cap. The `financial.budget_categories` table is the PostgreSQL counterpart to the existing Redis `BudgetEnforcer` class (which uses Redis DB5 keys for real-time fast-path checks). Each category row defines a monthly spending limit, an alert threshold percentage that triggers Discord notifications, a freeze threshold percentage that blocks non-critical autonomous work, and a `current_spend` field maintained by a PostgreSQL trigger that sums transactions in real time. Safety-critical spending categories (backup, secrets, monitoring) are exempt from freeze per AC-FIN-004 — their `freeze_threshold_pct` is set to NULL rather than 100.

The alembic migration file (`alembic/versions/XXXX_create_budget_categories_table.py`) must include this SQL block:

```sql
-- Create budget_categories table
CREATE TABLE financial.budget_categories (
    id              UUID            PRIMARY KEY DEFAULT gen_random_uuid(),
    category_name   VARCHAR(64)     NOT NULL UNIQUE,
    monthly_limit   NUMERIC(15,2)   NOT NULL CHECK (monthly_limit >= 0),
    alert_threshold_pct NUMERIC(5,2) NOT NULL DEFAULT 80.00
                        CHECK (alert_threshold_pct BETWEEN 0 AND 100),
    freeze_threshold_pct NUMERIC(5,2)
                        CHECK (freeze_threshold_pct IS NULL OR freeze_threshold_pct BETWEEN 0 AND 100),
    current_spend   NUMERIC(15,2)   NOT NULL DEFAULT 0.00,
    last_reset      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    is_frozen       BOOLEAN         NOT NULL DEFAULT FALSE,
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    classification_level VARCHAR(16) NOT NULL DEFAULT 'CRITICAL',
    data_owner      VARCHAR(64)     NOT NULL DEFAULT 'faiz',
    encryption_key_id VARCHAR(128),
    classified_at   TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    classified_by   VARCHAR(64)     NOT NULL DEFAULT 'system'
);

-- Trigger function: recompute current_spend from transactions hypertable
CREATE OR REPLACE FUNCTION financial.update_budget_current_spend()
RETURNS TRIGGER AS $$
BEGIN
    UPDATE financial.budget_categories b
    SET current_spend = COALESCE(
        (SELECT SUM(t.parsed_amount)
         FROM financial.transactions t
         WHERE t.category = b.category_name
           AND t.transaction_type = 'debit'
           AND DATE_TRUNC('month', t.created_at) = DATE_TRUNC('month', NOW())),
        0.00
    ),
    updated_at = NOW();
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

-- Attach trigger to transactions table (fires on INSERT/UPDATE/DELETE)
DROP TRIGGER IF EXISTS trg_budget_recalc ON financial.transactions;
CREATE TRIGGER trg_budget_recalc
    AFTER INSERT OR UPDATE OR DELETE ON financial.transactions
    FOR EACH STATEMENT
    EXECUTE FUNCTION financial.update_budget_current_spend();

-- Seed 8 default budget categories (IDR amounts for Indonesian cost-of-living)
INSERT INTO financial.budget_categories (category_name, monthly_limit, alert_threshold_pct, freeze_threshold_pct) VALUES
    ('food',          500000,  80, 100),
    ('transport',     300000,  80, 100),
    ('subscriptions', 200000,  80, 100),
    ('utilities',     400000,  80, 100),

    ('llm_costs',     500000,  80, 100),
    ('infrastructure',200000,  80, NULL),  -- exempt from freeze (backup, secrets, monitoring)
    ('other',         250000,  80, 100)
ON CONFLICT (category_name) DO NOTHING;
```

#### Troubleshooting
- **Issue:** Trigger `trg_budget_recalc` fails because `financial.transactions` is a hypertable
  - **Solution:** TimescaleDB supports AFTER triggers on hypertables but not BEFORE triggers. The trigger defined above uses AFTER, which IS supported. If you encounter issues, verify TimescaleDB version >= 2.5: `SELECT extversion FROM pg_extension WHERE extname='timescaledb'`
- **Issue:** Seed INSERT conflicts — categories already exist from a previous run
  - **Solution:** The `ON CONFLICT (category_name) DO NOTHING` clause handles this. If it still fails, check for case-sensitivity: `SELECT category_name FROM financial.budget_categories`
- **Issue:** `current_spend` stays at 0 after inserting a transaction
  - **Solution:** Verify trigger is attached: `SELECT tgname FROM pg_trigger WHERE tgrelid = 'financial.transactions'::regclass`. Check that `DATE_TRUNC('month', transaction.created_at)` matches the current month
- **Issue:** Redis `BudgetEnforcer` uses different category names than PostgreSQL seed data
  - **Solution:** Sync names in P9-006 when building the bridge between Redis and PostgreSQL budget state

#### Notes
- Budget freeze at 100% triggers autonomous freeze of non-critical work per AC-FIN-002 via the `BudgetEnforcer` class (Redis DB5). PostgreSQL trigger provides the authoritative `current_spend` value; Redis provides the fast-path enforcement
- Safety-critical categories (infrastructure = backup, secrets, monitoring) use `freeze_threshold_pct = NULL` to exempt them from freeze per AC-FIN-004 — LLM calls continue even during budget freeze for these operational needs
- Categories use IDR amounts: Rp 500,000 (~$30) for `llm_costs`, Rp 200,000 (~$12) for `infrastructure`. The $30/month hard cap is the sum ceiling enforced at application layer
- The trigger fires on `FOR EACH STATEMENT` rather than `FOR EACH ROW` to avoid performance degradation during batch inserts (P9-005 bulk parsing may insert many transactions at once)
- `last_reset` tracks monthly rollover; a scheduled job (P9-010) will reset `current_spend` to 0 and update `last_reset` on the 1st of each month
- All budget data = CRITICAL classification, encrypted at rest via SOPS+age (ADR-015). PostgreSQL column-level encryption will be applied in P9-011
