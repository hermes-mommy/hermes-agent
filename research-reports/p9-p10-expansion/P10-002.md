### Step P10-002: PostgreSQL Performance Tuning

**Type:** Infrastructure
**Status:** Not Started
**Risk:** Medium
**Git Commit:** `feat(P10): pending`

**Goal:** Optimize PostgreSQL 16 performance using pg_stat_statements analysis, index optimization, VACUUM/ANALYZE, and configuration tuning for the observed Guinevere workload including TimescaleDB hypertables and pgvector indexes.
**Dependencies:** P0 complete (PostgreSQL 16 running with TimescaleDB + pgvector extensions), P0-019 complete (PgBouncer configured), Guinevere services generating real workload for at least 24 hours.
**Cost Impact:** $0/month (configuration-only tuning, no additional resources)
**ADR References:** ADR-027 (PostgreSQL as Primary Database), ADR-009 (TimescaleDB for Time-Series Data)
**Acceptance Criteria:** AC-CORE-005 (Database performance meets SLO targets: query p99 < 100ms for hot paths, VACUUM completes without impacting production, no unused indexes consuming write overhead)
**Estimated Time:** 3 hours

#### Context

PostgreSQL 16 with TimescaleDB + pgvector running on shared VPS (4C/16GB, 8GB cgroup cap for Guinevere). Configuration tuning targets Guinevere's specific workload pattern: write-heavy financial transactions into TimescaleDB hypertables, read-heavy surveillance queries against memory tables, and pgvector similarity searches for memory recall. Research findings: enable pg_stat_statements for slow query analysis (previously disabled), query for unused indexes that waste write performance, tune work_mem/shared_buffers/effective_cache_size for the 8GB cgroup limit, verify PgBouncer transaction mode pooling. TimescaleDB-specific: chunk interval optimization, continuous aggregates for financial dashboards, compression policies for old time-series data. All configuration changes must be measured against AC-CORE-005 SLO targets.

#### Commands

```bash
# 1. Enable pg_stat_statements extension (requires restart)
psql -U guinevere -h localhost -d guinevere \
  -c "CREATE EXTENSION IF NOT EXISTS pg_stat_statements"
# Add to shared_preload_libraries in postgresql.conf:
grep -q "pg_stat_statements" /etc/postgresql/16/main/postgresql.conf \
  || echo "shared_preload_libraries = 'pg_stat_statements,timescaledb'" \
  >> /etc/postgresql/16/main/postgresql.conf
systemctl restart postgresql
# Verify it loaded:
psql -U guinevere -h localhost -d guinevere \
  -c "SELECT extname, extversion FROM pg_extension WHERE extname='pg_stat_statements'"

# 2. Top 20 slow queries analysis (after workload has accumulated)
psql -U guinevere -h localhost -d guinevere << 'SQL'
SELECT
  queryid,
  calls,
  ROUND(total_exec_time::numeric, 2) AS total_ms,
  ROUND(mean_exec_time::numeric, 2) AS mean_ms,
  ROUND(max_exec_time::numeric, 2) AS max_ms,
  ROUND((total_exec_time / SUM(total_exec_time) OVER()) * 100, 1) AS pct_total,
  LEFT(query, 120) AS query_preview
FROM pg_stat_statements
WHERE dbid = (SELECT oid FROM pg_database WHERE datname = 'guinevere')
ORDER BY total_exec_time DESC
LIMIT 20;
SQL

# 3. Unused index detection — indexes with zero scans waste write performance
psql -U guinevere -h localhost -d guinevere << 'SQL'
SELECT
  schemaname || '.' || relname AS table_name,
  indexrelname AS index_name,
  pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
  idx_scan,
  idx_tup_read,
  idx_tup_fetch
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND schemaname NOT IN ('pg_catalog', 'information_schema')
ORDER BY pg_relation_size(indexrelid) DESC;
SQL

# 4. VACUUM ANALYZE all tables (update statistics + reclaim dead tuples)
psql -U guinevere -h localhost -d guinevere << 'SQL'
-- Generate and execute VACUUM ANALYZE for all user tables
DO $$
DECLARE
  r RECORD;
BEGIN
  FOR r IN SELECT schemaname, tablename
           FROM pg_tables
           WHERE schemaname NOT IN ('pg_catalog', 'information_schema')
  LOOP
    RAISE NOTICE 'VACUUM ANALYZE %.%', r.schemaname, r.tablename;
    EXECUTE format('VACUUM ANALYZE %I.%I', r.schemaname, r.tablename);
  END LOOP;
END $$;
SQL

# 5. Bloat analysis — identify tables with excessive dead tuples
psql -U guinevere -h localhost -d guinevere << 'SQL'
SELECT
  schemaname || '.' || relname AS table_name,
  n_live_tup,
  n_dead_tup,
  CASE WHEN n_live_tup > 0
    THEN ROUND((n_dead_tup::numeric / n_live_tup) * 100, 1)
    ELSE 0
  END AS dead_tuple_pct,
  last_vacuum,
  last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 0
ORDER BY n_dead_tup DESC
LIMIT 20;
SQL

# 6. Tune postgresql.conf for 8GB cgroup limit
#    Back up current config first
cp /etc/postgresql/16/main/postgresql.conf \
  docs/setup-evidence/P10/STEP-P10-002/postgresql.conf.before
# Apply tuned values:
cat >> /etc/postgresql/16/main/postgresql.conf << 'CONF'

# P10-002 Performance Tuning (Guinevere: 8GB cgroup cap, 4 vCPU)
shared_buffers = 2GB                # 25% of 8GB cgroup limit
work_mem = 64MB                     # Per-operation sort memory
maintenance_work_mem = 512MB        # VACUUM, CREATE INDEX, REINDEX
effective_cache_size = 4GB          # 50% of cgroup — OS + PG cache estimate
effective_io_concurrency = 200      # SSD assumption
random_page_cost = 1.1              # SSD — lower than default 4.0
wal_buffers = 64MB                  # 1/32 of shared_buffers
max_worker_processes = 4
max_parallel_workers_per_gather = 2
max_parallel_workers = 4
autovacuum_max_workers = 2
autovacuum_naptime = 30s
autovacuum_vacuum_scale_factor = 0.05     # More aggressive autovacuum
autovacuum_analyze_scale_factor = 0.025   # More frequent analyze
idle_in_transaction_session_timeout = 300000  # 5 minutes
statement_timeout = 30000                  # 30 seconds
CONF

# 7. Apply and verify configuration
systemctl restart postgresql
# Wait 5 seconds for startup
sleep 5
systemctl is-active postgresql
psql -U guinevere -h localhost -d guinevere \
  -c "SHOW shared_buffers"
psql -U guinevere -h localhost -d guinevere \
  -c "SHOW work_mem"
psql -U guinevere -h localhost -d guinevere \
  -c "SHOW effective_cache_size"

# 8. PgBouncer pool_mode verification (should be transaction mode)
grep "pool_mode" /etc/pgbouncer/pgbouncer.ini
# If not 'transaction', update:
# sed -i 's/pool_mode = .*/pool_mode = transaction/' /etc/pgbouncer/pgbouncer.ini
# systemctl restart pgbouncer

# 9. TimescaleDB compression policy — compress data older than 90 days
psql -U guinevere -h localhost -d guinevere << 'SQL'
-- Check existing compression policies
SELECT * FROM timescaledb_information.compression_settings
WHERE hypertable_schema = 'financial';

-- Add compression policy for financial.transactions (if not exists)
SELECT add_compression_policy('financial.transactions',
  INTERVAL '90 days', if_not_exists => TRUE);

-- Verify expected storage savings (compressed data ~30% of original)
SELECT
  hypertable_name,
  pg_size_pretty(before_compression_total_bytes) AS uncompressed,
  pg_size_pretty(after_compression_total_bytes) AS compressed
FROM timescaledb_information.compressed_hypertable_stats;
SQL

# 10. Continuous aggregate for financial dashboard queries
psql -U guinevere -h localhost -d guinevere << 'SQL'
-- Monthly spending by category (refreshed hourly)
CREATE MATERIALIZED VIEW IF NOT EXISTS financial.monthly_category_spend
WITH (timescaledb.continuous) AS
SELECT
  time_bucket('1 month', created_at) AS month,
  category,
  SUM(parsed_amount) AS total_spend,
  COUNT(*) AS transaction_count
FROM financial.transactions
WHERE transaction_type = 'debit'
GROUP BY month, category
WITH NO DATA;

-- Add refresh policy: update every hour, covering last 2 days
SELECT add_continuous_aggregate_policy('financial.monthly_category_spend',
  start_offset => INTERVAL '2 days',
  end_offset => INTERVAL '1 hour',
  schedule_interval => INTERVAL '1 hour',
  if_not_exists => TRUE);
SQL

# 11. Save post-change configuration for evidence
cp /etc/postgresql/16/main/postgresql.conf \
  docs/setup-evidence/P10/STEP-P10-002/postgresql.conf.after
```

#### Troubleshooting
- **Issue:** PostgreSQL fails to restart after configuration change
  - **Solution:** Check logs: `journalctl -u postgresql -n 50 --no-pager`. Common causes: shared_buffers > available memory, invalid parameter values. Restore backup config and adjust values incrementally
- **Issue:** `shared_buffers = 2GB` causes OOM on 8GB cgroup
  - **Solution:** Reduce to 1GB. PostgreSQL needs OS cache for TimescaleDB chunks and pgvector indexes beyond shared_buffers. Formula: shared_buffers + effective_cache_size + work_mem * max_connections < 8GB
- **Issue:** pg_stat_statements extension fails to create — "already loaded in another database"
  - **Solution:** It must be loaded via shared_preload_libraries in postgresql.conf, then `CREATE EXTENSION` in each target database. Restart required after adding to shared_preload_libraries
- **Issue:** VACUUM ANALYZE takes too long on large hypertables
  - **Solution:** Run during low-usage window. Consider running per-table instead of all-at-once. TimescaleDB hypertables only need VACUUM on active chunks
- **Issue:** Continuous aggregate refresh fails with "data is not yet available"
  - **Solution:** The `start_offset` must be larger than the chunk interval. For 1-month chunks with 90-day compression, 2-day start_offset is safe. Adjust if chunk interval differs

#### Notes
- shared_buffers should be approximately 25% of Guinevere's 8GB cgroup limit (2GB). The remaining memory serves OS cache (effective_cache_size=4GB) + work_mem allocations + OS overhead
- PgBouncer transaction mode pools connections per-transaction rather than per-session, critical for applications that hold connections idle. Verify from P0-019 deployment
- TimescaleDB compression saves approximately 70% storage for old time-series data by applying columnar compression to chunks older than the compression interval
- Do NOT change system-wide PostgreSQL settings that affect Aizanta databases on the same shared VPS. All changes must be scoped to the `guinevere` database or postgresql.conf settings that do not degrade other databases
- The continuous aggregate `monthly_category_spend` is read-only — materialized views store pre-computed results. Query it directly instead of scanning raw transactions for dashboard queries
- Statement timeout of 30 seconds prevents runaway queries from blocking connections. Adjust upward for known-long operations (e.g., pgvector bulk index builds)
- All index drops must be reviewed manually — an index with zero scans might be newly created and not yet used, not truly unused
