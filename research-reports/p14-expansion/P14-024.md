## Goal

Implement a periodic health data freshness monitor that alerts via Discord `#guinevere-health` when no device data has been received for over 2 hours, watch battery drops below 20%, or the WebDAV endpoint becomes unreachable.

---

## Context

The wearable pipeline is fire-and-forget -- Gadgetbridge pushes hourly SQLite exports to WebDAV, and the ingestion pipeline picks them up. Silent failures (Gadgetbridge crash, WebDAV down, phone offline) can go undetected indefinitely without active monitoring. This step adds three watchdog alerts as the canary for the entire P14 data pipeline.

**Three monitoring dimensions:**
1. **Data freshness** -- track last successful sync via `health.sync_log`. Alert if gap exceeds 2 hours (i.e., Gadgetbridge missed 2 consecutive hourly pushes).
2. **Watch battery** -- parse Gadgetbridge metadata for battery percentage. Alert below 20%.
3. **WebDAV connectivity** -- periodic HEAD request to WebDAV endpoint with basic auth. Alert if unreachable.

**Design decisions:**
- All three checks run in a single APScheduler job at 30-minute intervals (consistent with existing P5 scheduler pattern).
- Alerts target dedicated `#guinevere-health` channel (not `#system-health`) to avoid noise pollution.
- Cooldown windows: stale alert resets after data arrives; battery alert re-fires every 6 hours; WebDAV re-fires every 1 hour.
- Battery data stored in a new `health.device_status` table created in this step.
- Freshness checks query `health.sync_log` (P14-003 schema) for the most recent `sync_time`.

**Thresholds (from requirements section 8):**
- `STALE_THRESHOLD_SECONDS = 7200` (2 hours)
- `BATTERY_LOW_THRESHOLD = 20` (percent)
- `CHECK_INTERVAL_MINUTES = 30`

**Why not Prometheus-only alerting?** Prometheus (P14-022) covers operational metrics for Grafana dashboards, but immediate Discord notifications with rich context (device ID, last sync timestamp, battery percentage, suggested action) require application-level logic integrated with the Discord bot channel registry.

### Step 3: Create `src/surveillance/monitoring/health_freshness.py`

The monitoring module contains these components (full implementation written to the file):

**Configuration constants:**
- `STALE_THRESHOLD_SECONDS = 7200` (2 hours)
- `BATTERY_LOW_THRESHOLD = 20` (percent)
- `CHECK_INTERVAL_MINUTES = 30`
- `BATTERY_ALERT_COOLDOWN_HOURS = 6`
- `WEBDAV_ALERT_COOLDOWN_HOURS = 1`

**AlertState dataclass** -- in-memory cooldown tracker with fields: `last_stale_alert`, `last_battery_alert`, `last_webdav_alert`, and boolean flags for `stale_was_active`, `battery_was_low`, `webdav_was_down`.

**Three check functions:**

1. `check_data_freshness(session, channel, device_id)` -- queries `health.sync_log` for most recent `sync_time`; if `(now - last_sync) > STALE_THRESHOLD_SECONDS`, sends Discord rich embed with "Device Data Stale" title, device ID, last sync timestamp, and suggested checks. Auto-resolves with "Device Data Resumed" embed when data flows again. Returns dict with `last_sync`, `seconds_since_sync`, `is_stale`, `alerted`.

2. `check_watch_battery(session, channel, device_id)` -- queries `health.device_status` for latest `battery_pct`; if < 20% and outside cooldown window, sends Discord embed with "Watch Battery Low" title and charge suggestion. Returns dict with `battery_pct`, `is_low`, `alerted`.

3. `check_webdav_connectivity(channel)` -- performs `httpx.AsyncClient.head(WEBDAV_URL)` with basic auth; if unreachable and outside cooldown, sends "WebDAV Endpoint Unreachable" embed. Auto-resolves when connectivity returns. Returns dict with `reachable`, `status_code`, `latency_ms`, `alerted`.

**Orchestrator:** `run_all_checks(session_factory, discord_channel, device_id)` -- calls all three checks sequentially. Each check manages its own alert cooldown independently.

**Registration:** `register_monitor_jobs(scheduler, session_factory, discord_channel, device_id)` -- adds the orchestrator as an APScheduler interval job (30 min) with `misfire_grace_time=300` and `coalesce=True`.

**Helper:** `_build_alert_embed(title, description, color)` -- constructs Discord `Embed` with timestamp and "Guinevere Health Monitor - P14-024" footer.

All alert embeds use color coding: orange (#FFA500) for stale, red (#FF4444) for battery, red (#FF0000) for WebDAV, green (#00FF00) for resolution messages.

## Troubleshooting

- **Issue:** Monitor not sending Discord alerts despite stale data
  - **Solution:** Verify `DISCORD_HEALTH_CHANNEL_ID` is correct and bot has Send Messages + Embed Links permissions in the channel. Check `journalctl -u guinevere-health -f | grep freshness`.
- **Issue:** `sqlalchemy.exc.ProgrammingError: relation "health.sync_log" does not exist`
  - **Solution:** P14-003 schema creation not complete. Run verification: `SELECT * FROM health.sync_log LIMIT 1`.
- **Issue:** WebDAV check always fails with TLS error
  - **Solution:** Monitor runs inside VPS hitting `https://localhost`. If using self-signed cert, ensure `verify=False` is set in the httpx client. Test manually: `curl -k -u user:pass https://localhost/guinevere/health/`.
- **Issue:** Battery alert fires repeatedly even after charging
  - **Solution:** Battery data comes from P14-005 parser. Verify parser is writing to `health.device_status`: `SELECT * FROM health.device_status ORDER BY time DESC LIMIT 5`.
- **Issue:** APScheduler job fires but `run_all_checks` crashes
  - **Solution:** Ensure `httpx` is installed in the health service venv: `pip install httpx`. Check that all three check functions are importable.
- **Issue:** Cooldown not working -- duplicate alerts every 30 minutes
  - **Solution:** `AlertState` is module-level and shared across job invocations in a single-worker process. If running multiple workers, cooldown state is not shared. Post-launch: use Redis-backed cooldown with TTL keys.

---

## Notes

- **Cooldown is in-memory only.** If the service restarts, cooldown resets and alerts may re-fire. Acceptable for MVP. Post-launch enhancement: Redis-backed cooldown (`health.alert_cooldown` table or Redis key with TTL).
- **WebDAV check uses `verify=False`** because the monitor hits localhost via HTTPS where the server certificate may not match. For external WebDAV URLs, set `verify=True`.
- **Device ID resolution:** `xiaomi-watch-s3` is the seed for a deterministic UUID5. If Faiz buys a Band 9, update to `xiaomi-band-9` in config.
- **Prometheus companion:** P14-022 defines `data_freshness_seconds` and `watch_battery_percent` gauges. This module should emit updates to those gauges alongside Discord alerts (post-launch enhancement).
- Cross-reference: P14-002 (WebDAV endpoint), P14-003 (sync_log schema), P14-005 (parser -- populates sync_log and device_status), P14-006 (ingestion -- writes sync_log), P14-025 (systemd service -- runs scheduler with this monitor).
